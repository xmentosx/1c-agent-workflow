## 1C Project Lifecycle

ITL owns lifecycle, bases, MCP, verification, export. Explicit generated `itl-*` skills run alone; other routine requests use only `1c-workflow-fast`. Use `1c-workflow` plus one reference only for non-routine work or helper-directed recovery without an explicit wrapper. 1C Designer/Enterprise LoadConfigFromFiles/UpdateDBCfg needs `timeout_ms >= 3900000`; default `init-project`/`sync-master` needs `>= 14700000`. Exceed configured action limits. Status/help need neither. Do not use `120000 ms`.

On Enterprise failure/timeout/suspected hang, inspect fresh branch `1Cv8Log` entries for its operation window; `/Out` is secondary. Correlate errors with process/state progress and expected duration. Proven failure/stall means stop waiting for the hard timeout; use helper recovery; never kill arbitrary 1C PIDs.

Native `/itl`: return exact helper stdout in one fenced `text` block; preserve line breaks, blank lines, and indentation; write nothing outside. Never summarize, reorder, omit, or merge sections.

The project may have several attached clients; the current session identifies its client without silently attaching it. ITL owns attach/detach/reconcile, shared-file ownership, and per-client model settings. Its project skills remain under `.agents/skills`; updating workflow across registered worktrees does not merge business configuration or run 1C tests.

Classify code/metadata independently as `executionPath=quick-fix|full-cycle` and `planningMode=direct|OpenSpec`; all four pairs are valid. Default `direct`; use OpenSpec on request or for agreement. Promotion triggers set only `executionPath=full-cycle`. Quick-fix obeys `QUICKFIX_MAX_LINES`; it needs sufficient current evidence, while retaining a regression and its cadence are separate risk-based decisions. OpenSpec explore/propose/apply/archive/update/sync read rules, activate required skills/docs, record `Context Sources`, preserve an existing approved plan, follow approved artifacts at apply, and finish with evidence. A separate `test-plan.md` is optional. Resolve a pinned OpenSpec CLI through the ITL helper; never run an unqualified global `openspec` or an arbitrary `openspec update`. Memory never replaces preflight.

Until the separate external-store feature is installed, managed OpenSpec supports only this checkout's local `openspec/` workspace. Before any OpenSpec write, resolve it with the ITL `openspec-context` helper. `OPEN_SPEC_EXTERNAL_STORE_DEFERRED` stops that phase before direct CLI/bundle writes, including `--store`, sync and archive moves; preserve the external binding and documents. Continue only after an explicit choice to use a local workspace for this project or a later qualified external-store release; never silently create a local substitute.

For PM5 product logic, architecture, workflows, permissions, reports, integrations, acceptance tests, or OpenSpec, activate `.agents/skills/product-docs/SKILL.md`. For the same OpenSpec scope, reuse current/proposal `Context Sources`; otherwise search `BookStack-product-docs-mcp` before broad repository traversal. Use sufficient non-duplicative current evidence; never repeat native discovery after sufficient code/graph MCP results. Cite sources and surface conflicts. PM4 uses a helper-installed replacement.

Use sibling `itldev/*` worktrees and only the state-proven copied branch infobase. Never load/dump/test against the source infobase. `/update1cbase`, `/loadfrom1cbase`, `/getconfigfiles`, and `/deploy-and-test` are ITL bridges that reconcile branch state. On `master` or outside managed `itldev/*`, they stop without mutation.

Pending extension branches ask Empty/CFE, name, and optional path, then initialize internally there. Never give PowerShell; blocked actions return `EXTENSION_INIT_REQUIRED`.

`ITL_YAXUNIT_TESTING`, `ITL_VANESSA_TESTING`, `ITL_CHECK_EVENT_LOG`: `auto|manual|off` (`auto`). For algorithms, recovery, or optimization, `yaxunit-tests.md` is mandatory, including its boundary matrix, optimization invariants, test grouping, and benchmark cadence. Integration/UI needs Vanessa; complex changes may need both. Classify changed tests and post-adoption BSL; reuse coverage or justify exact YAxUnit non-applicability per `verification-suite-selection.md`. Resolve gaps yourself before `/itl-check`.

Quick-fix is no exception; `verify_xml`/static are prechecks. Use targeted/static checks while implementing; run executable milestones only to decide continuation. Run fresh unfiltered `/itl-check` after the last relevant edit. Its assessment may use sufficient current one-off proof without requiring a retained suite; fragment-only proof remains partial. Missing/invalid YAxUnit JUnit, zero tests, failures, or errors in a selected run fail verification. Otherwise report `pending verification`. `off` prevents automatic invocation; only an explicit named request permits that run, and the permission expires when it ends. Valid proof from the run may be reused by later check/export without rerunning it.

After a failed check, classify ownership before editing: `runner` (ITL helper/topology/profiles/ports), `fixture` (scenario/data setup), or `product` (proven behavior/assertion). The ITL helper exclusively owns `TESTMANAGER -> TESTCLIENT`; runner/profile/port evidence never authorizes product/feature workarounds without proof of their defect. Do not repeat the same unchanged run without new evidence or a code/config change. On loaded-skill/installed-file conflict, stop lifecycle commands and resolve the stated `/reload` or version/cache mismatch. Preserve unrelated dirty changes; revert only owned diagnostic edits.

Execution `off` does not prohibit authoring needed tests; preserve approved plans. A skipped required obligation records `partial/skipped`, never a normal fresh pass. `verificationPolicy=block` requires sufficient fresh passed evidence, including valid one-off proof when accepted by the assessment owner. `warn` permits warned export without confirmation; advanced close retains confirmation. Report genuinely skipped verification as `implemented; executable verification skipped`, never `verified`, `ready`, or `done`.

For suspected workflow defects or contradictory rules, follow `1c-workflow/references/workflow-incidents.md`: consult saved fixes, recover or propose a concrete scoped workaround, reuse the user's authorization, write a transferable report, and resume the original task. Preserve independent progress and truthful verification status. Recorded patches retire only on workflow replacement; configuration-only refresh preserves them. A new barrier must include an agent-usable continuation.

Keep `USER-RULES.md` above `LLM-RULES.md` in precedence. `LLM-RULES.md` changes only through an explicit `/evolve`, one separately confirmed change at a time; `/evolve` cannot weaken branch safety, preflight, approved-plan, verification-mode, result, or fresh-check gates. Rules updates preserve `LLM-RULES.md`. Retain user-authored overrides; report an exact conflict with the affected operation and pause only that dependent operation.

## Shared Cross-Project Memory

Global `1c-templates-mcp` `remember`/`recall` is shared across projects, not project memory. `remember` only verified, non-confidential facts safe and useful across unrelated projects, preferably on an explicit cross-project retention request. Never store project objects/decisions, customer data, paths/endpoints, source/runtime evidence, secrets, or PII. Put project-specific facts and corrections in that project's `memory.md`; upstream correction capture never requires shared `remember`. Do not run shared `recall` by default: use it only when cross-project platform/tooling/workflow/team knowledge is relevant, and verify results against the current project. `templatesearch` is unaffected.

Use pinned `update-ai-rules`, `update-workflow`, and `/itl-refresh`; never hidden `/installmcp`, `/updatemcp`, `/checkmcp`, or `/updaterules`. Use ITL MCP helper requests. Qualify remote `vibecoding1c` and branch-local MCP separately; route deferred discovery, including Codex `ALL_TOOLS`, to `1c-workflow/references/mcp.md`. On-demand MCP is diagnostic, not a gate. Test `rtk rewrite` on the lifecycle helper; exclude only observed rewrites, then restart. Preserve `.agent-1c/event-log-baselines/*.json` and Vanessa `TESTMANAGER -> TESTCLIENT`. Search hygiene: ignore secrets/runtime, preserve user config; inspect only named runs under `.agent-1c/runs/` or `build/test-results/`.

Let bounded database executions finish or cancel them through their exact owner. A visible `waiting-for-base` state is normal serialization for one canonical base; work on other bases and file-only workflow phases may continue. Never stop a foreign or ambiguously identified 1C process, edit `execution-guards-v2` diagnostics, or treat old database-access tickets as authority. A bounded `execution-conflict` requires the exact external activity to finish; after it ends, repeat the original operation without recovery or manual unlock.
