# Скрытый клиент тестирования: результаты пробы

Дата: 2026-11-09. Платформа 8.3.27.2130, тонкий клиент, Windows 11, файловая
база. Связано с `docs/testclient-focus-plan.md`.

## Вопрос

Можно ли запускать клиент тестирования скрытым и показывать его только на время
ввода с клавиатуры, управления мышью или снимка, а потом снова скрывать?

## Как проверяли

- Одноразовая файловая база с пустой конфигурацией, в неё добавлена общая форма
  `HiddenProbe`: поле «Текст», кнопка «Открыть диалог». Кнопка открывает ту же
  форму в режиме `БлокироватьОкноВладельца`, через 3 с форма показывает
  `ПоказатьПредупреждение` с тайм-аутом 6 с. Форма пишет события в лог (время UTC
  в мс).
- Клиент `/TESTCLIENT` и менеджер `/TESTMANAGER` запускались через
  `Start-Process -WindowStyle Hidden`.
- Внешний наблюдатель (P/Invoke) каждые 100 мс перебирал все окна верхнего
  уровня процессов 1С, включая скрытые: класс, заголовок, видимость, владелец,
  окно переднего плана. Снимки делались через `PrintWindow`.
- Пробная форма запускалась из самой конфигурации, а не через `/Execute`:
  внешняя обработка без пользователей ИБ показывает «Предупреждение
  безопасности», а COM-коннектор на машине не зарегистрирован.
- Скрипты и лог: каталоги `hidden-probe` и `hidden-probe-tools` во временном
  каталоге сессии, в репозиторий не входят.

## Результаты

| Что проверяли | Результат |
|---|---|
| Главное окно (`V8TopLevelFrameSDI`) при `-WindowStyle Hidden` | Остаётся скрытым и у клиента, и у менеджера |
| Заставка «Загрузка конфигурационной информации...» | Видима около 1,5 с при каждом старте и выходит на передний план |
| Поиск скрытого окна снаружи | `EnumWindows` и отбор по PID и классу `V8TopLevelFrameSDI` находят его; `Process.MainWindowHandle` у скрытого окна равен 0 |
| Подключение менеджера к скрытому клиенту | С первой попытки; `НайтиОбъекты` видит 2 окна клиента |
| Ввод и нажатия по протоколу тестирования | `ВвестиТекст` в поле и `Нажать` на кнопке работают в скрытом окне; клиент получил «проба», диалог открылся |
| Новые окна скрытого клиента: форма `БлокироватьОкноВладельца`, `ПоказатьПредупреждение` | Появляются **видимыми** на экране (`V8TopLevelFrameSDIsec`, владелец — скрытое главное окно). Признак «скрыть» действует только на главное окно |
| `PrintWindow` скрытого окна (`PW_RENDERFULLCONTENT` и 0) | Полностью чёрный снимок |
| `ShowWindow(SW_SHOWNA)` из другого процесса | Окно появляется без активации, передний план не меняется; снимок после 0,8 с полный и корректный |
| `ShowWindow(SW_HIDE)` после показа | Окно снова скрыто, снимок снова чёрный |
| `ShowWindow(SW_SHOW)` и `SetForegroundWindow` из другого процесса | Окно появилось и стало активным (`SetForegroundWindow` = `True`) |
| Передний план после повторного скрытия активного окна | Уходит к следующему окну по Z-порядку, а не обязательно к окну, где работал пользователь |
| Передний план при старте | Скрытое главное окно клиента или менеджера само становится окном переднего плана и держит его до переключения пользователем (в одном прогоне около 20 с) |
| `ForegroundLockTimeout` | Действующее значение 1 мс, в реестре 200000 (аномалия из `testclient-focus-plan.md` сохраняется) |

## Выводы

1. **Схема реализуема для главного окна.** Скрыть клиент, показывать его
   (`SW_SHOWNA` для снимка, `SW_SHOW` и `SetForegroundWindow` перед вводом ОС) и
   скрывать обратно можно из постороннего процесса без прав администратора.
   Протокол тестирования со скрытым окном работает полностью, поэтому обычные
   шаги Vanessa показа не требуют.
2. **Снимок требует показа.** Фонового снимка скрытого окна нет; нужен показ без
   активации (`SW_SHOWNA`), ожидание отрисовки (в пробе 0,8 с, минимум не
   измерялся), снимок и скрытие.
3. **Диалоги и отдельные окна не скрываются.** Модальные формы, предупреждения,
   вопросы и окна `БлокироватьОкноВладельца` появляются видимыми. Чтобы они не
   мелькали, их нужно скрывать отдельно: отслеживать новые окна верхнего уровня
   процесса клиента и прятать их. Это постоянно работающий наблюдатель, а не
   разовый вызов. Насколько такие окна часты в реальных сценариях, проба не
   измеряла.
4. **Скрытое окно забирает клавиатуру.** При старте скрытое главное окно
   становится окном переднего плана: нажатия пользователя уходят в невидимую 1С
   (в том числе Enter в активную кнопку). Причина, вероятно, та же: действующий
   `ForegroundLockTimeout` = 1 мс. Со штатной блокировкой не проверялось. Это
   нужно закрыть до внедрения: после старта и после каждого скрытия возвращать
   передний план прежнему окну пользователя.
5. **Заставка видна при каждом старте** около 1,5 с и забирает передний план.
   Убрать её снаружи можно только тем же наблюдателем.
6. **Нужен свой поиск окна.** VanessaExt `НайтиКлиентТестирования` и
   `ПолучитьСписокОкон` скрытое окно не видят (коммит `5b432565`, отказ
   `get_window_list_os` в Release E2E). Дескриптор должен давать помощник ITL
   по PID.

## Ввод VanessaExt (первый прогон, 2026-11-09 19:59)

Менеджер подключал VanessaExt из макета `WindowCaptureComponent` сборки ITL
r8 (`ПодключитьВнешнююКомпонентуАсинх`, неизолированно; установка не
понадобилась). Наблюдатель ITL по запросу менеджера показывал окно клиента
(`SW_SHOW` и `SetForegroundWindow`), а после шага скрывал его и возвращал
передний план окну пользователя. Пауза после показа — 0 мс.

| Шаг | Результат |
|---|---|
| VanessaExt `АктивироватьОкно` для скрытого окна | Окно осталось скрытым, передний план не сменился |
| Показ наблюдателем перед вводом с клавиатуры | Окно показалось, но `SetForegroundWindow` вернул `False`: передний план остался у окна пользователя (PM5) |
| `ЭмуляцияВводаТекста("клав")` и Tab | Клиент текст не получил. Нажатия ушли в активное окно пользователя |
| Показ перед кликом мыши | `SetForegroundWindow` = `True`, окно клиента активно |
| Клик в координаты кнопки сразу после показа | Кнопка не сработала. Позже выяснилось: координаты пробы были неверны из-за масштаба 200% (см. ниже), отрисовка ни при чём |
| Скрытие и возврат переднего плана пользователю | Все три раза успешно (`SetForegroundWindow` = `True`) |

Выводы:

- Активация из постороннего процесса ненадёжна даже при `ForegroundLockTimeout`
  = 1 мс: из двух попыток одна не удалась. Ввод ОС без проверки «окно клиента
  действительно на переднем плане» отправляет нажатия в чужое окно. Проверка
  непосредственно перед каждым вводом обязательна (в ITL r10 она уже есть для
  случая «клиент уже активен», но не для случая «активация не удалась»).
- VanessaExt сама скрытое окно не показывает.
- Пауза после показа не нужна (см. следующий раздел).

## Ввод VanessaExt с защитой (2026-11-09 20:40–20:54)

Изменения по сравнению с первым прогоном:

- Наблюдатель активирует окно по цепочке: `SetForegroundWindow`; при неудаче
  пустое движение мыши через `SendInput` (процесс становится источником
  последнего ввода) и повтор; затем `AttachThreadInput`. Каждое действие —
  до 3 попыток. Результат (`plain`/`nudge`/`attach`/`fail`) передаётся
  менеджеру.
- Менеджер вводит только если наблюдатель вернул не `fail` и VanessaExt
  `АктивноеОкно` равно дескриптору клиента. Иначе шаг пропускается.
- Перед скрытием фокус возвращается окну пользователя той же цепочкой, пока
  клиент ещё видим; окно пользователя запоминается **до запуска 1С**.
  Положение курсора восстанавливается.

| Проверка | Результат |
|---|---|
| Активация показанного клиента | 18 из 18 в последней серии (все `plain`); в более ранних сериях часть удавалась только через `attach` или `nudge`, `fail` не было |
| Защита ввода | Ни одного пропуска, ни одного ввода в чужое окно |
| `ЭмуляцияВводаТекста` и Tab, паузы после показа 0/100/250/500 мс | Клиент получил текст во всех случаях, включая паузу 0 мс |
| Клик: VanessaExt `УстановитьПозициюКурсора` + `ЭмуляцияНажатияМыши(0)` | Работает при паузах 0/100/250 мс |
| Клик: VanessaExt `ЭмуляцияДвиженияМыши` + `ЭмуляцияНажатияМыши(0)` | Работает |
| Клик: `SendInput` наблюдателя | Работает |
| Возврат фокуса окну пользователя перед скрытием | 6 из 6 в последней серии, 11 из 12 обычным `SetForegroundWindow` и 1 через `nudge` в предыдущей |
| Возврат фокуса, если окно пользователя запомнено после старта 1С | 0 из 18: к этому моменту передний план уже у заставки или скрытого окна 1С |
| VanessaExt `АктивироватьОкно` для скрытого окна | Окно не показывается (из первого прогона) |

Ловушка DPI (масштаб 200%): процесс без поддержки DPI получает от
`GetWindowRect` логические координаты, а `PrintWindow` отдаёт физические
пиксели и обрезает снимок по логическому размеру. Координаты, взятые с такого
снимка, нельзя умножать на масштаб. Источник координат для клика и сам клик
должны работать в одной системе координат. VanessaExt (`ПолучитьРазмерОкна`,
`УстановитьПозициюКурсора`) работает в физических; помощник ITL должен
включать `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)`. Первые
неудачные клики были ошибкой пробы, а не 1С.

Выводы для схемы «скрыт → показать для ввода → скрыть»:

1. Ввод с клавиатуры и мышью VanessaExt в показанное на время окно работает
   без дополнительной паузы после показа (0 мс достаточно на этой машине).
2. Без защиты схема опасна: неудачная активация отправляет ввод в окно
   пользователя. Обязательны: активация с проверкой, подтверждение
   `АктивноеОкно` в VanessaExt перед каждым вводом и отказ от ввода при
   несовпадении.
3. Фокус надо возвращать до скрытия клиента, и цель возврата запоминать до
   запуска 1С и обновлять только окнами не из процессов 1С workflow.
4. Цикл показа и скрытия занимает около 0,5–1 с на шаг ввода, вместе с
   паузами пробы. Окно клиента на это время видно и активно, нажатия
   пользователя в этот промежуток уйдут в 1С.

## Что не проверено

- Штатный `ForegroundLockTimeout` (200000): все прогоны шли при действующем
  значении 1 мс; со штатным активация из постороннего процесса, вероятно,
  будет отказывать чаще, и `nudge` или `attach` станут обязательными.
- Ввод VanessaExt через шаги Vanessa (а не прямые вызовы компоненты), выпадающие
  списки и другие окна, которые 1С открывает отдельными окнами ОС.
- Одновременная работа пользователя мышью и клавиатурой во время шага ввода.
- Поведение со штатным `ForegroundLockTimeout`.
- Толстый клиент, Windows 10 и Server 2019, терминальная сессия.
- Частота отдельных окон и диалогов в типичных сценариях проекта.

## `/DisableSplash` и скрытые диалоги (2026-11-10, задачи 1.3 и 1.5)

Стенд — та же база пробы; все процессы запускались `Start-Process -WindowStyle
Hidden`. Наблюдатель опрашивал окна процессов 1С каждые 15 мс.

### Заставка (задача 1.3)

| Запуск | Без `/DisableSplash` | С `/DisableSplash` |
|---|---|---|
| `/TESTCLIENT`, 8.3.27.2130 | Окно «Загрузка конфигурационной информации...» видно | Видно так же |
| `/TESTCLIENT`, 8.5.4.1878 | Видно (класс `V8Window0.0`), берёт передний план | Видно, берёт передний план |
| `/TESTMANAGER`, 8.3.27.2130 | Окна загрузки нет | Окна загрузки нет |
| `/Execute`, 8.3.27.2130 | Окна загрузки нет | Окна загрузки нет |

- `/DisableSplash` окно загрузки клиента тестирования не убирает: результат
  отрицательный, действует вариант решения 7 `design.md`.
- Скрыть это окно снаружи быстрее платформы нельзя. `ShowWindow(SW_HIDE)`
  блокируется, а `ShowWindowAsync(SW_HIDE)` возвращается за 5 мс, но окно
  становится невидимым через 1,0–1,1 с: поток загрузки не обрабатывает
  сообщения. Без скрытия окно живёт около 1,7 с. Помощник сокращает показ
  заставки примерно до 1 с, но не до 250 мс.
- У менеджера и `/Execute` заставки нет, но скрытое главное окно при старте
  берёт передний план. Возврат окну пользователя удался во всех 6 прогонах
  (`plain`, один раз `nudge`).

### Скрытые диалоги (задача 1.5)

Клиент скрыт, менеджер через протокол тестирования вводит текст и нажимает
кнопку «Открыть диалог». Форма открывается в режиме `БлокироватьОкноВладельца`
и через 3 с показывает `ПоказатьПредупреждение`. Наблюдатель скрывает
(`SW_HIDE`) каждое видимое окно верхнего уровня клиента сразу после появления.

| Проверка | Результат |
|---|---|
| Время от появления диалога до скрытия | 21 мс (форма) и 9 мс (предупреждение), включая `PrintWindow` до скрытия: 20 и 8 мс |
| Снимок диалога до скрытия | Полный, не чёрный |
| Передний план при появлении диалога | Остался у окна пользователя: диалоги скрытого клиента передний план не забирают |
| Поиск скрытого диалога менеджером | `ПолучитьАктивноеОкно()` возвращает скрытую модальную форму; `НайтиОбъекты` видит 4 окна |
| Ввод в скрытый диалог | `ВвестиТекст` в поле диалога работает, событие изменения пришло |
| Нажатие в скрытом предупреждении | `Нажать` на кнопке OK закрывает предупреждение, затем закрывается диалог |

Результат положительный: реализация продолжается. У объекта
`ТестируемоеОкноКлиентскогоПриложения` нет свойства `Модальное`; модальное окно
находит `ПолучитьАктивноеОкно()`.

Выводы для помощника:

- Снимок для журнала делается до скрытия: после скрытия `PrintWindow` даёт
  чёрный снимок. У окна загрузки `PrintWindow` блокируется так же, как
  скрытие (1,1 с), поэтому его помощник прячет без снимка.
- Скрытие и снимок идут асинхронно (`ShowWindowAsync`, снимок с пределом
  ожидания), чтобы занятый поток 1С не останавливал помощника.
- После заставки скрытое главное окно клиента берёт передний план: его
  возвращает помощник по `EVENT_SYSTEM_FOREGROUND`.

## Служебные формы `VAExtension` в скрытом клиенте (2026-11-11, change `agent-window-control`)

Стенд — та же пустая конфигурация 8.3.27.2130 с общей формой пробы, в две базы
загружено расширение `VAExtension` из исходников r13:

- исходное;
- с удалённым `<WindowOpeningMode>LockOwnerWindow</WindowOpeningMode>` у шести
  форм обработок.

Клиент тестирования и менеджер запускались скрытыми (`-WindowStyle Hidden`,
`/DisableSplash`). Менеджер повторял путь Vanessa
(`ОткрытьНавигационнуюСсылку`): `ГлавноеОкно.ВыполнитьКоманду("e1cib/app/Обработка.<форма>")`,
затем `НайтиОбъект(Тип("ТестируемаяФорма"), , "*.<форма>.*")`. Пять форм:
`ВыполнитьПроизвольныйКод`, `ДанныеТекущегоОкна`, `ПолучениеДанныхИзБазы`,
`ПолучениеМакета`, `НажатьГиперссылкуHTMLДокумента`. Показ окон записывал
`scripts/measure-foreground-changes.ps1` (событие `show`).

| Вариант | Показы окон клиента, кроме заставки | Формы найдены тестовым API |
|---|---|---|
| Исходное расширение | 4 окна `V8TopLevelFrameSDIsec` — у каждой формы `LockOwnerWindow` — и по 4 дочерних `V8Window` | 5 из 5 |
| Независимый режим | 0 | 5 из 5 |

Форма `ПолучениеДанныхИзБазы` уже была независимой и окна не показывала и в
исходном варианте. Формы расширения находят нужное окно по заголовку через
`ПолучитьОкна()`, а не через владельца. Поэтому смена режима окна не меняет их
логику.

Вывод: мелькание даёт режим `LockOwnerWindow`, а не ссылка `e1cib/app`.
Ревизия `1.2.043.42-itl-r14` убирает этот режим у шести форм расширения. Код
Vanessa не меняется.
