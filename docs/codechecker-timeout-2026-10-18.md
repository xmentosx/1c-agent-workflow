# CodeChecker: незавершённый assistant после успешного результата ITS

Дата диагностики: 2026-10-18. Адресат: владелец `comol/1c-code-checker`
и владелец upstream API `code.1c.ai`. Отчёт подготовлен для передачи;
обращение в поддержку автоматически не отправлялось.

## Вывод и граница доказательства

В двух изолированных вызовах `its.fetch({"id":"root"})` upstream успешно
возвращает результат инструмента, затем начинает новое сообщение assistant,
которое не завершается до истечения бюджета клиента. Первый поток того же
вызова клиент завершает сразу после `assistant.finished=true`, до EOF.
Общее нераспознавание `finished=true` и ожидание EOF этим воспроизведением
исключаются. Во втором потоке не получено завершение именно нового assistant.

Наблюдение сделано на границе HTTP-клиента CodeChecker: исходные строки
`httpx.Response.aiter_lines` передавались установленному парсеру без изменений.
Это доказывает незавершённый upstream-этап, но не раскрывает внутреннюю причину
в модели, оркестраторе или API code.1c.ai. Для неё нужны серверные логи upstream.
Успешный результат ITS не означает завершение последующего assistant-ответа.

## Почему клиент продолжает ждать

Установленный `OneCApiClient._get_post_result_instruction("its.fetch")`
требует после результата инструмента подробный ответ assistant с содержанием
документа. Поэтому `tool.finished=true` завершает результат инструмента,
но не весь обмен. Нельзя называть это событие пропущенным завершением assistant:
у нового assistant другой UUID и собственный `finished=false`.

Ещё один подтверждённый дефект бюджета находится в читаемом
`/app/MCP_1copilot/mcp_server.py`: `_call_capability` создаёт бюджет на строке
469; после его timeout внешний обработчик переходит в `_fallback`.
На строках 585–589 fallback получает отдельный бюджет через `_send_prompt`,
а на строке 396 `_send_prompt` создаёт новый бюджет при отсутствии переданного.
В текущей телеметрии существующих вызовов это даёт около 600 с:

- `requestId=3f057a9006f047bda1bcf85f3a140823`: direct завершился ошибкой
  `OperationTimeoutError` в `2026-10-18T18:33:54.847Z`, через 299921 мс;
  prompt завершился такой же ошибкой в `18:38:54.835Z`, через 299921 мс;
  `tool_end.elapsedMs=600004`.
- Для этого же `fetch_its(root)` есть успешный direct-вызов
  `requestId=b912be5c91854323961e22eabff83717` в `18:38:28.475Z`,
  `upstream_attempt_end.elapsedMs=1460`. Отказ перемежающийся, не общая
  недоступность сервиса или MCP.

`outcome=returned` у `tool_end` не доказывает успешный ответ: внутри такого
вызова оба upstream-attempt могут завершиться ошибкой. Приёмку нужно оценивать
по содержанию результата и статусам попыток.

## Владельцы и требуемое исправление

1. **code.1c.ai:** выяснить, почему после успешного ITS tool result новый
   assistant остаётся незавершённым. Сервис должен завершать этот этап либо
   возвращать явную ошибку, а не только поддерживать SSE comments.
2. **`comol/1c-code-checker`:** проверить контракт post-result ответа в
   `OneCApiClient._call_capability_guarded`, `_collect_stream_inner` и
   `_get_post_result_instruction`. Определить корректный возврат уже полученных
   данных инструмента при сбое дополнительного assistant, не выдавая частичный
   результат за полностью успешный ответ. Согласовать общий бюджет direct /
   fallback / caller и не запускать новое полное ожидание после его исчерпания.
3. **ITL workflow:** не вызывать генеративный `fetch_its(root)` периодически
   для определения доступности MCP. При совпавших container-bound identity и
   tools/list сохранять `status/health=running`, а timeout другого инструмента
   показывать отдельно в `functionalStatus/functionalMessage`. Только операция,
   использующая этот инструмент, может требовать его успешного выполнения.

Критерии приёмки владельца CodeChecker: реальный `its.fetch(root)` с наблюдением
двух фаз потока; сохранение непустого результата инструмента; явное завершение
либо типизированный отказ последующего assistant; один согласованный общий
deadline; отсутствие фоновой работы/fallback после отмены или исчерпания
бюджета. Детерминированный regression должен воспроизвести `tool.finished=true`
и последующие SSE comments без `assistant.finished=true`.

## Объём и сохранность

Выполнены два диагностических read-only вызова, оба в отдельных процессах
в том же контейнере. Наблюдатель менял iterator только в своём процессе и
передавал строки парсеру без изменений. Каждый процесс закрыл собственный
API client и завершился. Рабочий сервер, env, файлы, образы и настройки не
изменялись; индексы и контейнерные данные не затрагивались.
После диагностики остался только основной Python PID 1074; container ID прежний,
`StartedAt=2026-10-18T10:08:34.080120014Z`, `RestartCount=0`, состояние `running`.
Исправление самого CodeChecker и отправка отчёта владельцу в эту задачу не входят.
