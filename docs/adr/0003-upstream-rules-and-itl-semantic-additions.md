# Новый каркас upstream с явным сохранением смысловых дополнений ITL

Принято 2026-09-28 при разборе перехода с controlled fork
`451c5a52e5b614c67406445d4af4b636da043aec` на upstream
`20a083e5bd9fa41402ad8428b740c4c01f0cc3d6` (решения Q15–Q17).
Это решение об архитектуре правил; обновление пакета и установленных проектов
ещё не выполнено.

Основой правил установленных проектов становится новый каркас upstream.
Самостоятельная полная редакция `AGENTS.md`, которую сейчас подставляет ITL,
заменяется адресными дополнениями к новым смысловым владельцам правил.
У каждого дополнения сохраняются назначение, условие загрузки, обязательное
действие, исключения, приоритет и результат при невыполнении. Обязательный
компактный контракт закрепляет владение ITL базами, MCP, проверкой и
восстановлением; подробности загружаются соответствующим маршрутом. Корневой
`AGENTS.md` исходного workflow остаётся отдельным контрактом сопровождения.
Пользовательский текст в `USER-RULES.md` сохраняется.

Причина выбора: новый upstream сам разделил прежний большой корневой файл и
назначил отдельных владельцев, включая `mcp-policy.md` и стандарты из MCP.
Подстановка старого корня может отключить новые обязательные маршруты; принятие
всех новых файлов без сверки может потерять наши исправления. Поддержка собственной
полной редакции снова создала бы параллельную политику и постоянную ручную
синхронизацию. Поэтому для каждого прежнего дополнения требуется явное решение:
сохранить у нового владельца, адаптировать к согласованному поведению или удалить
с обоснованием. Отсутствие текстового конфликта и совпадение контрольной суммы
сами по себе не доказывают сохранение смысла.

При этом сохраняются только действующие обязательства с учётом принятых изменений,
в том числе [разделения доказательств и сохранённых тестов](0001-verification-evidence-and-retained-tests.md).
Принятый новый reviewer gate допускает отдельного reviewer при явно выбранной и
фактически применяемой модельной настройке; иначе запрошенное ревью выполняет
основной агент, сохраняя обязательные проверки и честно называя исполнителя.
Уровень `1c-error-fixer` меняется с `light` на `coding`.

Наше дополнение к исправлению ошибок сохраняет ограниченный поиск аналогичных
проявлений подтверждённой причины в области текущей задачи. Одну причину исправляет
один пишущий исполнитель; параллельное исследование и проверка допустимы.
Локальное исправление одного модуля остаётся у error-fixer, более широкая область
передаётся основному агенту для назначения подходящего исполнителя. Повторение
ошибки само по себе не требует OpenSpec, новой абстракции или аудита всей
конфигурации. Выбор `coding` меняет модельный уровень, а не полномочия.

Действующий реестр путей и текстовые anchors относятся к прежнему intake.
Они должны быть согласованы с новыми владельцами и принятыми изменениями через
[процесс обновления fork](../ai-rules-fork-upgrades.md). Этот ADR фиксирует выбор,
но не заменяет полную сверку downstream-добавлений и квалификацию нового результата.
