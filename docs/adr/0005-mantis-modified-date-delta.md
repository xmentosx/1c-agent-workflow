# Дельта по дате изменения обращения вместо регулярного полного обхода

28 сентября 2026 года пользователь подтвердил отдельную контрольную точку каждого проекта по **дате последнего изменения обращения** (`updated_at` в REST, `last_updated` в SOAP), а не по дате создания. Выбран инкрементальный маршрут с целью обновления обычных изменений за пять минут при исправных зависимостях: чтение недавних страниц до сохранённой границы с перекрытием, получение новых или изменённых обращений и обновление только затронутых фрагментов. Неизменённое содержимое не отправляется повторно на эмбеддинги; новый доступный проект получает собственную первичную загрузку с сохранением индексов остальных проектов. Регулярный полный обход доступной базы и полная повторная индексация не выбраны.

На работающем `support.itland.ru` read-only запрос `GET /api/rest/issues?project_id=814&filter_id=any&page_size=10&page=1&select=id,project,status,updated_at` и следующая страница вернули 20 разных обращений нужного проекта по убыванию `updated_at`, включая 17 закрытых: около 2,7 КБ и 0,12 секунды на страницу. Это подтверждение маршрута и выборки, а не нагрузочная квалификация всей базы или доказательство полноты при параллельных изменениях. [Штатный REST-путь](https://github.com/mantisbt/mantisbt/blob/release-2.28.1/api/rest/restcore/issues_rest.php) допускает такой опрос; повторные timestamps, перемещение записей между страницами и возобновление после сбоя требуют сохранения перекрытия, дедупликации и контрольной точки только завершённой обработки.

Дата обращения в upstream 2.28.1 не отражает некоторые изменения связанных данных: [смену приватности комментария](https://github.com/mantisbt/mantisbt/blob/release-2.28.1/core/bugnote_api.php), [удаление вложения](https://github.com/mantisbt/mantisbt/blob/release-2.28.1/core/file_api.php) и [переименование метки](https://github.com/mantisbt/mantisbt/blob/release-2.28.1/core/tag_api.php). Для меток отдельно подтверждён read-only `mc_tag_get_all`: 354 записи с `date_updated`. Для остальных исключений пользователь выбрал проверку найденных и открываемых обращений при доступном Mantis вместо регулярной сверки всей базы; при сбое действует [сохранение кэша](0002-mantis-cache-until-confirmed-revocation.md). Принятая цена этого выбора: например, ставший публичным комментарий без сдвига даты обращения может не попасть в поиск, пока обращение не перечитано; безусловная пятиминутная полнота таких исключений не обещается.

Альтернатива серверной выборки по диапазону дат существует в SOAP `mc_filter_search_issue_headers`, но две read-only попытки на установленном сервере вернули HTTP 500 с предупреждением `foreach() argument must be of type array|object, null given`. Причина без серверного trace не установлена; этот путь не квалифицирован и не является предпосылкой выбранного работающего REST-маршрута. Изменения или исправления самого Mantis в объём решения не входят.
