# Перенос проверяют по изменениям в подключённой базе

Для первого варианта переноса используем существующую подключённую к хранилищу ИБ, в которой разработчик сегодня выполняет сравнение и объединение с CF. Отдельная ИБ агента потребовала бы ещё одного рабочего контура. Если в подключённой ИБ есть посторонние незавершённые изменения, агент показывает их и передаёт решение человеку.

Подключённая ИБ — та же исходная ИБ, из которой refresh получает `master`. Она не содержит уникальных данных, поэтому реструктуризация с удалением данных и данные дымового сценария допустимы, а монопольный доступ отдельно не проверяется. Пользователь не выполняет одновременно два переноса из разных веток или перенос в одной ветке и обновление из хранилища в другой. Workflow эту одновременность не контролирует.

Область первой реализации — ветки основной конфигурации и результат CF. Для одного процесса помещения предусмотрены две команды ветки. Ниже приведены их рабочие имена.

- `/itl-repository-commit-review` показывает человеку сравнение с возможностью удаления объектов и ждёт решения в чате перед объединением. После одобрения агент сам доводит перенос до конца.
- `/itl-repository-commit-auto` поручает агенту оценить то же сравнение и выполнить весь перенос. На штатном пути дополнительного подтверждения нет.

Просьба «помести изменения в хранилище» выбирает просмотр человеком. Явная просьба выполнить перенос самостоятельно выбирает автоматическую команду.

Человек и агент оценивают один и тот же состав переноса до объединения. При ручном просмотре человек может изучить добавления, изменения и удаления вплоть до свойств объектов и строк кода, принять показанное целиком или вернуть задачу в ветку. Повторная сборка CF или изменение состава переноса требует нового просмотра. В автоматическом режиме решение по тому же сравнению принимает агент. После конфликтов в ветке в обоих режимах он объясняет, как в результате учтены доработки ветки и хранилища.

После принятия объединения агент обновляет конфигурацию базы данных и проверяет результат одним коротким пользовательским сценарием по сути задачи. Так можно обнаружить ошибку именно переноса и использовать уже полученные результаты проверок ветки. По умолчанию полный набор тестов ветки повторно не запускается. Успешный сценарий позволяет продолжить помещение по исходному поручению.

## Захват и возобновление

Перед обновлением ветки нужны все захваты, предусмотренные для переноса. При частичном захвате агент сохраняет полученные захваты. Если нужные объекты заняты, он перечисляет каждый такой объект и пользователя хранилища, который его захватил, и ждёт сообщения человека об освобождении. Это правило действует в обоих режимах. После сообщения агент повторяет штатный захват и продолжает по его результату.

При штатном успешном завершении повторного захвата Конфигуратор может перечислить только вновь захваченные объекты. Запрошенный объект без отдельной строки и без сообщения о конфликте считается уже захваченным текущим пользователем. Отсутствие строки в оборванном журнале оставляет исход неизвестным.

После обновления ветки и разрешения конфликтов агент повторно сверяет требуемые захваты с итогом ветки. Дополнительные объекты захватывает до показа сравнения. При занятом объекте действует тот же порядок ожидания. В помещение входят только изменения задачи. Захват, принадлежавший тому же пользователю до начала переноса, сохраняется, если соответствующий объект выпал из задачи. Помещение отпускает захваты помещённых объектов и не меняет захваты объектов вне состава.

## Решения по результатам просмотра и проверки

Если подготовленное сравнение скрывает существенную деталь, человек может изучить её в штатном сравнении Конфигуратора и ответить в чате. В автоматическом режиме агент передаёт человеку конкретный объект, если сам не может установить суть изменения. Аналогично при конфликте агент самостоятельно совмещает требования обеих сторон, когда может объяснить и проверить результат. Выбор между несовместимыми требованиями остаётся за человеком.

Если дымовой сценарий упал после обновления подключённой ИБ, агент сохраняет захваты и результат проверки, возвращает доработку в ветку и оставляет подключённую ИБ без автоматического отката. Повторный просмотр охватывает весь итог относительно хранилища, включая уже применённую часть задачи. Если безопасно проверить нужное поведение на доступных данных невозможно, агент сообщает, что подтверждено в каждой ИБ, и передаёт человеку решение о помещении.

## Версия хранилища и Mantis

Комментарий к версии имеет вид `номер обращения: заголовок` для задачи из Mantis или кратко описывает задачу вне Mantis. Номер обращения агент берёт из известного ему контекста задачи или из параметров ветки, где он хранится до её сброса; иначе спрашивает человека. Имя ветки источником номера не является. Подтверждённая версия завершает перенос. После неё агент без обновления из хранилища выгружает конфигурацию подключённой ИБ в `master`, чтобы другие ветки получили помещённые изменения быстрым `/itl-refresh-lite`. Затем агент перечисляет в комментарии Mantis закрытые пункты и переводит обращение в «Решено» только при выполнении всех пунктов. Если запись в Mantis прервалась, агент сообщает номер версии, сверяет фактический комментарий и статус и повторяет только оставшееся действие.

При обрыве связи во время помещения агент сначала сверяет историю хранилища и состав изменений. Однозначно найденная версия позволяет продолжить с Mantis. Подтверждённое отсутствие помещения позволяет повторить операцию. При неоднозначности агент показывает найденные версии человеку. Один и тот же комментарий может относиться к нескольким помещениям.
