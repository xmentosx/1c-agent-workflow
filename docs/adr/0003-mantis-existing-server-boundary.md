# Развитие MCP без изменения установленного Mantis

28 сентября 2026 года пользователь исключил изменение Mantis и выбрал ограниченную запись через существующий API вместо обновления сервера как предпосылки записи. Read-only вызов `mc_version` на `https://support.itland.ru/api/soap/mantisconnect.php` вернул 2.28.1; эта версия входит в диапазоны опубликованных ошибок проверки прав на [редактирование комментариев](https://github.com/mantisbt/mantisbt/security/advisories/GHSA-pq86-j2c2-47f6) и [изменение статусов](https://github.com/mantisbt/mantisbt/security/advisories/GHSA-m7ph-9558-mrx3), наличие локальных исправлений не подтверждено. Будущий MCP должен учитывать ограничения и проверять разрешения независимо от успеха HTTP-запроса; это не исправляет сам Mantis и не разрешает обход прав. Пользователь согласовал изменение как собственных, так и чужих комментариев в пределах подтверждённых разрешений и по явной команде на конкретный комментарий.

Отдельно согласована предпосылка будущего ввода записи: предоставить тому же служебному аккаунту минимально необходимые права по проектам для выбранных действий. На момент исследования `GET /api/rest/users/me` и `GET /api/rest/projects` показывают уровень 10 (наблюдатель); существующих прав недостаточно даже для создания обращения, комментария и загрузки файла. Это согласование архитектуры, а не команда изменить права сейчас.

Пользователь принял остаточный риск гонки с другими клиентами Mantis при изменении существующих данных: проверку версии, остановку при обнаруженном конфликте, последовательную запись MCP в одно обращение и проверку результата. Проверка `If-Match` у REST и последующая запись в upstream 2.28.1 разделены; у отдельного SOAP-метода изменения комментария нет `If-Match`, и сравнение снимка перед вызовом также не атомарно. Выбранный контракт обнаруживает проверяемые конфликты, но не обещает абсолютную защиту от перезаписи между проверкой и записью; реализация атомарной гарантии потребовала бы пересмотра запрета менять Mantis.

Конкретная команда пользователя с определённым объектом и изменением достаточна для выполнения после проверок; обязательное повторное подтверждение не вводится. Подготовка черновика сама по себе не разрешает публикацию. Ограничения штатного API, в частности отсутствие подтверждённого способа прикрепить файл к уже существующему комментарию, должны оставаться явными, а не заменяться другим действием без согласованного намерения пользователя.
