# Дополнительные конфигурации и базы

Дополнительный контур — это именованная конфигурация и база, с которой нужно работать в той же ветке разработки. Он подходит для обмена между конфигурациями, отдельной серверной проверки и временного эксперимента без создания новой Git-ветки.

Пользователь не редактирует `project.json`, `.dev.env` или настройки MCP вручную. Достаточно описать задачу агенту. Агент задаёт понятные вопросы, показывает итоговые права на изменение базы и сам сохраняет настройки через безопасную операцию workflow.

Если дополнительные контуры не настроены, основная база, её тесты, CF и MCP работают как раньше.

## Как подключить базу

Начните с запроса, например:

> Подключи дополнительную базу для тестирования обмена.

> Добавь существующую серверную базу для замеров производительности.

> Создай отдельную локальную базу для эксперимента с другой конфигурацией.

Агент последовательно уточнит только недостающую информацию.

### 1. Для чего нужен контур

Нужно коротко описать назначение: «приёмник обмена», «серверный замер», «эксперимент с расширением». По этому описанию агент предложит понятное имя и технический идентификатор. Обычно подтверждения предложенного идентификатора достаточно.

### 2. Кто может изменять базу

Агент предложит один из трёх режимов:

| Вариант | Для чего подходит | Что разрешено |
|---|---|---|
| Локальная база workflow | Обмен, эксперименты, дополнительная конфигурация | Создание базы, загрузка конфигурации и расширений, тесты, выгрузка исходников и CF |
| Внешняя база только для диагностики | Изучение существующей базы | Статус, ROCTUP и Vanessa UI MCP; изменение базы и автоматические тесты запрещены |
| Выделенная внешняя тестовая база | Серверные проверки и нагрузочные эксперименты | Workflow может загружать конфигурацию, обновлять базу и запускать тесты |

Перед выбором внешней тестовой базы агент обязан явно предупредить, что её конфигурация и данные могут изменяться. Рабочую или ценную базу нужно подключать только для диагностики.

### 3. Откуда брать конфигурацию

Можно использовать:

- основную конфигурацию текущей ветки;
- отдельную конфигурацию, уже находящуюся в проекте;
- отдельную конфигурацию, которую предполагается выгружать из подключённой тестовой базы.

Агент сам определит и сохранит путь. Если нужна обратная выгрузка исходников из базы, об этом нужно сказать явно. Основная конфигурация ветки никогда не передаётся дополнительному контуру во владение на запись.

### 4. Какие тесты нужны

Варианты:

- не запускать автоматические тесты;
- запускать основные тесты проекта в дополнительной базе;
- иметь отдельные тесты только для этого контура;
- запускать оба набора.

Для отдельного набора агент предложит каталог вида `tests/auxiliary/<имя-контура>` и при необходимости поможет создать сценарии.

Если настроены основные и отдельные тесты, полный проверенный результат появляется только после последовательного запуска обоих наборов. Запуск одного набора остаётся диагностическим и не выдаётся за полную проверку.

### 5. Нужны ли расширения

Для каждого расширения достаточно сообщить агенту его имя и где в проекте находятся исходники. При обновлении контура workflow сначала полностью загрузит конфигурацию, затем объявленные расширения, после чего выполнит нормализацию базы в режиме предприятия.

### 6. Какие средства диагностики подключить

Можно выбрать:

- ROCTUP для чтения метаданных и данных;
- Vanessa UI MCP для интерактивного исследования интерфейса;
- оба средства;
- ничего.

Vanessa UI MCP не заменяет Vanessa Automation. MCP используется для диагностики и разработки сценариев, а проверочное доказательство создаётся отдельным запуском тестов.

### 7. Как подключается внешняя база

Агент спросит:

- файловая это база или серверная;
- точный путь либо строку `сервер\имя-базы`;
- пользователя;
- установлен ли пароль.

Пароль не нужно отправлять в чат. Если он есть, агент попросит скопировать пароль в буфер обмена и подтвердить готовность. Workflow прочитает его без вывода в командной строке и сохранит только в локальном игнорируемом окружении. Если пароля нет, агент явно сохранит пустое значение.

Перед записью агент покажет краткое резюме: какая база может изменяться, откуда загружаются файлы, какие тесты и расширения подключены и какие MCP появятся.

## Обычная работа

После подключения можно обращаться к агенту естественным языком.

### Состояние

> Покажи дополнительные базы и их состояние.

Для каждого контура агент сообщит режим базы, источник конфигурации, готовность, состояние тестов и подключённые MCP.

### Обновление базы

> Обнови базу «Приёмник обмена» из файлов текущей ветки.

Workflow проверит точный контур, остановит относящиеся к нему MCP и сеансы 1С, загрузит конфигурацию и расширения и выполнит обновление. Обычное обновление основной базы дополнительные контуры не затрагивает.

Повторная команда ничего не загружает, если подключение и исходники не изменились.

### Выгрузка исходников

> Выгрузи изменения конфигурации из экспериментальной базы.

Выгрузка разрешена только контуру, которому при настройке явно дали право записи в отдельный каталог исходников. Она выполняется через staging и заменяет каталог только после проверки целостности выгрузки.

### Запуск тестов

> Запусти основные тесты в базе обмена.

> Запусти только тесты базы обмена.

> Полностью проверь базу обмена всеми настроенными тестами.

Основной набор фактически выполняется в выбранной дополнительной базе. Отдельный набор хранится и запускается независимо. Отчёты разных контуров и наборов не перезаписывают отчёты основной базы.

### Обмен между несколькими базами

Сообщите агенту, какие роли сценария должны открываться в каких базах:

> В сценарии обмена клиент Source должен работать в основной базе, а Receiver — в базе exchange.

Агент настроит именованные TestClient-профили schema 2. Каждый профиль содержит явный контур, поэтому скрытого переключателя «активная база» нет. Один сценарий может одновременно открыть клиентов в основной и дополнительных базах с учётом общего лимита сеансов 1С.

### ROCTUP и Vanessa UI MCP

> Исследуй данные через ROCTUP в базе обмена.

> Открой форму документа через Vanessa UI в серверной тестовой базе.

У каждого контура собственные MCP и runtime. Запуск или остановка дополнительного MCP не перенаправляет основные `itl-roctup-data` и `itl-vanessa-ui` на другую базу.

### Создание CF

> Сделай проверенный CF из базы обмена.

CF и его манифест сохраняются отдельно от результата основной базы. Проверенный CF требует свежего полного прогона всех наборов, назначенных контуру. Агент не должен автоматически обходить это требование.

Если нужен диагностический CF без полного доказательства, пользователь должен попросить об этом явно. В манифесте будет записано, что использовано разрешение на непроверенный результат.

### Пересоздание локальной базы

> Пересоздай экспериментальную базу.

Операция доступна только локальной базе workflow. Старая база не удаляется, а перемещается в локальный архив; затем по запросу обновления создаётся новая.

## Изменение настроек

Настройки также меняются через агента:

> Добавь к exchange отдельный набор тестов.

> Подключи к server-perf ROCTUP, но не Vanessa UI.

> Замени пароль подключения к серверной базе.

Агент сначала покажет текущие настройки, спросит только изменяемые решения и ещё раз проговорит новые права на изменение базы. Для неизменившегося пароля используется сохранённое локальное значение; новый пароль снова передаётся через буфер обмена.

## Где находятся результаты

Пользователю обычно не нужно работать с каталогами напрямую, но для диагностики:

- отчёты Vanessa: `build/test-results/vanessa/auxiliary/<контур>/<набор>/`;
- CF и манифест: `build/result/auxiliary/<контур>/`;
- архивы пересозданных локальных баз: `.agent-1c/auxiliary-archives/`;
- runtime-состояние и подключения остаются игнорируемыми Git.

## Типичные ограничения

- Идентификатор контура уникален в проекте.
- Один каталог исходников может иметь только одного владельца на выгрузку.
- Основной `src/cf` всегда доступен дополнительным базам только для загрузки.
- Основной и отдельный наборы тестов должны находиться в непересекающихся каталогах.
- Диагностическая внешняя база не обновляется и не используется для автоматических тестов.
- Перед изменением базы workflow останавливает только принадлежащие ему процессы и сеансы точной целевой базы.
- Операции основной базы не обновляют дополнительные базы неявно.

Если агенту не хватает ответа для безопасного выбора режима, он должен остановить настройку и уточнить решение, а не угадывать право на изменение базы.
