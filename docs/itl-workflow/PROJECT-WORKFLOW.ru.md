# Работа с проектом 1C Agent Workflow

Это главное руководство для повседневной работы. Если проект ещё не подготовлен, начните с [инициализации](../../AGENT-INSTALL.md): она связывает новую папку проекта с исходной базой 1С и создаёт начальное состояние `master`. Затем прочитайте разделы «За пять минут» и «Модель проекта». Как ставить задачи агенту, описано в [руководстве по разработке изменения](FEATURE-DEVELOPMENT.ru.md); режимы и `.dev.env` — отдельные справочники.

## За пять минут

Сначала workflow инициализирует проект из исходной базы. После этого ветка конфигурации используется многократно: новая доработка не требует новой ветки.

```text
новая папка проекта + исходная база 1С
  │ инициализация проекта
  ▼
master: начальная выгрузка конфигурации и настройки проекта
  │ создать рабочую ветку конфигурации
  │ или отдельную ветку конкретного расширения
  ▼
itldev/<имя-ветки> + собственная копия базы
  │
  ┌────────────────────────────────────────────────────────────────┐
  │ доработка → /itl-check → /itl-result                           │
  │      → загрузка CF/CFE в исходную базу                         │
  │      → /itl-refresh: исходная база → master → текущая ветка    │
  └──────────────────── следующая доработка в той же ветке ◄───────┘
```

1. Инициализируйте новую папку проекта, указав исходную базу 1С.
2. В `master` создайте рабочую ветку конфигурации. Для изменяемого расширения создайте отдельную ветку расширения.
3. Откройте напечатанный путь к worktree и поставьте агенту первую доработку обычным текстом.
4. После реализации получите `fresh passed` от `/itl-check`, затем выполните `/itl-result` и загрузите полученный `CF` или `CFE` в исходную базу.
5. Выполните `/itl-refresh`, чтобы перенести принятое состояние исходной базы через `master` обратно в рабочую ветку. Следующую доработку основной конфигурации выполняйте в этой же ветке.

Команда `/itl` — навигатор: она определяет текущий контекст, показывает доступные команды и рекомендуемый следующий шаг. Конкретный способ запуска зависит от активного AI-клиента; не переносите синтаксис одного клиента в другой.

## Инициализация проекта

Создайте новую пустую папку с коротким путём, откройте её в поддерживаемом AI-клиенте и попросите:

```text
Инициализируй проект 1С по инструкции:
https://raw.githubusercontent.com/xmentosx/1c-agent-workflow/master/AGENT-INSTALL.md
```

Агент запустит мастер настройки. В нём нужно выбрать платформу 1С и AI-клиент, указать тип и путь исходной базы, а также ответить на вопросы о хранилище, веб-публикации и локальных инструментах. Отдельного вопроса о модели нет: агент передаёт `-AgentModel` только если точно знает slug `opus5`, `sonnet5`, `fable5` или `gpt56`; иначе остаётся пустой профиль `auto`, который позже меняется через `/rulesmodel`. Модель никогда не выводится из названия AI-клиента. Workflow выгрузит исходную конфигурацию в Git, создаст начальный коммит `master` и не будет изменять исходную базу при последующей разработке.

## Модель проекта

- `master` хранит актуальную выгрузку исходной конфигурации в Git. Разработка прикладного кода и метаданных непосредственно в `master` запрещена.
- `itldev/<name>` — изолированная ветка разработки со своей worktree-папкой и копией информационной базы. Ветка основной конфигурации не привязана к одной задаче и может последовательно содержать много доработок.
- Агент применяет изменения только к копии базы текущей `itldev/*` ветки. Исходная база изменяется разработчиком вручную после получения `CF` или `CFE`.

Основная папка проекта остается на `master`. После создания ветки откройте путь к worktree, который сообщил workflow, отдельным окном AI-клиента или IDE.

## После инициализации

В Kilo итог инициализации показывает состояние Browser Automation. Этот параметр добавляет Playwright MCP к контексту модели, поэтому его следует включать только на время задач, которым нужен веб-браузер. Workflow сообщает состояние, но никогда не меняет настройку разработчика.

В `master` должны быть закоммичены настройки проекта и исходники конфигурации. Обычно используются:

| Путь | Назначение | Состояние в Git |
|---|---|---|
| `src/cf` | Файлы основной конфигурации | отслеживается |
| `src/cfe/<Имя>` | Файлы расширений | отслеживается |
| `tests/features` | Vanessa-сценарии | отслеживается |
| `.agent-1c/project.json` | Несекретные настройки проекта | отслеживается |
| `.agent-1c/dependency-lock.json` | Зафиксированные версии и источники зависимостей | отслеживается |
| `.dev.env` | Локальные параметры и секреты | игнорируется |
| `.agent-1c/infobases/dev-branches` | Копии баз веток | игнорируется |
| `.agent-1c/branch-seed` | Один актуальный seed исходной базы и baseline ошибок | игнорируется |
| `.agent-1c/dev-branches` | Локальное состояние веток | игнорируется |
| `build/result` | Выгруженные `CF`/`CFE` и манифесты | игнорируется |
| `build/test-results/vanessa` | Отчеты Vanessa Automation | игнорируется |

Для `src/cf/**` и `src/cfe/**` workflow добавляет в `.gitattributes` правила `-text`. Это не перевод в CRLF или LF: Git перестаёт преобразовывать переносы строк и хранит ровно те байты, которые выгрузила платформа 1С. Остальные файлы проекта под это правило не попадают.

Полный перечень локальных параметров приведен в [справочнике `.dev.env`](DEV-ENV-REFERENCE.ru.md).

## Создание ветки разработки

Из `master` попросите агента создать ветку конфигурации или расширения. В клиентах со slash-командами доступны:

```text
/itl-new-config-branch <name>
/itl-new-extension-branch <name>
```

Workflow проверит чистоту Git, создаст `itldev/<name>` в соседней worktree-папке, восстановит отдельную копию базы из последнего seed и сообщит новый путь. Хранится только один актуальный seed на исходную базу; старый `1Cv8Log` в ветку не копируется, вместо него устанавливается готовый baseline сигнатур ошибок. Для просмотра активных веток и путей используйте:

```text
/itl-status
```

### Ветка основной конфигурации

В ветке основной конфигурации агент изменяет файлы под настроенным `exportPath` — обычно `src/cf`. Эта ветка является рабочим контуром конфигурации, а не веткой одной задачи: после выдачи результата в ней можно начинать следующую доработку. Каждая доработка завершается собственными `/itl-check` и `/itl-result`.

### Ветка расширения

При создании ветки расширения агент заранее спросит, создать пустое расширение или загрузить существующий `CFE`, а также имя расширения и путь к CFE при необходимости. Workflow создаст worktree и копию базы, затем сам инициализирует расширение в новой ветке. Если параметры пока неизвестны, ветка сохранит статус ожидания и агент соберёт их при первом входе; запускать PowerShell вручную не нужно.

Одна extension-ветка обслуживает ровно одно изменяемое расширение. Для другого `CFE` создайте отдельную ветку.

## Работа с изменением

Поставьте задачу обычным текстом. По установленному пакету правил `ai_rules_1c` агент независимо определит путь выполнения (`quick-fix` или `full-cycle`) и способ планирования (`direct` или OpenSpec). По умолчанию используется `direct`; OpenSpec нужен для формального исследования и согласования, а не для каждого изменения повышенного риска. Подробный процесс описан в [руководстве по разработке изменения](FEATURE-DEVELOPMENT.ru.md).

После изменений стандартная проверка выполняется одной командой:

```text
/itl-check
```

Она обновляет копию базы измененными файлами, применяет обработчики обновления в пользовательском режиме и запускает разрешенные компоненты проверки. Отдельное обновление базы перед `/itl-check` не требуется.

Если нужно только загрузить файлы без тестового прогона, попросите агента обновить копию базы без тестов. Если предыдущая реализация могла пропустить тест или проверка упала и требуется цикл исправления, используйте `/itl-verify-fix`.

## Обновление свежим master

Когда исходная база или `master` изменились, из worktree текущей ветки выполните:

```text
/itl-refresh
```

Workflow синхронизирует исходную конфигурацию, обновит `master`, обеспечит совместимый latest-only seed, сольет точный полученный commit `master` в текущую ветку и обновит копию базы. При Git-конфликте операция останавливается: конфликт нужно разрешить явно, после чего повторить штатный цикл.

Для нескольких параллельных веток сначала один раз из основной worktree выполните:

```text
/itl-sync-master
```

Эта команда обновляет `master` и всегда полностью пересоздаёт seed, включая данные и baseline. Затем в каждой ветке можно параллельно выполнить:

```text
/itl-refresh-lite
```

Облегчённый refresh не обращается к исходной базе и seed: он берёт текущий точный SHA `master`, сливает его и обновляет только базу своей ветки.

## Получение результата

Для передачи текущего состояния в исходную базу выполните:

```text
/itl-result
```

Workflow выгрузит `CF` для ветки основной конфигурации или `CFE` для ветки расширения в `build/result`. В ответе будут указаны полные пути к созданному файлу и соседнему манифесту, а также объекты для переноса в хранилище конфигурации: полностью либо частично с перечнем изменённых частей. Список строится от общей базы текущей ветки и локального `master` до фактического рабочего дерева, поэтому включает committed, staged, unstaged и untracked изменения текущей задачи. `ConfigDumpInfo.xml` и служебное изменение состава корневого `Configuration.xml` в список не входят; несопоставленные пути выводятся для ручной проверки. Предварительный коммит не требуется: `/itl-result` принимает только то содержимое, для которого сохранён `fresh passed` от `/itl-check`, и проверяет, что файлы не изменились во время выгрузки. Манифест содержит контрольную сумму SHA-256, исходные коммиты, статус проверки и пути к отчётам. Загрузка результата в исходную базу выполняется вручную.

По умолчанию `VERIFICATION_POLICY=warn`: при отсутствии свежей успешной проверки потребуется явное подтверждение непроверенного результата. В режиме `block` выгрузка запрещена до fresh passed `/itl-check`.

## Обслуживание workflow

Из `master` или активной `itldev/*`:

- `/itl-update-workflow` всегда обновляет принадлежащие workflow файлы и правила в основном worktree и затем создаёт один локальный коммит только из разрешённых updater-путей в `master`; при вызове из `itldev/*` текущая ветка не переключается и не изменяется;
- `/itl-sync-master` синхронизирует исходную базу с `master` и принудительно пересоздаёт latest-only seed;
- `/itl-switch-client <client>` переключает активный AI-клиент;
- `/itl-status` показывает установленную версию и источник workflow, состояние инструментов и активные worktree.

Успешное обновление не оставляет изменённых отслеживаемых файлов в `master` и не выполняет push. Если изменений нет, пустой коммит не создаётся. Обновление не переносится автоматически в существующие `itldev/*` ветки: после вызова из рабочей ветки оставайтесь в ней и выполните `/itl-refresh-lite` для переноса текущего `master` либо обычный полный `/itl-refresh`.

При первом `/itl-sync-master` после появления byte-preserving контракта полный выгруз и `.gitattributes` фиксируются одним коммитом. Первый последующий refresh существующей ветки выполняет одноразовый переходный merge и пересобирает индекс её `src/cf`/`src/cfe`; обычные последующие merge снова используют строгие правила.

## Правила безопасности

- Не коммитьте `.dev.env`, пароли, локальные базы, скачанные инструменты, логи и `build/`.
- Не загружайте файлы ветки разработки напрямую в исходную базу через внутренние скрипты workflow.
- Перед операциями жизненного цикла сохраняйте чистыми отслеживаемые Git-файлы. Исключение — `/itl-check` и `/itl-result`: они работают с одним и тем же проверенным содержимым без обязательного коммита.
- Не завершайте процессы 1С, принадлежащие другой worktree.
- ROCTUP MCP и Vanessa UI MCP запускаются по требованию и не заменяют `/itl-check`.
- При ошибке 1С или Git сохраните диагностику и путь к логу; не продолжайте процесс вручную в обход workflow.
