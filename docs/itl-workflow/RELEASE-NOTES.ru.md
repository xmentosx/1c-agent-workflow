# Что нового в релизах ITL workflow

Новые релизы канала `master` добавляются сверху.

## Релиз master от 25.11.2026

Релиз 25.11.2026 (master `5cf445ec`, PR #129) заменяет предыдущий релиз master от 09.09.2026 (`69c0863b`, PR #126). За это время в develop вошло около 980 изменений; ниже — то, что заметно пользователю установленного проекта, включая форки, которые поставляются вместе с workflow.

### Как обновиться

Первый переход с прошлого master (правила r33) делается один раз из чистой копии исходников workflow, а не старым установленным помощником. Новый помощник сначала снимает снимок всех управляемых файлов и только потом их заменяет, поэтому прерванное обновление можно продолжить или откатить.

**Не запускайте `/itl-update-workflow` в проекте на прошлом master.** Старый помощник скопирует новый пакет без снимка, после чего новый помощник остановится с `WORKFLOW_UPDATE_POST_COPY_RECEIPT_MISSING` и оставит `master` с незакоммиченными файлами. Если это уже произошло, ничего не коммитьте и не повторяйте команду: восстановление через `-Recovery legacy-status` описано в справке `workflow-update-recovery.md`, раздел «Legacy copy without receipt or backup».

1. Получите чистую копию репозитория workflow на ветке `master`.
2. Из `master`-worktree проекта запустите обновление через исходники:

   ```powershell
   powershell -ExecutionPolicy Bypass -File <source>\scripts\update-installed-workflow.ps1 -ProjectRoot <project> -SourceRoot <source>
   ```

3. Дальнейшие обновления — обычной командой `/itl-update-workflow` из `master`.

Что изменится в проекте автоматически при первом обновлении:

- Обновление спросит проект из каталога продуктов и проектов; инициализация и обновление теперь требуют явно выбранный опубликованный проект.
- `DEPENDENCY_MODE` переходит со значений `fresh`/`locked` на `workflow`: версии всех зависимостей берутся из поставки workflow. Свой старый пин потребует явного решения перед заменой.
- `UI_TESTING` один раз переводится с `manual` на `essential`: существенные UI-проверки выполняются по умолчанию.
- Настройки моделей одного клиента переносятся в `.agent-1c/project.json` (`aiRules.modelTiersByClient.<client>`).
- Обновление workflow распространяется на все зарегистрированные worktree, но не сливает бизнес-конфигурацию и не запускает тесты 1С.

Если обновление прервалось, повторите ту же команду. Не удаляйте `index.lock` и не правьте `status.json` вручную; порядок восстановления описан в справке `workflow-update-recovery.md`.

### Главное

- **Несколько клиентов в одном проекте.** Вместо одного активного клиента можно подключить сразу несколько; добавлены ZCode и MiMo Code (всего 12 клиентов).
- **Окна 1С агента скрыты.** TestClient, TestManager и ROCTUP больше не отнимают фокус; клавиатуру и мышь агент берёт только после обратного отсчёта с согласия пользователя.
- **Проверка текущего изменения.** По умолчанию `ITL_VERIFICATION_MODEL=change`: проверяется то, что поменялось, а приёмка задачи целиком идёт отдельно.
- **Быстрый откат загрузки.** Неудачная загрузка в веточную ИБ откатывается к конфигурации БД (`/RollbackCfg`, секунды) вместо полной выгрузки DT перед каждой загрузкой.
- **Память проекта (Cognee).** Агент вспоминает решения и ловушки перед правкой 1С и сохраняет новые знания в нужную область: ветка, проект, продукт или организация.
- **Каталог продуктов и проектов.** При инициализации проект выбирается из каталога; семейство PM4/PM5 и источники знаний подтягиваются из записи.
- **Новые команды** `/itl-delete-branch` и `/itl-clean`; автоматическая очистка старых артефактов ITL после успешных операций.
- **Работа без прав администратора** на Windows 10, Windows 11 и Windows Server 2019+, включая терминальные серверы.

### Клиенты, окна 1С и MCP

**Клиенты**

- Мастер инициализации позволяет выбрать несколько клиентов; `/itl-switch-client` теперь подключает и отключает клиента (`attach`/`detach`), а не заменяет единственного. Клиент, установленный позже, автоматически получает включённую память проекта.
- Добавлены ZCode и MiMo Code. Для Claude Code корневые правила подключаются импортами, а встроенная автопамять Claude отключается, пока подключена память проекта.
- Пользовательские настройки MCP и OpenCode сохраняются при обновлении; собственные записи ITL больше не выдаются за конфликт с пользовательским каталогом.
- Появился сайдкар для ChatGPT через RDC-хост ([CHATGPT.ru.md](CHATGPT.ru.md)).

**Окна 1С и фокус**

- `ONEC_WINDOW_MODE=hidden` (по умолчанию): TestClient, TestManager, главное окно ROCTUP и служебные окна Enterprise запускаются скрытыми. Агент может показать или скрыть окна по запросу.
- Когда агенту нужен ввод ОС (выпадающий список, клик), появляется панель с обратным отсчётом (`ONEC_UI_LEASE_COUNTDOWN_SECONDS=10`), её можно поставить на паузу. Панель запоминает выбранный угол экрана, а журнал фиксирует шаг и файл фичи, занявшие ввод.
- Консольные команды Vanessa и MCP-процессов запускаются скрытыми; есть предупреждение, если блок кода в фиче открывает видимую консоль через `WScript.Shell.Exec`.

**MCP по запросу (ROCTUP и Vanessa UI)**

- Фасад `itl-ondemand-mcp` 0.4.38 публикует компактные `resolve_tool`/`call_tool`; бэкенд стартует при первом вызове и останавливается по простою. Настройки `VANESSA_MCP_AUTO_START` и `ROCTUP_MCP_AUTO_START` удалены.
- Новый relay 1.0.0: записи MCP в конфигурации клиента больше не переписываются при каждом обновлении фасада (раньше путь менялся с каждой версией).
- Таймаут или обрыв вызова сообщает `callOutcome: unknown`, последний прогресс и следующий шаг; изменяющий вызов никогда не повторяется автоматически. Потерянный бэкенд восстанавливается без переподключения MCP.
- ROCTUP: `ROCTUP_DATA_CHANGES=auto` — в веточной ИБ `Записать` и привилегированный режим идут без диалога, прочие опасные слова отклоняются с подсказкой выполнить код через шаг Vanessa; `confirm` возвращает диалог на каждый вызов.
- Vanessa: ошибка шага, отключённый TestClient и недоказанный результат возвращаются как ошибки инструмента с понятным кодом, а не как успех.

### Проверка и тесты

- **Модель «изменение».** План проверки строится по текущему изменению из уже сохранённых проверок; одноразовое доказательство допустимо, обязательный новый регрессионный тест — нет. Проверяются и затронутые макеты. Прежняя накопительная оценка остаётся доступной настройкой.
- **Разработка и подготовка к рабочей базе разделены.** В разработке выполняются `/CheckModules` и проверка применимости расширения; полный `CheckConfig` — только при явной подготовке к рабочей ИБ (`-ResultPurpose production`).
- **Откат загрузки через `/RollbackCfg`** вместо выгрузки и восстановления DT: на пилоте откат занимал около 4 с.
- **Бюджет Vanessa по истории.** Если `VANESSA_TEST_TIMEOUT_SECONDS` не задан, бюджет прогона считается по записанной длительности выбранных фич (от 1800 до 7200 с). Прогон, в котором TestManager не запустил TestClient, останавливается через 300 с, а не висит до конца бюджета.
- **Перезапускаемые сценарии Vanessa** сначала убирают свои остатки; после падения UI независимые наборы продолжают работу. UI-сбой при заблокированном сеансе Windows направляется на удалённый исполнитель.
- **YAxUnit:** актуальный пройденный результат переиспользуется без повторного запуска; тестовые данные не накапливаются; тесты проекта можно устанавливать в безопасном режиме (SafeMode).
- **Журнал регистрации:** агент сам решает по ошибкам по их происхождению и связи с веткой и может подтвердить намеренно вызванные ошибки.
- **Ревью большой ветки.** При большом объёме изменений BSL помощник предлагает область ревью: незакоммиченное, с выбранного коммита или вся ветка; записанный проектом проход гейта принимается как доказательство.
- **Ремонт проверки (`/itl-verify-fix`)** продолжает текущую сессию по явному разрешению; попытки, сорванные дефектом самого workflow, не списываются.
- **Лицензия и подпись:** команды Designer и запуск Vanessa, отклонённые 1С из-за лицензии или проверки подписи конфигурации, повторяются автоматически.

### Ветки, жизненный цикл и обслуживание

- **`/itl-delete-branch`** (из `master`) полностью удаляет ветку `itldev/<имя>`: worktree, веточную ИБ, запись в списке баз и архивы. Спрашивает подтверждение один раз; при обрыве достаточно повторить команду. Удалённые ветки и общий кэш не трогает.
- **`/itl-clean`** показывает план очистки старых артефактов ITL (число и объём) и удаляет только неиспользуемые. Та же очистка идёт автоматически после успешных операций (лимиты — в разделе настроек). Остатки тестов и Vanessa больше не копятся во временной папке.
- **Вспомогательные контуры:** новая операция `remove-auxiliary-contour` снимает регистрацию контура с его настройками; `/itl-reset-branch` при сбросе убирает контуры, которых нет в `master`, и пересоздаёт ветку.
- **Меньше остановок жизненного цикла.** Перед созданием ветки агент сам коммитит свои изменения, а refresh продолжается при независимых изменениях на диске. Папка `/handoffs/` исключена из Git.
- **Очередь к базе вместо сбоя.** Состояние `waiting-for-base` означает нормальную очередь к одной базе; работа с другими базами и файловые этапы при этом идут дальше. Прерванные загрузки, выгрузки и операции с серверными базами восстанавливаются по журналам.
- **Хранилище конфигурации:** для локальных правок и проверки в готовой ветке захват объектов не требуется; частичный отказ захвата отчитывается по каждому объекту; новые объекты верхнего уровня захватывают корень конфигурации.
- **Удобства:** веточные ИБ называются по имени ветки; в автоматических клиентах и при обновлении файловой базы регламентные задания отключены. Инициализация из файлов и полный refresh ветки стали быстрее.
- **Известные дефекты workflow** собраны в реестр с обходными путями: при подозрении на дефект агент применяет обход, пишет отчёт и продолжает задачу.
- **OpenSpec** устанавливается локально в проект (CLI 1.13.1); одобренный `apply` продолжается после локальных блокеров без повторного согласования.

### Память и реестр продуктов и проектов

**Память проекта (`scoped-cognee-memory-v1`)** работает через одно общее подключение к сервису Cognee и включается по умолчанию, когда сервис доступен. Глобальная `remember`/`recall` из `1c-templates-mcp` по-прежнему для знаний, полезных вне проекта.

- Перед первой связанной правкой 1С агент вызывает recall один раз на тему — по инструменту, действию или симптому.
- Знание сохраняется в область по сроку жизни и аудитории: ветка, проект, продуктовая линия, организация. Ожидания отделяются от проверенных фактов; исправление из памяти перепроверяется в текущей ветке.
- Обходные пути по открытым дефектам ITL хранятся в памяти организации.
- Статус памяти ограничен 3000 токенами; неполное чтение и отказ доступа к эмбеддингам сообщаются явно, а недописанная запись доводится по тому же идентификатору.

**Каталог продуктов и проектов** хранит стабильные идентификаторы продуктов, проектов и их источников знаний (код, граф, документация, СППР, Mantis). При инициализации и обновлении проект выбирается из каталога, а PM4/PM5 и настройки MCP выводятся из записи без лишних вопросов. Список проектов: `vibecoding1c-mcp-status -CatalogAction list`. Навык `product-docs` больше не привязан только к PM5.

Правила переехали на апстрим comol/ai_rules_1c `2f640143` (20.10.2026) — 93 апстрим-коммита после прежнего `410951e7`. Корневой `AGENTS.md` теперь равен точному апстриму плюс приложение ITL, а не заменён целиком.

**Из апстрима**

- Новый навык `1c-change-package` (пакеты для ручной реализации и ревью); необязательные навыки тестов, DOCX и транскрибации.
- QA MCP стал основным маршрутом UI-проверки, `UI_TESTING=essential` по умолчанию; UI-тесты отделены от профилей SDLC.
- Правила форм и данных формы, стандартных команд, параметров виртуальных таблиц; многоконтурный поиск по исходникам; контракт частичной загрузки/выгрузки.
- Сокращён постоянный контекст: память и детали операций загружаются по запросу; один стабильный канал образов MCP вместо beta.
- Исправлено имя инструмента проверки запросов `vcvalidatequery`; ошибки и пустые результаты запросов 1c-data-mcp стали явными.

**Изменения ITL в форке**

- Соразмерная приёмка результата: проверяется исход задачи и затронутые макеты; материальные решения планирования и исполняемые критерии приёмки обозначаются явно (r48).
- Завершение задачи и повторяющиеся препятствия не зависят от модели (r51).
- Контракт ревью изменений работает и без субагента-ревьюера; область ревью берётся из помощника ITL; мелкие замечания исправляются в строках самой задачи (r52–r54).
- Память проекта: выбор области по сроку жизни, recall перед правкой, многоразовые заметки вместо журнала (r49–r64).
- OpenSpec `apply` продолжается после локальных блокеров (r58); quick-fix закрывается своим гейтом, а Claude Code импортирует корневые правила (r60–r61).
- Правило вычисления фильтров СКД в движке СКД для отчётов, динамических списков и рабочих мест (r63).

### Общие MCP-сервисы на хосте

Эти изменения разворачиваются на общем хосте vibecoding1c и становятся доступны проектам без действий пользователя.

- **Mantis:** поиск с ограничением (10 карточек по умолчанию), инкрементальный индекс, поиск по содержимому вложений и защищённая запись.
- **BookStack (документация продукта):** полнотекстовый и семантический индекс всех разделов (Qwen3-Embedding-8B); ссылки на страницы проверяются вживую; запись страниц — с личными учётными данными Windows и после просмотра.
- **СППР MCP:** поиск по техническим проектам, идеям, процессам и решениям СППР через OData; начальный охват — «Кейс проект PM5».
- **Cognee:** общий сервис памяти с мониторингом здоровья, кэшем векторов запросов и постоянным соединением с эмбеддингами.
- **Code, Graph, Docs, Templates, CodeChecker:** один стабильный канал образов вместо beta, обновления с сохранением индексов; длинная первичная индексация продолжается после перезапуска. CodeChecker возвращает полные проверенные ответы в пределах срока; в Code доставлен XSD-пакет прав ролей.
- **Обслуживание:** ночная индексация перезапускает AI Gateway, старые образы, тома и контейнеры удаляются по правилам хранения, зависший Docker Engine восстанавливается автоматически.

### Что ещё не готово

- **Перенос изменений в хранилище конфигурации** (с просмотром и автоматический) в этом релизе только описан и специфицирован; реализация ещё не начата.
- По части изменений ещё открыты задачи приёмки (скрытие окон 1С, реестр проектов, память Cognee, СППР MCP, откат через `/RollbackCfg`): основное поведение в релизе, дополнительные сценарии и итоговая приёмка продолжаются в develop.
