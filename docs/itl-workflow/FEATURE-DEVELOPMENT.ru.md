# Разработка изменения

Документ описывает, как разработчику поставить задачу агенту и контролировать результат внутри созданной `itldev/*` ветки.

## Процесс целиком

```text
ось выполнения: локальная правка без promotion triggers ─► quick-fix
                всё остальное или сомнение ──────────────► full-cycle

ось планирования: по умолчанию ──────────────────────────► direct
                  нужен OpenSpec по запросу
                  или для формального согласования ──────► OpenSpec

любой путь ─► реализация + YAxUnit для локальных алгоритмов
                         + Vanessa для интеграции/UI
           ─► /itl-check
           ─► fresh passed
           ─► /itl-result
```

За готовность отвечает не название процесса, а фактический результат: реализованное поведение, релевантное покрытие и fresh passed `/itl-check`.

## Перед началом

Откройте worktree нужной ветки и проверьте контекст:

```text
/itl-status
```

Опишите требуемое поведение, ограничения и критерии приемки обычным текстом. Если задача относится к конкретному тикету или продуктовой документации, укажите ссылку или идентификатор.

## Выбор процесса

Агент классифицирует изменение по установленному пакету правил `ai_rules_1c` по двум независимым осям: выбирает путь выполнения `quick-fix` или `full-cycle` и способ планирования `direct` или OpenSpec. Допустимы все четыре сочетания. По умолчанию используется `direct`. Условия повышения сложности меняют только путь выполнения и глубину проверок, но сами по себе не требуют OpenSpec.

### Quick-fix

Подходит для одного понятного локального изменения в одном модуле либо новой полностью неподключенной добавки метаданных, разрешённой политикой проверки `ai_rules_1c`. Лимит BSL-строк задает `QUICKFIX_MAX_LINES`, по умолчанию `40`; любое условие повышения сложности из правил `ai_rules_1c` переводит изменение в `full-cycle`.

Обычный запрос:

```text
Исправь <наблюдаемая проблема>. Ожидаемое поведение: <результат>.
```

Для quick-fix по умолчанию используется `direct`, но явный запрос на OpenSpec или полезная формализация требований не превращают его в `full-cycle`. Сам факт исправления наблюдаемого поведения также не меняет planning mode, если локальная BSL-правка сохраняет публичные контракты и не затрагивает условия повышения сложности. Quick-fix не отменяет тестирование: локальный алгоритмический дефект получает YAxUnit-регрессию, а интеграционный или UI-дефект — целевой сценарий Vanessa.

### Direct full-cycle

Используется по умолчанию для изменений, которые не проходят критерии quick-fix, но имеют понятные границы, решение и критерии приемки. Сюда относятся, например, ясная правка существующей формы, связанных метаданных, транзакционного участка или публичного контракта. Агент составляет обычный план, выполняет применимые проверки `full-cycle` из правил `ai_rules_1c` и не создает `proposal.md`, `design.md`, `tasks.md` или изменения спецификаций OpenSpec.

Пример классификации:

```text
executionPath=full-cycle
planningMode=direct
Reason: existing form metadata; scope and solution are clear.
```

### OpenSpec

Используется как planning mode вместе с `quick-fix` или `full-cycle`, когда пользователь явно запросил OpenSpec либо формальное исследование и согласование требований, архитектуры, критериев приемки или этапов реализации действительно добавляет ценность. Количество файлов, связанных объектов метаданных или высокий риск проверки сами по себе не принуждают к OpenSpec и не определяют planning mode.

В Codex разработчик может явно запускать этапы командами `$opsx-explore`, `$opsx-propose`, `$opsx-apply` и `$opsx-archive`. Эти aliases не участвуют в неявном выборе: для него остаются исходные `openspec-*` skills.

OpenSpec доступен в двух режимах. `native` означает, что установленная в проекте версия `ai_rules_1c` добавила для активного AI-клиента готовую команду или навык. `natural` означает, что папка `openspec/` и правила доступны, но отдельной команды или навыка для клиента нет, поэтому разработчик обращается к агенту обычным текстом. Состав документов OpenSpec, предварительные условия и критерий завершения в обоих режимах одинаковы. Узнать текущий режим и точный способ запуска можно через `/itl`.

Для natural-режима используйте точные запросы:

```text
Исследуй задачу в режиме OpenSpec, не создавая proposal и не меняя код
```

```text
Подготовь OpenSpec proposal для <изменение>; создай proposal, design, tasks, test-plan и spec deltas; код не меняй
```

```text
Реализуй согласованный OpenSpec change <change-id> по tasks.md и test-plan.md
```

```text
Заархивируй принятый OpenSpec change <change-id> и синхронизируй specs
```

В режиме `native` команда `/itl` вместо этих запросов показывает команды или навыки, действительно установленные из `ai_rules_1c`. Не переносите синтаксис одного клиента на другой и не считайте `/opsx*` универсальным.

До реализации проверьте proposal, design, спецификации, `tasks.md` и `test-plan.md`. В них должны быть зафиксированы границы изменения, критерии приёмки, `Context Sources` и проверяемые сценарии. Apply в обоих режимах владеет targeted/static проверками реализованных срезов, решающими executable milestones и финальным fresh passed unfiltered `/itl-check`. Не запускайте `/itl-check` повторно сразу после успешного apply, если после него не было новых правок; повтор нужен только после более позднего изменения или stale/failed evidence.

Отсутствие отдельной программы `openspec` не блокирует режим `natural`. Workflow не выполняет скрытый `npm install` и не запускает `openspec update`: эти операции могут создать посторонние файлы поверх зафиксированной версии `ai_rules_1c`.

Если контекст пока неясен в native-клиенте с соответствующей командой:

```text
/opsx-explore
```

Для подготовки согласуемого изменения в таком native-клиенте:

```text
/opsx-propose <описание>
```

После согласования в таком native-клиенте:

```text
/opsx-apply <change-id>
```

Эти `/opsx-*` примеры относятся только к клиентам, где `/itl` показывает именно такой native-синтаксис.

## Реализация и проверяемые срезы

Для большой задачи не нужен полный прогон после каждой строки `tasks.md` или каждого среза. Работу делят на проверяемые срезы:

- локальный алгоритмический срез получает YAxUnit-тесты границ, а интеграционный/UI-срез — focused Vanessa scenario и дешёвые targeted/static проверки;
- подготовительная задача без самостоятельного поведения отмечается как pending verification;
- ближайший следующий проверяемый срез покрывает накопленное изменение;
- промежуточный `/itl-check` запускается только на milestone, где runtime-результат решает, продолжать выбранную реализацию или переделывать её;
- после последней verification-relevant правки выполняется обычный unfiltered `/itl-check` по всему разрешённому набору сценариев change.

Для OpenSpec обычно достаточно 1–2 Vanessa-сценариев на репрезентативные сквозные пути. Множество алгоритмических границ проверяется компактной параметризованной таблицей YAxUnit, а не копиями длинного UI-сценария.

Тип теста выбирается по поведению:

- YAxUnit unit — расчеты, разбор, выбор, группировка, заполнение и локальная прикладная логика; обязательны применимые пустые, минимальные, below/at/above boundary и опасные негативные случаи;
- integration — документы, регистры, объекты и обмены;
- UI — формы, команды и видимое пользователю состояние.

При оптимизации алгоритма агент сначала фиксирует его текущий функциональный контракт, а затем доказывает эквивалентность результата, корректное инвалидирование кэша или промежуточного состояния, изоляцию независимых расчётов и восстановление после ошибки. Только после этих проверок добавляется один небольшой устойчивый performance-regression test. Точные замеры времени, большие наборы данных, профилирование памяти и сравнение cold/warm относятся к отдельному benchmark, а не к обычному `/itl-check`.

YAxUnit-тесты группируются в тестовом расширении по прикладной подсистеме, объекту и алгоритму: быстрые функциональные и граничные случаи, сохранённые регрессии дефектов и инварианты оптимизации. Каждый новый или изменённый тестовый модуль сразу получает группу, режим `default-fast|explicit-benchmark` и пути владельца в branch-каталоге. Все `default-fast` группы выполняются вместе за один штатный сеанс YAxUnit; отдельный процесс 1С на каждую группу не запускается. `explicit-benchmark` не включается в обычную регистрацию `ИсполняемыеСценарии`. Выборочный запуск быстрых YAxUnit-групп по владельцам стоит добавлять только после измеримого замедления их полного набора.

Vanessa-сценарий в том же изменении получает `acceptance|explicit` и `ownerPaths` в branch-каталоге. После refresh агент обязан завершить обнаруженную классификацию в той же задаче. Если каталог отсутствует, неоднозначен или не покрывает новый тест/владельца, `/itl-check` останавливается до запуска 1С; полный набор больше не используется как неявный запасной вариант.

## Штатная проверка

Для решающего executable milestone либо финального completion gate после quick-fix, direct full-cycle, apply или ручных изменений выполните:

```text
/itl-check
```

Команда загружает изменённые файлы в копию базы, запускает разрешённые YAxUnit, Vanessa Automation и проверку журнала регистрации. Финальный запуск выполняется без `VanessaFeaturePath` и `VanessaFilterTags`: filtered run не считается финальным fresh pass. Fresh passed результат относится к точному содержимому конфигурации, расширения и обоих слоёв тестов; следующая verification-relevant правка делает его stale.

Upstream Gate 3a (`validatequery`/`vcexecutecode`) выполняется только когда именно branch Data MCP экспортирован для уже опубликованной dev/test ИБ. ROCTUP не подменяет этот gate, а workflow не публикует базу автоматически только ради него. Если инструмента нет, применяется штатный upstream-отчёт о пропуске; финальным обязательным executable evidence всё равно остаётся fresh passed `/itl-check`.

Не запускайте отдельное обновление базы перед `/itl-check`. Не заменяйте executable evidence данными MCP или ручным открытием формы.

Если агент мог пропустить релевантный сценарий либо должен диагностировать падение, исправить реализацию и повторить проверку, используйте:

```text
/itl-verify-fix
```

Сначала переиспользуется существующее покрытие. Новый сценарий создается только при реальном пробеле. После трех неуспешных попыток по одной группе ошибок агент останавливается и показывает диагностику.

## Режимы проверки

`/litemode` и `/itl-litemode` управляют разными слоями. Первый меняет глубину статических проверок из `ai_rules_1c`, второй — выполнение проверок ITL через Vanessa и журнал регистрации. Их точные значения и значения по умолчанию приведены в [справочнике режимов](MODES-AND-SETTINGS.ru.md).

Если ITL-компонент явно отключен, результат считается partial, а не verified. При `VERIFICATION_POLICY=warn` partial result требует подтверждения; при `block` он запрещен.

## Ревью кода

Отдельный review не запускается автоматически. Если он нужен, попросите явно:

```text
Сделай code review изменения <change-id>. Проверь ошибки, регрессии, риски, недостающие тесты и соответствие OpenSpec.
```

После исправлений review предыдущий `/itl-check` становится stale; выполните проверку снова.

## Результат и завершение

Когда требуется передать текущую версию изменения:

```text
/itl-result
```

В ответе `/itl-result` проверьте полный путь к `CF`/`CFE`, путь к манифесту и статус проверки. Контрольная сумма SHA-256 хранится в манифесте. Импорт результата в исходную базу выполняется вручную.

После приемки OpenSpec change заархивируйте его способом, который показывает `/itl`. Для native-клиента с таким синтаксисом:

```text
/opsx-archive <change-id>
```

Для natural-режима:

```text
Заархивируй принятый OpenSpec change <change-id> и синхронизируй specs
```

Архивация переносит согласованные изменения спецификаций в актуальные документы проекта. Она выполняется после приемки, а не вместо проверки или выгрузки результата.

## Критерий готовности

Изменение можно назвать готовым, когда:

- реализованы согласованные требования;
- добавлено или обновлено релевантное покрытие: YAxUnit для локальной логики, Vanessa для интеграции/UI либо оба слоя для смешанного изменения;
- после последних правок получен fresh passed `/itl-check`;
- указаны пути к отчетам действительно выполненных тестовых слоев;
- для OpenSpec обновлены tasks/test report и выполнена нужная архивация.

Если тест нельзя реализовать или проверку нельзя довести до pass, результат оформляется как блокер или явно подтвержденный partial result, но не как verified/done.
