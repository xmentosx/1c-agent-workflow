# Design

## Context

Мотивация и замеры — в `proposal.md`, требования — в `specs/checked-load-rollback/spec.md`.

Сейчас всё проходит через `Invoke-ConfigLoadDesignerAttempt` в `agent-1c.lifecycle.ps1`:

1. `New-DesignerGate6Snapshot` берёт снапшот внешней операции или делает `/DumpIB` в `.agent-1c/snapshots/gate6-*.dt` и регистрирует restoration duty `infobase-snapshot` (policy `on-failure`) во внутрипроцессном журнале.
2. Для основной конфигурации с legacy-контекстом — базовый `/CheckConfig`. Его привязка включает SHA снапшота, а перед проверкой «после» хэш DT пересчитывается.
3. Редактируемая загрузка и проверка стабильности источника.
4. `Invoke-DesignerGate6CheckLadder`.
5. `/UpdateDBCfg`, затем `AfterApply` (сейчас только проверка готовности расширения тестов). При успехе DT удаляется.
6. При ошибке до `applySucceeded`, то есть и после успешного `/UpdateDBCfg`, если упал `AfterApply`: `/RestoreIB`, затем `ItlConfigLoadSnapshotRestored` (уже содержит `applyStarted`), затем `Restore-ConfigLoadPreviousDesignerProof`.

Вокруг этого `Load-ConfigFromFiles` перед загрузкой очищает fingerprint и ставит `configLoadStatus=pending`, но **не** очищает поле применённого дерева. `Get-ConfigLoadChangeSet` строит частичный список как `git diff` между этим деревом и текущим. Полная загрузка выбирается только при отсутствии дерева, недоступности diff или удалении файлов. Там же уже вычисляется `$loadProofInvalidated`: пустой fingerprint при незавершённом `configLoadStatus` заставляет выполнить полную загрузку, если diff пуст.

Отсюда инвариант, на котором держится частичная загрузка: **редактируемый объект равен применённому дереву**. Сейчас его обеспечивает только успешный `/RestoreIB`. После `GATE6_SNAPSHOT_RECOVERY_FAILED` сообщение требует восстановить DT перед повтором, но код этого не проверяет. После убитого процесса защиты нет совсем.

Курсор `ConfigDumpInfo.xml` сохраняет и восстанавливает отдельный владелец (`New-ConfigDumpInfoLoadSnapshot`).

Legacy-контекст (`New-ProductionPlatformLegacyContext`) доступен только при доказанном происхождении прежнего дерева. Без записанного дерева он отказывает с `PRODUCTION_ORIGIN_UNPROVEN`, и проверка становится строгой.

## Goals / Non-Goals

**Goals:**

- Убрать DT из обычной проверенной загрузки без новых сравнений и без потери частичного повтора.
- Восстанавливать инвариант «редактируемый объект = применённое дерево» и после неудачи, и после прерванного запуска.
- У каждого нового отказа должно быть продолжение, которое двигает исходную задачу к приёмке, а не повторяет тот же отказ.
- Обойтись без нового persisted-состояния: незавершённость определяется по уже существующим полям.

**Non-Goals:**

- Устранение гонки владельцев из инцидента 14:27. Здесь фиксируется только предпосылка, без которой D3 небезопасен (D3).
- Удаление оставшихся DT.
- Снапшоты `Init-DevBranchExtension` и Release.
- Состав и условия проверок gate6.
- Защита неприменённых ручных правок в Конфигураторе. Workflow их и сейчас не защищает: частичная загрузка применяет их без проверки, полная перезаписывает.

## Decisions

### D0. Объекты проверенной загрузки

| Объект | Владелец и путь | Режим | Доказательство применённого | Точка отката |
|---|---|---|---|---|
| Основная конфигурация из исходников | `Load-ConfigFromFiles` → `Invoke-ConfigLoadWithFallback` | partial, full, fallback | `lastConfigDesignerFingerprint`, `lastConfigDesignerTreeObjectId` | `db-configuration` |
| Расширение проекта из исходников | то же, `ContentKind=extension` | partial, full, fallback | `lastExtensionDesignerFingerprint`, `lastExtensionDesignerTreeObjectId` | `db-configuration` или `absent-extension` (D4) |
| Расширение тестов | синхронизация YAxUnit (`agent-1c.yaxunit.ps1`), `/LoadConfigFromFiles` без `-listFile` | всегда полная | `yaxunitInstallationProof` (обнуляется до загрузки) и runtime-запись расширения | по присутствию от владельца (D4) |
| Инструментальные CFE | `Invoke-GuardedCfeExtensionApply` (`/LoadCfg`) | всегда полная замена | у владельца или нет | по присутствию от владельца или проверке (D4) |
| Инициализация расширения, Release | передают `-EnclosingSnapshot` | — | — | `enclosing` |

Дыра частичного повтора есть только у **частично загружаемых объектов** (первые две строки). Поэтому D2, D3 и D3a применяются только к ним. Для объектов с полной загрузкой следующая загрузка и так целиком заменяет содержимое, и им нужен только немедленный откат D1 и правило D1b.

Сверка с кодом (задача 1.2, 2026-11-10):

- `Invoke-ConfigLoadWithFallback` (partial, full, fallback) вызывается только из `Load-ConfigFromFiles`. Его вызывают `Update-DevBranchBase`, `Invoke-BranchSourceSyncLoad`, `Invoke-RefreshDevBranchCore`, `Invoke-ReleaseE2EExtensionSmoke`, `Export-DevBranchResult` и `Close-DevBranch`. Все они работают внутри изменяющих действий, а `Enter-Agent1cLifecycleOperation` берёт для таких действий эксклюзивную lifecycle-блокировку worktree ветки (`FileShare.Read`). `sync-dev-branches` берёт её на worktree всех участвующих веток. Процесс-продолжение работает под блокировкой родителя. Пути без эксклюзивной блокировки не найдено.
- `Invoke-GuardedCfeExtensionApply`: `Ensure-YAxUnitExtensions` (движок, присутствие из runtime-пробы), `Install-DataMcpExtension`, `Install-VanessaMcpExtensionCfe`, `Prepare-ReleaseE2EOnDemandDependencies` (присутствие через `/DumpDBCfgList`, если не заимствован снапшот Release).
- Прямой `Invoke-ConfigLoadDesignerAttempt` из `Ensure-YAxUnitExtensions` — расширение тестов, присутствие из runtime-пробы. `Init-DevBranchExtension` передаёт `-EnclosingSnapshot`.

Чтобы attempt мог выполнить D2–D3a, `Load-ConfigFromFiles` передаёт ему контекст применённого доказательства: путь состояния, имена полей fingerprint и дерева объекта, значения fingerprint и дерева **до** очистки, а также признак незавершённой загрузки (D3). Без этого контекста (расширение тестов, CFE) D2–D3a не выполняются.

### D1. Точка отката — конфигурация БД, без DT и без сравнения

`New-DesignerGate6Snapshot` становится фабрикой точки отката с видами:

- `enclosing` — без изменений;
- `db-configuration` — основная конфигурация или расширение, которое есть в БД;
- `absent-extension` — расширения нет в БД до загрузки.

При неудаче **до успешного завершения `/UpdateDBCfg`** (загрузка, проверка стабильности, лестница проверок, ошибка самого `/UpdateDBCfg`) блок `catch` вызывает `/RollbackCfg [-Extension <name>]` или `/DeleteCfg -Extension <name>`. Успех — нулевой код процесса и `/DumpResult=0`. Контрольного `/CompareCfg` нет.

Почему без сравнения:

- `/RollbackCfg` — нативная операция с явным результатом. В пробе успешный результат всегда совпадал с отсутствием различий.
- Сравнение «до» защищало только неприменённые ручные правки, а их workflow и так не защищает.
- Каждое сравнение — полный проход по конфигурации, и на крупных конфигурациях его цена не измерена.

Отклонённые альтернативы:

- **Всегда DT.** 50–146 с на каждую загрузку.
- **Ничего не откатывать и полагаться на следующую загрузку.** Частичный список строится от применённого дерева, поэтому неудачное содержимое файлов, не изменённых исправлением, уйдёт в БД. Принудительная полная загрузка на каждом повторе закрыла бы это, но стоила бы 20–41 с и отключала бы legacy-проверку «до».
- **Сравнение «до» и «после» через `/CompareCfg`.** Полный проход на каждую загрузку ради защиты, которой больше нигде нет.

### D1b. Ошибка после успешного применения не откатывается

После успешного `/UpdateDBCfg` конфигурация БД уже равна кандидату, и `/RollbackCfg` ничего не изменит. Сейчас так может упасть только `AfterApply` — проверка готовности расширения тестов. Владелец в этом случае:

- не выполняет откат и не заявляет его;
- возвращает `GATE6_POST_APPLY_FAILED` с исходной ошибкой и путями журналов применения и проверки;
- оставляет доказательство применённого недействительным. У частично загружаемых объектов дерево уже очищено по D2, у расширения тестов владелец уже обнулил `yaxunitInstallationProof`. Поэтому повтор исходной операции выполняет полную загрузку и снова проверяет готовность.

Это **сужение гарантии** по сравнению с DT: DT возвращал прежнюю версию расширения, теперь в БД остаётся кандидат. Он прошёл все обязательные проверки gate6 до применения, и ни один владелец не считает его проверенным, пока доказательство не записано заново. Сужение требует решения пользователя (задача 1.1).

Отклонённые альтернативы:

- **Удалять расширение тестов после ошибки готовности.** Удаляет его данные и настройки безопасного режима, а защиты сверх обнулённого доказательства не даёт.
- **Оставить DT только для расширения тестов.** Возвращает около 90 с на каждую его загрузку.

### D2. Применение аннулирует доказательство дерева

Только для частично загружаемых объектов (D0). Перед `/UpdateDBCfg` владелец записывает в состояние пустое применённое дерево объекта. Новое дерево записывается как сейчас после успеха.

Если применение завершилось ошибкой, редактируемый объект откатывается по D1, а следующая загрузка полная. Если процесс убит во время применения, следующая загрузка тоже полная. Причина: убийство после фиксации нельзя отличить от сбоя до неё, а частичный список от старого дерева пропустил бы изменения, уже попавшие в БД. Это новый случай полной загрузки по сравнению с DT, где повтор после восстановления оставался частичным. Он возможен только при сбое самого `/UpdateDBCfg`.

### D3. Откат незавершённой загрузки в начале следующей

Только для частично загружаемых объектов (D0).

**Признак.** Признак вычисляет `Load-ConfigFromFiles` по состоянию **до** собственной очистки fingerprint — в том же чтении, где уже вычисляется `$loadProofInvalidated`. Признак незавершённой загрузки этого объекта: поле fingerprint объекта пусто, а поле дерева объекта записано. Общий `configLoadStatus` для признака не используется: он один на основную конфигурацию и расширение. `$loadProofInvalidated` сохраняет нынешнюю роль. Признак передаётся в attempt в контексте из D0.

Такое состояние остаётся после прерванной загрузки до применения, после `GATE6_SNAPSHOT_RECOVERY_FAILED` старой версии и после подтверждённого отката, если `Restore-ConfigLoadPreviousDesignerProof` не восстановил доказательство (повторный откат тогда безвреден и стоит около 4 с). Места, которые инвалидируют доказательство (инициализация и смена расширения, восстановление Release), очищают fingerprint и дерево вместе, поэтому признак не срабатывает. Если дерево пусто (первая загрузка, прерванное применение по D2, неудачный откат по D3a), загрузка и так полная, и откат не выполняется.

**Действие.** При этом признаке фабрика точки отката до legacy-проверки и до загрузки выполняет тот же откат, что и в D1. Сообщение об откате указывает, что неприменённые правки в Конфигураторе отброшены. Если откат не удался — D3a.

**Предпосылка.** Признак отличает незавершённую загрузку от идущей только тогда, когда никакой другой процесс не может в это время загружать тот же объект. Поэтому D3 выполняется только под эксклюзивной lifecycle-блокировкой worktree ветки, которая удерживается всю проверенную загрузку. Задача 1.2 проверяет это для каждого вызывающего. Если найдётся путь проверенной загрузки без этой блокировки, D3 на нём не выполняется, и решение возвращается пользователю до реализации: это область гонки владельцев, выведенная из постановки.

### D3a. Неудачный откат переводит следующую загрузку в полную

Если немедленный откат (D1) или откат в начале загрузки (D3) завершился неуспешно, владелец:

- возвращает `GATE6_ROLLBACK_RECOVERY_FAILED` с исходной ошибкой и путями журналов загрузки, проверки и отката;
- оставляет fingerprint пустым и не восстанавливает прежнее доказательство;
- очищает применённое дерево частично загружаемого объекта; при откате в начале загрузки новая загрузка не начинается.

Продолжение для агента — повтор исходной операции. Дерево пусто, поэтому откат не повторяется, и выполняется полная загрузка. Она целиком заменяет редактируемый объект содержимым исходников и проверяет его, то есть восстанавливает инвариант без отката. Legacy-контекст недоступен (`PRODUCTION_ORIGIN_UNPROVEN`), и проверка строгая, поэтому найденные в неудачном содержимом ошибки не могут быть приняты как прежние. Если не проходит и полная загрузка, агент получает обычную ошибку загрузки с журналами. Повреждённая ИБ восстанавливается через `reset-dev-branch`, и текст `GATE6_ROLLBACK_RECOVERY_FAILED` называет этот путь.

Так устойчивая причина (платформа без поддержки команды, расширение удалено вручную при записанном доказательстве, повреждённая ИБ) не приводит к бесконечному повтору одного и того же отката.

Для объектов с полной загрузкой поля дерева нет, и следующая загрузка и так полная, поэтому продолжение то же.

Для `absent-extension` неудачный `/DeleteCfg` или убитая первая загрузка нового расширения оставляют в ИБ кандидат, ни разу не применённый в БД. Проба задачи 1.4 (8.3.27.2074, копия ветки PM5, 2026-11-10) показала, что различить его нельзя: `/DumpDBCfgList -Extension` после `/LoadCfg` без `/UpdateDBCfg` выводит имя такого расширения с кодом 0. `/RollbackCfg -Extension` на нём возвращает `0/0`, но запись остаётся в списке. `/DeleteCfg -Extension` затем удаляет её чисто.

Решение: такой остаток определяется как присутствующий (`db-configuration`) и не удаляется — как и любое расширение, которое уже есть в ИБ. Инвариант при этом сохраняется. У нового расширения нет записанного дерева, поэтому следующая загрузка полная и целиком заменяет содержимое. Остаток не применяется в БД, пока проверенная загрузка не пройдёт. Цена — неприменённая запись в списке расширений до успешной загрузки или ручного `/DeleteCfg`. Не проверено, удаётся ли полная загрузка с применением поверх такой записи: проба остановлена из-за нехватки лицензий при работающем живом пилоте (задача 5.2).

Отклонённая альтернатива: **повторять тот же откат при каждом повторе операции.** При устойчивой причине это блокировка без продвижения.

### D4. Присутствие расширения в конфигурации БД

Источник присутствия выбирается в таком порядке:

1. Расширение проекта из исходников: записанное доказательство (fingerprint или дерево) означает присутствие, вид `db-configuration`.
2. Владелец передаёт присутствие из своей свежей runtime-пробы, которая уже выполняется до загрузки. Синхронизация YAxUnit берёт его из `Get-ToolingRuntimeExtensions` для расширения тестов и движка YAxUnit. Дополнительной нативной операции нет.
3. Иначе вызывается существующий `Test-DevBranchExtensionExists` (`/DumpDBCfgList -Extension <name>`, 4–6 с). Отсутствие он определяет по тексту журнала, поэтому фикстуры задачи 1.4 покрывают русский и английский тексты.

- Расширения нет — `absent-extension`.
- Расширение есть (например, перенесено при создании ветки) — `db-configuration`. Такое расширение никогда не удаляется.

Если записанное доказательство говорит, что расширение есть, а его удалили вручную, `/RollbackCfg -Extension` завершится ошибкой, и сработает D3a: следующая загрузка будет полной, без вечного отката.

### D5. Доказательства и совместимость

- **`editableLoad`:** добавляется `rollbackPoint = {kind, extensionName, attemptId, baseIdentity, mechanism, unfinishedPreviousRolledBack}`. Для `enclosing` поле `snapshot` остаётся как сейчас, для остальных видов `snapshot = $null`.
- **`baseIdentity`:** SHA-256 канонического JSON из вида ИБ, нормализованного пути ИБ, вида содержимого, имени расширения, а также fingerprint и дерева применённого доказательства **до** загрузки. Для `absent-extension` вместо доказательства — маркер `absent`. `attemptId` — уникальный идентификатор попытки.
- **Привязка `LegacyBaseline`:** базовая и последующая проверки должны совпадать по `attemptId` и `baseIdentity`. Так «до» привязано к содержимому, к которому ведёт откат, как раньше к SHA DT. Вместо пересчёта хэша DT перед проверкой «после» владелец проверяет, что поле дерева в состоянии не изменилось. Legacy-контекст и так требует доказанного дерева, поэтому `baseIdentity` всегда содержит его.
- **`ItlConfigLoadSnapshotRestored`:** ключ сохраняется, это данные исключения в памяти. `applyStarted` в нём уже есть. Добавляются `mechanism` и `rollbackPoint`. `Restore-ConfigLoadPreviousDesignerProof` по-прежнему требует `applyStarted=$false`. С D2 это следует и из пустого дерева, но условие остаётся явным.
- **Читатели SHA снапшота**, которые переходят на `rollbackPoint` с сохранением DT-ветки:
  - сравнение `LegacyBaseline.snapshot.sha256` и `EditableLoad.snapshot.sha256` и пересчёт хэша DT в `Invoke-DesignerGate6CheckLadder`;
  - `snapshotSha256` в квитанции `1c-gate6-evidence-*.json`;
  - `Write-ConfigLoadRejectionEvidence`: квитанция `itl-gate6-rejection` получает `rollbackPoint` и `rollbackConfirmed`; `snapshotSha256` и `snapshotRestored` пишутся только для `enclosing` и старых записей.
- **Старые доказательства и состояние** с DT-ссылками читаются без изменений. Все читатели `lastGate6Evidence` проверяются на `snapshot = $null` (задача 1.3).

### D6. Нативные операции

`/RollbackCfg`, `/DeleteCfg -Extension` и `/DumpDBCfgList -Extension` (через `Test-DevBranchExtensionExists`) запускаются через существующий `Invoke-Designer` под per-infobase guard, класс `designer-command`. Если существующий контракт native-effect или guard перечисляет допустимые редактируемые мутации, новые операции добавляются в то же перечисление с регрессией полноты набора.

### D7. Тексты правил

- `references/verification-result.md`: абзацы о DT-снапшоте заменяются точкой отката, D1b–D3a и кодами `GATE6_ROLLBACK_RECOVERY_FAILED` и `GATE6_POST_APPLY_FAILED` с их продолжениями.
- Корневой `AGENTS.md`: «snapshot rollback» → «checked-load rollback». Гарантия та же, кроме сужения D1b; механизм — DT внешнего владельца или нативный откат к конфигурации БД.
- `references/artifact-retention.md`: `gate6-*.dt` упоминается как наследие старых запусков.

## Architecture checkpoint

- **Инвариант:** неудачная или прерванная проверенная загрузка не оставляет в редактируемой конфигурации или расширении веточной ИБ содержимое, отличное от применённого дерева, которое последующая частичная загрузка могла бы применить без проверки. Содержимое, которое попало в БД до ошибки `AfterApply`, прошло обязательные проверки и не считается проверенным, пока доказательство не записано заново (D1b).
- **Владелец:** checked-load owner (`Invoke-ConfigLoadDesignerAttempt` и фабрика точки отката) вместе с `Load-ConfigFromFiles`, которому уже принадлежат fingerprint и дерево и который вычисляет признак D3. Присутствие расширения сообщает владелец объекта либо `Test-DevBranchExtensionExists`.
- **Чего нет:** нового координатора, блокировки, фоновой службы, persisted-поля и машины состояний. Восстановление между независимыми владельцами не расширяется.
- **Предпосылка:** проверенная загрузка частично загружаемого объекта выполняется под эксклюзивной lifecycle-блокировкой worktree ветки (D3, задача 1.2).
- **Затронуто:**
  - загрузки основной конфигурации и расширения проекта из исходников (partial, full, fallback) в файловые и серверные веточные ИБ;
  - загрузка расширения тестов и передача присутствия из синхронизации YAxUnit;
  - установка инструментальных CFE через проверенную загрузку без внешнего снапшота.
- **Не затронуто:** инициализация расширения, Release E2E, экспорт `/DumpCfg`, `reset-dev-branch`, мастер-база, сессии Enterprise, клиенты и MCP.
- **Установленное состояние:** миграции нет. Незавершённое состояние старой версии распознаётся по тем же полям (D3).
- **Откат изменения:** предыдущая версия пакета снова делает DT. Доказательства с `snapshot = $null` она должна воспринимать как устаревшие без ошибки (задача 1.3).
- **Ожидание:** дополнительные нативные операции только при неудаче, при незавершённой загрузке и при проверке присутствия расширения без доказательства и без переданного владельцем присутствия. Используются существующие таймауты.
- **Платформы:** Windows 10, 11 и Server 2019+ без повышения прав. Если платформа не поддерживает `/RollbackCfg` или `/DeleteCfg -Extension`, это ошибка восстановления по D3a, а не тихий пропуск. Минимальная версия проверяется в задаче 1.5.
- **Решающее доказательство:** live-приёмка 5.2 на копии `branch10` и замер длительности до и после по `logs/1c`.
- **Отдельное разрешение пользователя:** правка корневого правила `AGENTS.md` и сужение гарантии D1b.

## Risks / Trade-offs

- [`/RollbackCfg` вернул успех, но не вернул объект] → в пробе такого не было. Live-приёмка 5.2 включает контрольное сравнение вне продуктового кода.
- [Сбой `/UpdateDBCfg`, после которого следующая загрузка полная] → редкий случай, 20–41 с один раз. Это цена корректности при неизвестном состоянии БД.
- [Неудачный откат] → одна полная загрузка со строгой проверкой (D3a), без вечной блокировки.
- [Ошибка готовности расширения тестов после применения] → кандидат остаётся в БД без доказательства, повтор выполняет полную загрузку (D1b). Сужение гарантии требует решения пользователя.
- [Физическое повреждение файловой ИБ при прерывании реструктуризации] → раньше это покрывал DT. Теперь — `reset-dev-branch`, как при любом повреждении веточной ИБ.
- [`/RollbackCfg` в начале загрузки отбрасывает неприменённые ручные правки] → workflow их и сейчас не защищает. Сообщение об откате незавершённой загрузки говорит об этом.
- [Параллельный владелец той же ИБ] → признак D3 принял бы его идущую загрузку за незавершённую, и после отката тот владелец записал бы ложное доказательство. Поэтому есть предпосылка эксклюзивной блокировки (D3, задача 1.2).
- [Отсутствие расширения определяется по тексту журнала] → фикстуры на русском и английском, неизвестный текст — ошибка, а не «отсутствует».
- [Платформа без пакетных `/RollbackCfg -Extension` или `/DeleteCfg -Extension`] → ошибка восстановления с журналом. Минимальная версия проверяется в задаче 1.5 до реализации.

## Migration Plan

Миграции нет. Доставка обычная: `RegisterChange`, затем `PublishDevelop`. Установленные проекты получают изменение через `update-workflow`. Откат — предыдущая версия пакета.
