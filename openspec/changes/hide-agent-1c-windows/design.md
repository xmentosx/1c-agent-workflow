# Design

## Context

Мотивация — в `proposal.md`, факты пробы — в `docs/hidden-testclient-probe.md`.
Состояние `origin/develop` (`7d6cb6a5`):

- Фоновые запуски 1С идут через `Start-EnterpriseBackground` →
  `Start-OneCProcessBackground` (`agent-1c.sessions.ps1`) →
  `Start-NativeProcessBackground` (`agent-1c.core.ps1`) под ограничителем
  сеансов на инфобазу. Скрыто (`-WindowStyle Hidden`) запускаются все, кроме
  TestClient: у него `-Visible:$UseTestClient` (коммит `5b432565`).
- Клиент тестирования раннера запускает сам Vanessa
  (`ЗапуститьСеанс1СЧерез1cv8`): bat-файл через `WScript.Shell.Run(bat, 0)`.
  Скрытым получается `cmd`, а 1С показывается. Ограничитель сеансов узнаёт
  клиента по `/TESTCLIENT` в командной строке, а не по цепочке родителей.
- ITL-патч Vanessa (r10–r11 в `develop`, r12 в очереди) отмечает агентский
  запуск флагом `ITLAgentLaunch` (единственный владелец —
  `Add-VanessaAgentLaunchParams`). В нём есть одна точка перед вводом ОС
  (`ITLАктивироватьКлиентТестированияДляВводаОС`) и фоновый снимок окна
  процесса через `PrintWindow`.
- `Add-VanessaAgentLaunchParams` уже защищает файловый канал кода
  (`ITLClientCodeChannelRoot`) от предела `MAX_PATH` файлового API 1С: корень,
  в который не помещается самый длинный путь канала, не передаётся.
- Окно клиента Vanessa ищет через VanessaExt `НайтиКлиентТестирования`,
  которая не видит скрытые окна.
- Раннер уже отслеживает дочерние `/TESTCLIENT` процессы менеджера (`ca317004`)
  в своём мониторе живости. ROCTUP MCP — долгоживущий `/Execute` с
  HTTP-сервером, его главное окно уже скрыто; готовность ждёт
  `Wait-RoctupMcpPort`.
- `scripts/measure-foreground-changes.ps1` пишет каждое событие переднего плана
  и классифицирует события процессов 1С (`new-process`, `new-window`,
  `reactivation`). Базовый замер — 21 событие за один Release E2E.
- Проект и артефакты прогона часто лежат в каталоге, синхронизируемом
  OneDrive (так на машине разработки).
- Пример ограничений машины: `dev-karimov` с нехваткой памяти, отсюда лимит
  на рабочий набор помощника.

## Goals / Non-Goals

**Goals:**

- Окна агентских процессов не видны и не забирают фокус. Управление
  забирается только для ввода ОС, с согласием и на минимальное время.
- Помощник не становится частой точкой отказа: его можно убить, он
  перезапускается сам, а при недоступности клиент запускается видимым.

**Non-Goals:**

- Designer, служебные `/Execute` через `Invoke-Enterprise`.
- Отдельный рабочий стол Windows: несовместим с вводом и снимками VanessaExt.
- Изменение `ForegroundLockTimeout` и других настроек Windows.
- Чужие процессы 1С пользователя.
- Скрытие заставки и диалогов TestManager и ROCTUP (решение 7).
- Сокращение числа шагов ввода ОС в сценариях проекта сверх правила
  авторинга: это решение автора сценария.

## Decisions

### 1. Без помощника там, где он не нужен

Менеджер тестирования и ROCTUP запускаются скрытыми, с `/DisableSplash`.
Помощник им не нужен: у них нет ввода ОС, а их диалоги — это редкие ошибки,
которые полезно видеть (случай `ca317004`).

Фокус, который скрытое окно забрало при старте, возвращает одна функция
возврата фокуса запуска (stateless, имя выбирается при реализации):

- путь запуска запоминает окно пользователя до `Start-Process` и кладёт его в
  результат запуска;
- функцию вызывают существующие циклы ожидания вызывающих: `Wait-RoctupMcpPort`
  для ROCTUP и монитор живости раннера для TestManager, с периодом не больше
  500 мс в первые 60 с после старта;
- если передний план принадлежит процессу этого запуска, функция возвращает
  его запомненному окну той же цепочкой `plain`/`nudge`/`attach`, что и
  помощник;
- после 60 с проверка прекращается. Диалоги TestManager и ROCTUP остаются
  видимыми и могут взять фокус, как сигнал ошибки.

Нового процесса и нового ожидания нет. Если период существующего цикла больше
500 мс, он сокращается только на эти 60 с.

Помощник нужен только группам клиентов тестирования. Их диалоги — обычная
часть сценариев, а ввод ОС требует показа и активации.

### 2. Помощник — маленький исполняемый файл .NET Framework, собранный на машине

Исходник C# лежит в workflow. Его собирает `csc.exe` из .NET Framework 4.x
(входит в Windows 10+, Server 2019+); язык ограничен C# 5, который этот
компилятор поддерживает. Каталог результата —
`%LOCALAPPDATA%\itl\window-helper\<sha256 исходника>\`.

- **Сборка.** Во временный каталог рядом, затем атомарное переименование в
  целевой. Два проекта, собирающие одновременно, не портят друг друга:
  проигравший переименование использует готовый каталог.
- **Хеш.** `csc` из .NET Framework недетерминирован, поэтому ожидаемого хеша
  exe заранее нет. После сборки рядом с exe записывается его SHA-256. Перед
  каждым запуском хеш exe сверяется с записанным. Несовпадение — одна
  пересборка, затем отказ.
- **Пути.** Каталог экранируется общим помощником кавычек; путь проверяется на
  пробелы и кириллицу.
- **Процесс.** Без PowerShell-хоста. Рабочий набор не больше 30 МБ,
  фактическое значение и время старта измеряет задача 2.6.
- `SetWinEventHook` (`EVENT_OBJECT_SHOW`, `EVENT_SYSTEM_FOREGROUND`,
  `WINEVENT_OUTOFCONTEXT`), фильтр по PID своей группы. Раз в 2 с — дешёвая
  сверка окон и каталога запросов, чтобы не потерять пропущенное событие.
  Других пробуждений в простое нет.
- `PER_MONITOR_AWARE_V2` до создания первого окна, чтобы координаты совпадали
  с VanessaExt.

Отвергнутые варианты:

- **Скрипт PowerShell с `Add-Type`** (как в пробе): 60–80 МБ на экземпляр и
  около 1 с на компиляцию при каждом старте. Это плохо при нескольких
  проектах.
- **Выпускаемый бинарник** (например, в `itl-ondemand-mcp`): отдельная
  Release-квалификация и подпись ради того же кода.
- **VanessaExt**: upstream-бинарник, показывать скрытые окна не умеет.

Риск: антивирус, AppLocker или WDAC запрещают свежесобранный exe в профиле
(правила AppLocker по умолчанию разрешают только `Program Files` и
`Windows`). Это обрабатывает проверка готовности при запуске (решение 3):
клиент запускается видимым с `WARN`.

### 3. Помощник одноразовый, готовность проверяется до запуска клиента

- **Состояние.** Всё, что нужно для работы, лежит в каталоге группы:
  `group.json` с версией протокола, корневыми PID и параметрами, запросы и
  ответы, журнал, `helper.json` с PID и временем старта помощника. Состояние
  в памяти восстанавливается из каталога и из живых процессов.
- **Один экземпляр на группу** — по открытому эксклюзивно файлу
  `helper.lock` в каталоге группы. ОС снимает блокировку, когда процесс
  умирает, поэтому зависших блокировок не бывает. Файлы группы — данные, а не
  владение.
- **Старт и готовность.** Помощник запускает PowerShell-путь запуска до
  клиента тестирования:
  - vanessa-ui — перед `Start-EnterpriseBackground -UseTestClient`, группа —
    каталог сессии;
  - раннер — перед запуском TestManager, группа — каталог прогона, корень —
    PID менеджера, клиенты добавляются через `adopt` как потомки менеджера.

  Готовность — ответ на `status` за 3 с.
- **Помощник недоступен при запуске** (сборка, запуск, AppLocker, предел
  `MAX_PATH` для каталога группы, нет ответа на `status`): группа не
  создаётся, `ITLWindowChannelRoot` не передаётся, клиент запускается видимым,
  как в режиме `visible`. В вывод и итог идёт `WARN`
  `ITL_WINDOW_HELPER_UNAVAILABLE` с причиной. Прогон продолжается: блокировать
  здесь нечего, данные и цель не под угрозой.
- **Завершение.** Убийство процесса допустимо в любой момент. Если помощник
  убит посреди аренды, окно клиента может остаться видимым до следующего
  запроса. Пользователь при этом не теряет управление: помощника, который
  держал бы фокус, больше нет. Помощник сам завершается, когда все процессы
  группы завершились, но не раньше чем увидит хотя бы один корень; без
  корней — через 60 с после старта.
- **Перезапуск посреди прогона.** Запрашивающая сторона (Vanessa через
  `ВыполнитьКомандуОСБезПоказаЧерногоОкна` или PowerShell-путь) ждёт ответа
  3 с, затем:
  - `helper.lock` свободен — запускает помощник с каталогом группы и
    повторяет запрос один раз;
  - `helper.lock` занят, но ответа нет — помощник завис: процесс из
    `helper.json` завершается после сверки имени образа и времени старта,
    затем запуск и один повтор;
  - повтор неудачен — шаг ввода ОС получает `ITL_WINDOW_HELPER_UNAVAILABLE`
    с подсказкой о `visible`. Скрытый клиент показать больше нечем.
    Продолжение — повторный прогон: проверка готовности при запуске выберет
    видимый клиент, если помощник всё ещё недоступен. Снимок при ошибке шага в
    этом случае пропускается с `WARN`, результат шага не меняется.
- **Команды агента** через существующую точку входа `agent-1c.ps1`:
  `window-helper status | stop | restart`, плюс `stop -All` по всем группам
  текущего пользователя. `stop` в режиме `visible` перед выходом показывает
  скрытые главные окна группы. `status` показывает действующий режим группы.

### 4. Канал запросов — файлы в каталоге группы

Каталог группы лежит в артефактах прогона или сессии (по
`docs/itl-workflow/ARTIFACTS.md`), путь передаётся в Vanessa параметром
`ITLWindowChannelRoot` через `Add-VanessaAgentLaunchParams`. Проверку
`MAX_PATH` для него выполняет та же функция, что для
`ITLClientCodeChannelRoot`. Если корень не помещается, это отказ готовности
(решение 3).

- **Операции:** `lease`, `lease-end`, `capture-show`, `capture-end`, `adopt`,
  `status`. Список операций и их полей — один контракт для помощника,
  PowerShell и патча Vanessa. Регрессия проверяет полноту набора во всех трёх
  местах.
- **Поля запроса:** версия протокола, операция, идентификатор области (сценарий
  Vanessa или вызов vanessa-ui), крайний срок (UTC). Помощник отвечает ошибкой
  `protocol-mismatch` на чужую версию; запрашивающая сторона считает это
  недоступностью помощника.
- **Запись.** Атомарно: временный файл, затем переименование. Кодировка UTF-8;
  BOM, который пишет `ЗаписьТекста` 1С, допустим.
- **Доставка.** Помощник узнаёт о запросах через `FileSystemWatcher` и
  дополнительно просматривает каталог запросов в сверке раз в 2 с.
  `FileSystemWatcher` теряет события при переполнении буфера и в каталогах
  OneDrive. Приём тот же, что у файлового канала кода Vanessa: 1С не умеет
  именованные каналы без внешней компоненты.

### 5. Аренда управления и согласие

Помощник ведёт одну машину состояний на группу:
`idle` → `queued` → `consent` → `idle-wait` → `leased` → `idle`; отказ
переводит область в `declined`.

- **Область согласия.** Согласие и отказ действуют до конца области —
  сценария Vanessa или вызова vanessa-ui (решение пользователя 2026-11-10).
  Первый `lease` области показывает окно согласия. Следующие аренды той же
  области начинаются без окна, только с панелью аренды. После «Отмены» все
  следующие `lease` области сразу получают `declined` без окна. Область
  закрывает `lease-end` с признаком конца области или запрос с другим
  идентификатором области.
- **Очередь между группами.** Перед окном согласия помощник берёт именованный
  мьютекс `Local\ITL-UiLease` (пространство `Local` — один терминальный
  сеанс). Поэтому два окна согласия одновременно не показываются. «Пауза»
  отпускает мьютекс; «Сейчас» на панели паузы снова встаёт в очередь. Мьютекс
  захватывается и отпускается одним выделенным потоком помощника: владение
  мьютексом привязано к потоку. Непрерывное удержание ограничено 60 с: после
  них аренда заканчивается штатно (возврат фокуса, скрытие), следующий `lease`
  встаёт в очередь заново. Согласие области при этом сохраняется. Ожидание
  мьютекса не дольше крайнего срока запроса.
- **Окно согласия** (WinForms в том же exe) на мониторе активного окна
  пользователя:
  - полноэкранное окно «Агент хочет получить доступ к интерфейсу», поверх всех
    окон (`TopMost`), отсчёт (`ONEC_UI_LEASE_COUNTDOWN_SECONDS`, по умолчанию
    10, 0 — без окна), кнопки «Сейчас», «Пауза», «Отмена»;
  - кнопки по умолчанию нет: Enter и пробел, которые пользователь печатал в
    своём приложении, не нажимают кнопку. Кнопки нажимаются мышью или
    явными сочетаниями Alt;
  - окно показывается видимым и поверх всех даже без активации (блокировка
    переднего плана). Отсчёт начинается только после подтверждения, что окно
    видимо. Если окно показать нельзя (заблокированный или отключённый сеанс),
    аренда отклоняется с `ITL_UI_CONTROL_DECLINED` и причиной;
  - при «Паузе» — маленькая панель поверх всех окон в углу монитора, вне
    прямоугольника клиента, с теми же кнопками.
- **Предел ожидания.** Пауза и ожидание простоя ограничены
  `ONEC_UI_LEASE_PAUSE_LIMIT_SECONDS` (по умолчанию 600), но не дольше
  крайнего срока запроса. Vanessa передаёт тайм-аут шага, vanessa-ui —
  остаток бюджета вызова. По истечении — `ITL_UI_CONTROL_DECLINED` с причиной
  `pause-limit` или `deadline`.
- **Ожидание простоя.** После согласия помощник ждёт простоя ввода
  пользователя 300 мс (`GetLastInputInfo`). Если простоя нет 5 с, появляется
  панель «Жду паузы в вашем вводе» с кнопками «Сейчас» и «Отмена», и ожидание
  продолжается до предела ожидания (решение пользователя 2026-11-10).
  «Сейчас» на этой панели начинает аренду сразу.
- **Начало аренды.** Помощник показывает главное окно и скрытые окна клиента и
  активирует последнее активное окно (`GetLastActivePopup`) цепочкой
  `SetForegroundWindow` → пустое движение мыши → `AttachThreadInput`, до 3
  попыток.
- **Проверка перед вводом.** Vanessa сверяет PID окна из `АктивноеОкно`
  VanessaExt с PID клиента. Несовпадение — `ITL_WINDOW_ACTIVATION_FAILED`.
- **Во время аренды.** Видна небольшая панель «Агент управляет вводом» с кнопкой
  «Отмена». Она не активирует себя (`WS_EX_NOACTIVATE`) и стоит вне
  прямоугольника клиента, поэтому не перехватывает клики VanessaExt. «Отмена»
  на ней завершает аренду, текущий шаг падает с `ITL_UI_CONTROL_DECLINED`, а
  область переходит в `declined`.
- **Продление.** Каждый `lease` следующего шага ввода продлевает аренду в
  пределах 60 с непрерывного удержания. Аренда кончается через 2 с без
  запросов, по `lease-end` из обработчика завершения сценария или вызова и по
  пределу удержания.
- **Конец аренды.** Фокус возвращается окну пользователя, пока клиент ещё
  видим. Затем окна клиента скрываются, курсор возвращается, и на 2,5 с
  показывается окно «Операция завершена, можно пользоваться». Оно не
  активирует себя (`WS_EX_NOACTIVATE`, поверх всех), чтобы не отнять только
  что возвращённый фокус. Закрывается раньше по клику и сразу — при начале
  следующей аренды.
- **Окно пользователя.** Помощник обновляет его по `EVENT_SYSTEM_FOREGROUND`
  только окнами, которые не принадлежат помощникам ITL и процессам 1С с
  ролью `/TESTCLIENT` или `/TESTMANAGER` (по командной строке, кэш по PID).
  Поэтому помощник одной группы не запоминает арендованный клиент другой.
  Свои окна согласия и панели тоже не запоминаются.
- **Учёт.** Каждая аренда пишется в журнал группы: начало, ожидание согласия,
  ожидание очереди, длительность, исход. Раннер и vanessa-ui суммируют журнал
  в итог.

### 6. Снимки и список окон — без аренды

`capture-show`: `SetWindowPos(HWND_BOTTOM, SWP_SHOWWINDOW | SWP_NOACTIVATE)`.
Окно становится видимым для `PrintWindow` и VanessaExt, но стоит под окнами
пользователя и не активируется. `capture-end` сразу скрывает его. Окно
согласия не нужно: управление не забирается. Если снимок чёрный, пауза на
отрисовку и повтор один раз. Так же обслуживаются `get_window_list_os` и
`get_window_screenshot_os` vanessa-ui. Действие `activate` vanessa-ui — это
ввод, ему нужна аренда.

Окно клиента в этот момент закрыто окнами пользователя, поэтому в скрытом
режиме допустим только снимок окна процесса через `PrintWindow`. Снимок экрана
или его области в агентском запуске со скрытым клиентом запрещён: он сохранил
бы в артефакты содержимое окон пользователя. Патч Vanessa принудительно
выбирает способ «окно процесса»; способ снимка в `get_window_screenshot_os`
проверяет задача 3.4.

### 7. Скрытый запуск TestClient и заставка

`/DisableSplash` добавляется ко всем запускам этого изменения. Если проба
покажет, что параметр не убирает окно «Загрузка конфигурационной
информации...»:

- у клиентов тестирования его прячет помощник, как любое окно группы;
- у TestManager и ROCTUP заставка допускается: около 1,5 с при старте,
  фокус возвращает функция из решения 1. Помощник для них не вводится
  (решение пользователя 2026-11-10).

Патч Vanessa в агентском запуске с каналом окон запускает клиент напрямую
через `WScript.Shell.Run(<exe и аргументы>, 0, Ложь)`, без bat-файла. Дескриптор
окна и PID берутся из ответа `status` помощника по порту, а не из
`НайтиКлиентТестирования`. Ограничитель сеансов это не меняет: клиент
по-прежнему узнаётся по `/TESTCLIENT`.

### 8. Режим и совместимость

- **Настройка.** `ONEC_WINDOW_MODE` (`hidden` | `visible`), по умолчанию
  `hidden`. Одна функция режима; её вызывают путь запуска и
  `Add-VanessaAgentLaunchParams`. Читается при каждом запуске клиента, поэтому
  переключение действует со следующего запуска. Уже запущенный прогон и
  сессия vanessa-ui сохраняют режим своего запуска до перезапуска клиента;
  `window-helper status` и ответ vanessa-ui показывают действующий режим.
- **Старая ревизия Vanessa.** Если ревизия не объявляет в манифесте
  возможность канала окон, клиенты тестирования запускаются видимыми с
  `WARN`. Менеджер и ROCTUP при этом остаются скрытыми: Vanessa для них не
  нужна.

## Architecture checkpoint

Согласовано пользователем 2026-11-10 после правок: одноразовый лёгкий помощник
с перезапуском и режимом `visible`, параллельные экземпляры, окно согласия с
отсчётом и паузой, аренда только для ввода ОС, `/DisableSplash` вместо
скрытия заставки. Согласие распространяется на границу, описанную ниже. Новый
владелец, класс ресурсов или требование к установленному состоянию требует
нового согласования.

Уточнения по ревью 2026-11-10 остаются внутри границы: новых владельцев,
ресурсов и установленного состояния нет. Пользователь выбрал:

- согласие и отказ действуют до конца сценария или вызова;
- при отсутствии простоя ввода ожидание продолжается с панелью;
- заставка TestManager и ROCTUP допустима без помощника.

Кроме того: недоступный при запуске помощник переводит клиент в видимый
запуск вместо отказа шагов; мьютекс берётся до окна согласия и держится не
дольше 60 с подряд.

Нужен по `docs/package-architecture.md`. Изменение вводит:

- вспомогательный процесс с правом скрывать окна и забирать фокус;
- мьютекс аренды на сеанс Windows между проектами;
- протокол между ITL и патчем Vanessa;
- отказ шага ввода при отказе пользователя или неподтверждённой активации;
- новое поведение по умолчанию во всех установленных проектах.

Пункты контрольной точки:

- **Инвариант:** процесс 1С агентского запуска не владеет экраном и вводом
  пользователя вне аренды, а аренда начинается только после согласия области
  или отсчёта.
- **Владельцы:**
  - путь запуска — окно пользователя, `/DisableSplash`, проверка готовности
    помощника и выбор видимого запуска, создание группы;
  - функция возврата фокуса запуска — TestManager и ROCTUP, вызывается из
    существующих циклов ожидания;
  - помощник — скрытие, очередь, согласие, аренда, журнал; одна машина
    состояний на группу (решение 5);
  - патч Vanessa — когда нужен ввод или снимок, проверка `АктивноеОкно`,
    ошибки шага;
  - одна функция режима;
  - один контракт операций канала.
- **Общее состояние:** мьютекс `Local\ITL-UiLease` — единственный ресурс сверх
  группы. Он упорядочивает аренды разных групп на одном рабочем столе, потому
  что двум агентам нельзя одновременно забирать фокус. Он не переживает
  процесс и не хранит данных. Других координаторов, очередей и постоянного
  состояния нет.
- **Почему не локально у владельца:** окна запускает PowerShell или Vanessa, а
  ввод делает Vanessa в другом процессе. Диалоги скрытого клиента может скрыть
  только внешний процесс, это показал воспроизводитель пробы. Окно согласия
  должно жить вне 1С, иначе его нельзя показать до показа клиента.
- **Затронуты:** запуск TestClient (раннер, vanessa-ui), TestManager раннера,
  ROCTUP, патч Vanessa, диагностика и итоги раннера и MCP.
- **Не затронуты:** Designer, `Invoke-Enterprise`, ограничитель сеансов,
  доставка исходников, другие MCP.
- **Ожидание:**
  - готовность помощника при запуске — не дольше 3 с, затем видимый запуск;
  - запрос Vanessa ждёт ответа помощника не дольше 3 с, затем один
    перезапуск и повтор;
  - очередь, согласие, пауза и ожидание простоя — до предела ожидания и не
    дольше крайнего срока запроса;
  - непрерывное удержание мьютекса — не дольше 60 с;
  - аренда кончается через 2 с без запросов;
  - возврат фокуса TestManager и ROCTUP — первые 60 с после старта.
- **Отмена и восстановление:** убийство помощника допустимо всегда.
  Следующий запрос перезапускает его. Окна, оставшиеся видимыми после
  убийства посреди аренды, прячутся при перезапуске. Отказ помощника при
  запуске даёт видимый клиент с `WARN`; отказ посреди прогона даёт
  `ITL_WINDOW_HELPER_UNAVAILABLE` только в шагах ввода ОС, остальное
  продолжается. Продолжение — повторный прогон или режим `visible`. Миграции
  установленного состояния нет.
- **Платформы:** без прав администратора. Локальный и терминальный сеанс,
  Windows 10, 11 и Server 2019+; параллельные пользователи разделены сеансом
  Windows и `%LOCALAPPDATA%`. Server, терминальный сеанс и среды с AppLocker
  не проверены до E2E.
- **Нагрузка:** в простое только сверка раз в 2 с, до 30 МБ на помощник,
  помощник только у групп с клиентом тестирования.
- **Контекст клиента:** постоянные правила не растут, одна строка в
  `vanessa-authoring.md`.
- **Откат:** `ONEC_WINDOW_MODE=visible`; полный откат — прежние пины Vanessa.
- **Решающее доказательство:**
  - Release E2E `vanessa-ui` и сценарий Vanessa с вводом ОС проходят в режиме
    по умолчанию (отсчёт 0 на стенде, 10 в ручной приёмке);
  - повторный замер `scripts/measure-foreground-changes.ps1` (было 21 событие
    1С): 0 событий переднего плана у процессов клиентов тестирования вне
    интервалов аренды из журнала; у TestManager и ROCTUP не больше одного
    события на запуск, передний план возвращён окну пользователя не позже чем
    через 1 с. Окна помощника не процессы 1С и в счёт не входят;
  - убийство помощника посреди прогона не роняет шаги протокола, а следующий
    шаг ввода проходит после автоматического перезапуска;
  - недоступный помощник даёт видимый клиент и проходящий прогон с `WARN`.

## Risks / Trade-offs

- [Штатный `ForegroundLockTimeout` (200000) чаще отказывает в активации] →
  цепочка `nudge`/`attach`; при неудаче — явная ошибка без ввода, продолжение
  через `visible`. Приёмка повторяется со штатным значением.
- [Окно согласия раздражает] → одно согласие на сценарий или вызов; «Сейчас»;
  настройка отсчёта; итог показывает агенту стоимость шагов ввода ОС.
- [Безлюдный стенд ждёт 10 с на каждую область] → стенды Release E2E задают
  отсчёт 0.
- [Скрытый модальный диалог клиента прячет причину ошибки] → журнал с
  изображением в диагностике отказа.
- [Протокол тестирования не работает со скрытыми диалогами] → проба в задаче
  1.5 до реализации помощника; при отрицательном результате — возврат к
  пользователю.
- [Свежесобранный exe блокирует антивирус, AppLocker или WDAC] → видимый
  запуск с `WARN` при проверке готовности.
- [`FileSystemWatcher` теряет события, особенно в OneDrive] → просмотр
  каталога запросов в сверке раз в 2 с.
- [Убийство посреди аренды оставляет клиент видимым] → окно пропадает при
  следующем запросе. Фокус при этом не удерживается.
- [`/DisableSplash` может не убирать окно загрузки конфигурации] → проба в
  задаче 1.3; у клиентов его прячет помощник, у TestManager и ROCTUP
  заставка допускается с возвратом фокуса.
- [Окно согласия на мониторе, где пользователь его не видит] → показ на
  мониторе активного окна пользователя.
- [Снимок экрана со скрытым клиентом захватывает окна пользователя] → в
  скрытом режиме только `PrintWindow` окна процесса.

## Migration Plan

1. Новая ревизия патча Vanessa поверх ревизии, принятой в `develop` на момент
   реализации: сборка, ассеты, пины.
2. Помощник, путь запуска, настройки и команды в одном изменении с пинами.
3. Публикация через `PublishDevelop` со стадией Release E2E `vanessa-ui`
   (отсчёт 0).
4. Откат: `ONEC_WINDOW_MODE=visible`; в исходниках — revert изменения.
