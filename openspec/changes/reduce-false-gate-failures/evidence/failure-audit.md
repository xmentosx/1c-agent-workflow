## По пунктам

### 1. SourceDeliveryStandPreparation — `Import-StandTestOwner` с перечнем функций
- Что защищает: ничего. Это механизм загрузки фикстуры, а не проверка. Вызов нового хелпера даёт CommandNotFound.
- Вердикт: **вывести из кода (derive)**. Общий хелпер импортирует транзитивное замыкание вызовов из корней
  (`Invoke-WorkflowDevelopmentBranchRollout`, …) внутри перечисленных файлов-владельцев и пропускает явный список
  `-Stubbed` (функции, которые тест подменяет). Если имя из `-Stubbed` не подменено, хелпер падает.
  Риск: замыкание затягивает реальную функцию, которую раньше никто не вызывал. Защита — в замыкание попадают
  только функции из названных файлов-владельцев; всё внешнее остаётся под явным контролем.
- Раньше обнаружить: после этой правки нечего обнаруживать.

### 2. SourceQualityCatalog — «fits the observed lifecycle cohort…» (57/80/84 + исключения)
- Что защищает: исходный дефект — Targeted для изменения lifecycle упирался в жёсткий лимит
  (источник 0bc3ff21, «cohort before the hard stop», лимит тогда был 1200 с). Счётчики — прокси:
  они заставляют автора добавить резерв времени для каждого нового consumer.
- Сейчас: `targetedHardSeconds` = 3600, а проверка требует только запаса `3600 − оценка > 120` при оценке около 1900 с,
  поэтому это ограничение ничего не решает. Лимит в рантайме всё равно соблюдает watchdog,
  а стоимость показывают Plan и журнал запусков («over-target» в docs/local-quality-gate.md).
  Точные счётчики дублируют каталог (`paths`/`tests`) и ломаются от любого нового легитимного consumer.
- Вердикт: **заменить счётчики производной проверкой ёмкости**. Брать реальную выборку
  `Resolve-QualityContractsForPaths` для тех же исторических путей и веса планировщика
  (`pester-timings.json` + его значение по умолчанию). Проверять, что критический путь при `targetedImplicitDefault`
  воркерах меньше `targetedHardSeconds` с запасом. Все `Should -Contain` (lifecycle должен выбирать конкретных
  потребителей) и проверки owner/paths/reuseInputPaths оставить: это настоящие контракты селекции.
  Оговорка: у 105 из 236 тест-файлов нет веса в `pester-timings.json`. Поэтому в чекпоинте нужно
  решить, какой вес по умолчанию считать консервативным (бюджеты контрактов не подходят — это лимиты, сумма выходит 50 892 с).
- Раньше обнаружить: после правки нечего; превышение лимита ловится по факту.

### 3. BootstrapUpdate — «documents the helper action catalog» (advanced-actions.md)
- Что защищает: настоящий контракт. Каталог действий, который видит агент установленного проекта,
  равен `ValidateSet` (без лишних и без пропусков).
- Вердикт: **оставить контракт, перенести проверку**. Всё равно это пятое место, где перечисляется
  каждое действие (ValidateSet, dispatch-метки, `lifecycleActions`, `actionOwners`, docs).
  Первые четыре уже сверяет `Get-QualityContractCatalog` (`scripts/quality-contracts.ps1:631-671`) — он стартует
  в первой строке check.ps1 (`scripts/check.ps1:84`), за секунды, до Pester. Нужно добавить туда сверку docs,
  чтобы одно сообщение называло все места, где нового действия не хватает.
  Опционально: блок занимает 156 строк в контексте агента, включая внутренние `release-e2e-*`. Можно сократить его до
  «полный список: `-Action help`» и выводить список из ValidateSet. Но это меняет документацию установленных проектов,
  поэтому — отдельное решение.

### 4. ProductProjectContext — `$actions.Count | Should -Be 102; $brokers.Count | Should -Be 8`
- Что защищает: ничего сверх соседнего цикла. Цикл идёт по всему ValidateSet и проверяет, что каждое действие

  в OnDemandMcp «does not reacquire the runtime lock…» (AGENTS.md требует именно такую регрессию).
- Вердикт: **убрать дублирование**. Удалить только два точных счётчика; от пустого множества защищают уже
  имеющиеся `Should -Contain` для конкретных действий.

### 5. DevelopBrokerInputScope — «retained-runtime reader inventory closed»
- Что защищает: настоящий инвариант безопасности переиспользования. `Get-DevelopColdCutoverProjection`
  (`scripts/develop-e2e-scenarios.ps1:225`) исключает тело `Get-WorkflowUpdateRootRuntimeBusyReason` из входов
  fresh-доказательства. Это корректно, только пока все вызывающие функции работают лишь при update.
  Новый вызывающий, достижимый из fresh, позволил бы ложное переиспользование.
- Почему Targeted его не выбрал: у контракта `develop-broker-input-scope` в `paths` нет lifecycle.ps1;
  он есть только в `reuseInputPaths` (`.agents/skills/1c-workflow/scripts/lib/*.ps1`). Там он инвалидирует кэш,
  но не выбирает тест. Проверено: путь lifecycle.ps1 выбирает 75 тестов, этого среди них нет. Develop гоняет полный
  инвентарь, поэтому упал там. Статическая проверка исходника, которая на деле читает lifecycle.ps1, сидит
  в процессном файле на 120 с — ровно та смесь, против которой предупреждает «Maintaining selection».
- Вердикт: **перенести в продукт по принципу fail-safe**. Тот же приём уже работает в
  `callsSha256` (`quality-contracts.ps1:382-389`): новый вызываемый → откат к широкой селекции, а не красный гейт.
  `Get-DevelopColdCutoverProjection` должна сама вычислять вызывающих функций и при любом вызывающем вне
  проверенного набора возвращать `$null` (полная привязка, сценарий выполняется, причина в диагностике).
  Тест доказывает отказ к безопасному варианту на внедрённом новом вызывающем. Тогда новый вызывающий стоит
  промаха кэша fresh, а не упавшего Develop. Если проверку оставить тестом — вынести её `It` в маленький
  статический контракт, у которого в `paths` есть lifecycle.ps1 и execution-guard-cutover.ps1 (~1 с).

## Решение по п. 8 (lock sha256 = сборка текущего Go-исходника)
Мнение: инвариант настоящий и должен выполняться уже к регистрации, но проверяться адресно и чиниться одной командой.
- Почему не только при выпуске: `source-e2e-artifact-discovery.ps1:11` ищет исходную сборку по sha256 из lock,
  `invoke-develop-e2e.ps1:87-98` квалифицирует в Develop именно её. Finalizer (`source-delivery-component.ps1:670`)
  видит по URL из lock опубликованный старый ассет как `matched` и ничего не публикует. Значит, расхождение lock и исходника
  тихо отправило бы в проекты старый бинарник, а Develop квалифицировал бы не тот артефакт.
- Что не так сейчас: проверка — побочный эффект фикстуры DevBranchLifecycle. Перепиновка вручную трогает
  4–5 мест (lock: version/releaseTag/url/sha256, compatibility.json, тесты с зашитыми releaseTag/версией — 2d801cac, 536c571a).
  Поэтому одна правка facade-self-reset упала дважды подряд.
- Предложение: (1) собственный владелец проверки — только когда в диапазоне изменены входы сборки `tools/itl-ondemand-mcp/**`;
  `_test.go`/README бинарник не меняют, поэтому проходят естественно. Сборка по Go-кэшу занимает секунды,
  проверка идёт до Pester. (2) Одна команда перепиновки, которая атомарно пишет lock и compatibility.json из результата
  `Build-ItlOnDemandMcp.ps1`; сообщение об отказе называет её. (3) Тесты читают версию/тег из lock, а не держат копию.
