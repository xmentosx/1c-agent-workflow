# Design

## Context

Мотивация и цифры — в `proposal.md` и `evidence/failure-audit.md`. На подход влияют следующие факты.

- `Get-QualityContractCatalog` (`scripts/quality-contracts.ps1`) вызывается первым в `scripts/check.ps1:84`, до любой стадии. Он уже требует точного равенства `ValidateSet`, литеральных dispatch-меток, `semanticTargeting.actionOwners` и `lifecycleActions.journey/boundary` (`quality-contracts.ps1:631-671`). Расхождение там стоит секунды, а не прогон Pester.
- Семантическая селекция уже отказывает безопасно: при изменении `callsSha256` она откатывается к широкой селекции (`quality-contracts.ps1:382-389`), а не роняет гейт. Этот шаблон и переносится на остальные инварианты переиспользования.
- `Get-DevelopColdCutoverProjection` и `Test-DevelopColdCutoverConsumers` (`scripts/develop-e2e-scenarios.ps1:180-268`) уже возвращают `$null` (полная привязка) для неизвестных версий файлов. Список вызывающих при этом проверяет только тест. Тесты переиспользования требуют reuse на живых файлах, поэтому каждая правка проверенного файла роняет гейт.
- Контракт `develop-broker-input-scope` держит `lib/*.ps1` только в `reuseInputPaths`. Изменение `lifecycle.ps1` выбирает 75 тестов, но не этот. Статическая проверка в процессном файле на 120 с упала только в Develop.
- `Get-PesterWorkloadEstimate` (`scripts/invoke-pester-shards.ps1:70`) — модель планировщика: preflight → LPT → serial. Веса берутся из `scripts/pester-timings.json`, у которого `defaultSeconds = 1.0` — это вес упорядочивания, а не оценка стоимости. 105 из 236 файлов весов не имеют. Медиана отслеживаемых весов — 50 с.
- `Get-DeliveryFailureClass` (`scripts/source-delivery-process.ps1:881`) классифицирует по регуляркам текста. Признака повторяемости у него нет.
- Develop E2E находит исходную сборку on-demand MCP по `sha256` из lock (`scripts/source-e2e-artifact-discovery.ps1:11`). Finalizer считает существующий ассет по URL из lock `matched` (`scripts/source-delivery-component.ps1:670`). Поэтому расхождение lock и исходника тихо отправит старый бинарник.

## Goals / Non-Goals

**Goals:**
- Легитимное добавление (функции, действия, consumer, вызывающего, версии файла) не роняет Targeted или Develop. Добавление, которое нарушает инвариант, по-прежнему ловится — раньше или безопасным выполнением.
- Расхождения дублированных реестров и версий находятся за секунды до Pester, одним сообщением.
- Нестабильный тест отличается от дефекта продукта в записи отказа, без ослабления гейта.

**Non-Goals:**
- Массово переписывать ~1167 существующих regex-проверок текста.
- Автоматически засчитывать проход на повторе, менять правило повторного отказа или `-RetryBlockedStage`.
- Сокращать `advanced-actions.md` до «смотри `-Action help`». Это меняет контекст агента в установленных проектах и требует отдельного решения.
- Менять квалификацию Release, стенды, контролируемый форк, установленные проекты.
- Заводить счётчик-«храповик» для regex-проверок или новый сервис/хранилище метрик.

## Decisions

### D1. Импорт фикстуры — транзитивное замыкание с явными подменами
Общий хелпер тестов принимает файлы-владельцы, корневые функции и `-Stubbed`. Он строит замыкание по `CommandAst`, ограниченное функциями этих файлов, и пропускает имена из `-Stubbed`. Если подменённое имя не определено, хелпер падает. Подмены выводятся из функций самого тестового файла (`-StubSource`); намеренно отсутствующие владельцы задаются `-Exclude`. Первым мигрирует `SourceDeliveryStandPreparation`. `SourceDeliveryProcessLifetime` переводится только вместе с распознаванием этой формы в `SourceDeliveryProofOwnership`, который намеренно сужает входы теста. Фикстуры с намеренно минимальным набором (например `LocalQualityGate`, 9996b97d) остаются явными. Остальные AST-импорты — при касании.
*Альтернатива:* dot-source всего модуля. Отклонена: у части скриптов есть код верхнего уровня, а `lifecycle.ps1` занимает >22k строк. *Альтернатива:* статическая проверка полноты списка. Отклонена: она лишь переименовывает тот же отказ.

### D2. Убрать точные счётчики там, где цикл уже выведен из источника
В `ProductProjectContext` удаляются `Count 102/8`. Цикл по `ValidateSet` и allowlist read-only действий (неизвестное действие требует lock) защищают классификацию. Полноту broker-операций уже проверяет выведенный из источника тест в `OnDemandMcp`.

### D3. Ёмкость когорты Targeted — оценка планировщика по реальной выборке
Счётчики 57/80/84 и списки исключений заменяются так: `Resolve-QualityContractsForPaths` для тех же исторических путей → `Get-PesterWorkloadEstimate` при `targetedImplicitDefault` воркерах. Для файлов без веса берётся консервативный запасной вес — медиана отслеживаемых весов (сейчас 50 с), а не `defaultSeconds`. Тест требует, чтобы оценка была меньше `targetedHardSeconds` минус запас, и при отказе называет крупнейшие вклады. Все `Should -Contain` и проверки owner/paths/reuseInputPaths остаются. Исторические измерения сохраняются как комментарии-источники, а не как утверждения.
*Альтернатива:* обязательный вес для каждого файла. Отклонена: это новый ручной реестр.

### D4. Реестры действий и версии — в валидации каталога
`Get-QualityContractCatalog` дополнительно сверяет блок `Common internal actions` в `advanced-actions.md` с `ValidateSet` (без `help`). Он собирает все расхождения и всех реестров в одно сообщение вместо первого `throw`. Тест `BootstrapUpdate` проверяет только это поведение валидатора. Версия и тег on-demand MCP в `compatibility.json` и `dependency-lock.json` сверяются там же. Тесты читают версию и тег из lock, а не хранят копии (2d801cac, 949cf47a).

### D5. Lock ↔ сборка on-demand MCP — ранняя адресная стадия и одна команда
Новая стадия `check.ps1` до Pester срабатывает, только если диапазон меняет входы сборки `tools/itl-ondemand-mcp/**`. Она собирает бинарник через `Build-ItlOnDemandMcp.ps1` (с кэшем Go) и сравнивает с `sha256` из lock. При расхождении отказ называет команду перепиновки. Команда (параметр существующего build-скрипта или соседний скрипт) атомарно записывает version/releaseTag/url/sha256 в lock и `compatibility.json`. `DevBranchLifecycleSupport` перестаёт быть неявным владельцем этой проверки и ссылается на стадию.
*Альтернатива:* проверять только при выпуске компонента. Отклонена: Develop квалифицировал бы не тот артефакт, а finalizer тихо оставил бы старый.

### D6. Инварианты переиспользования — в продукте с безопасным отказом
`Get-DevelopColdCutoverProjection` вычисляет вызывающих `Get-WorkflowUpdateRootRuntimeBusyReason` по AST. Если какой-то вызывающий вне проверенного update-only набора, проекция не применяется (`$null`, причина в диагностике). Тест `DevelopBrokerInputScope` доказывает отказ к выполнению на внедрённом новом вызывающем и сохраняет исходные сценарии переиспользования. Регрессии переиспользования для allowlist SHA (`DeliveryGoInputScope` и др.) работают на фикстурах с проверенными версиями файлов, как уже делает первый `It` в `DevelopBrokerInputScope`. Правка живого файла тогда стоит промаха кэша. Проверенный набор вызывающих остаётся в продукте как явное решение ревью: без его обновления правка безопасна, просто без переиспользования.
*Альтернатива:* перевести контракт `develop-broker-input-scope` в `paths` lifecycle.ps1. Отклонена: каждое изменение lifecycle получало бы 120-секундный процессный файл. Если по ходу реализации инвариант останется тестом, его `It` выносится в маленький статический контракт, у которого `paths` = lifecycle.ps1 и execution-guard-cutover.ps1.

### D7. Диагностический изолированный повтор Pester
После отказа стадии Pester `check.ps1` один раз последовательно запускает упавшие файлы в отдельном воркере, если позволяет остаток бюджета стадии. Результат пишется только в запись отказа: `failure.tests[*].isolatedRerun = passed|failed|skipped`, а при прошедших повторах `failureClass = nondeterministic`. Кэш шардов, доказательства и registration из повтора не создаются, гейт падает. Сообщение блокировки повторного отказа в `source-delivery-candidate.ps1` называет нестабильные тесты как направление диагностики. Само правило не меняется.
*Альтернатива:* засчитывать проход на повторе. Отклонена: это противоречит AGENTS.md (падение — доказательство дефекта, гейты не ослаблять) и скрыло бы настоящие гонки в продукте.

### D8. Нестабильные тесты в Status
`Status -StatusDetail Full` получает раздел по существующему журналу запусков: тесты с `nondeterministic` и тесты, упавшие на tree, который позже прошёл. Новое хранилище не нужно.

### D10. Замороженный план, перекрытый новой регистрацией
`PublishDevelop` с закреплённым планом берёт записи из замороженной попытки (`scripts/source-delivery-candidate.ps1:740`, `$entries = @($frozenAttempt.queue)`). Сдвиг `origin/develop` он уже ловит до гейта (`DELIVERY_REMOTE_MOVED` → `-Replan <planId>`), а перерегистрацию записи с новым принятым head — нет. 2026-11-11: исправление `210cdfd5` было принято (кандидат `5ebdccce`), но обычный `PublishDevelop` снова собрал `12814ca1` из старого `2ff47734` и около часа повторял тот же уже исправленный отказ. Помогло только `-Replan f68824bc…`.
Решение: в точке входа `source-delivery.ps1`, где обычный повтор неявно подставляет `-ResumePlan` активного плана, сравнить каждую замороженную запись с текущим `refs/itl/develop-queue/<id>/head`. Именно там, а не в супервизоре: возобновление выполняет супервизор, записанный в плане, и проверка в нём не защитила бы планы, созданные до исправления. При расхождении остановиться с `DELIVERY_QUEUE_ADVANCED` и командой `-Replan <planId>`, сохранив checkpoint и доказательства — так же, как при сдвиге remote.
*Альтернатива:* автоматический replan. Отклонена: она молча заменила бы замороженную квалификацию, а явный `-Replan` уже является штатным продолжением для сдвига remote.

### D9. Правило для проверок по тексту
В `docs/local-quality-gate.md` («Maintaining selection, cost and reuse») добавляется короткое правило по `source-check-derivation`: исполнение или AST вместо regex по коду, маркеры документов — идентификаторы, замена при касании. Сразу исправляются известные случаи: `ParserDocsBudgets` (прозовый маркер), `SourceDeliveryComponentPublication` (текст сообщения → код/поведение), `CompactRunnerWatchdog` (настенные часы → записанный дедлайн).

## Architecture checkpoint

По `docs/package-architecture.md` это изменение затрагивает доставку и селекцию гейтов.
- **Инвариант и владелец:**
  - гейт падает только на дефекте продукта, теста или окружения, а не на устаревшей копии авторитетных данных;
  - владельцы — существующие `quality-contracts.ps1` (валидация), `check.ps1` (стадии), `develop-e2e-scenarios.ps1` (проекция), `source-delivery-process.ps1` (запись отказа).
- **Новое состояние:** нет нового координатора, блокировки, очереди или постоянного состояния. Добавляются только поля в существующей записи отказа.
- **Затронуто:** Targeted/Full/Develop Pester-стадия (диагностика после отказа), выборка тестов (один статический контракт, если понадобится), переиспользование fresh-сценариев (безопасный отказ — то есть больше выполнений, не меньше).
- **Не затронуто:** Release E2E, стенды, установленные проекты, форк, клиенты, правило повторного отказа.
- **Ожидание и отмена:** изолированный повтор ограничен остатком бюджета стадии и пропускается, если остатка не хватает.
- **Совместимость:** старые записи без новых полей читаются как раньше.
- **Откат:** обычный revert исходного изменения; миграций нет.
- **Решающая приёмка:** исходные отказы (`evidence/failure-audit.md`) воспроизводятся на фикстурах и больше не роняют гейт, а исходные дефекты по-прежнему ловятся.

## Risks / Trade-offs

- [Замыкание импорта затянет функцию с побочным эффектом] → оно ограничено названными файлами-владельцами, подмены явные, отсутствующая подмена — ошибка.
- [Безопасный отказ проекции снизит переиспользование до ревью нового вызывающего] → это допустимая стоимость: холодное выполнение легитимно по `docs/local-quality-gate.md`, причина видна в диагностике.
- [Запасной вес 50 с занижает стоимость тяжёлых новых файлов] → watchdog и наблюдение `over-target` в рантайме остаются, а большие файлы получают вес при первом измерении, как сейчас.
- [Ранняя Go-сборка добавляет секунды к изменениям Go] → она запускается только при изменении входов сборки и использует кэш Go.
- [Изолированный повтор удлиняет упавший запуск] → только упавшие файлы, один раз, в пределах бюджета, и его можно пропустить.
- [Правило для regex соблюдается непоследовательно] → проверяется ревью при касании; механического «храповика» намеренно нет.

## Migration Plan

Порядок фаз, каждая — отдельная завершённая единица и одна регистрация:
- **A:** только тесты — D1, D2, watchdog из D9;
- **B:** каталог и выборка тестов — D3, D4, D5, D6;
- **C:** классификация отказов — D7, D8;
- **D:** правило в документации и оставшиеся точечные исправления из D9.

Откат — revert соответствующей единицы. Данные установленных проектов не меняются.
