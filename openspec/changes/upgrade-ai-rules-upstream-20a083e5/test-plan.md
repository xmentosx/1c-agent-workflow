## Migration acceptance (IM7, D11)

Use the existing installed update/snapshot owner and owned isolated canaries;
qualification starts from the published workflow baseline, retaining r36 and
supported old states as applicable additional cases. Do not patch installed env,
receipts or lifecycle state to manufacture readiness. Record exact old/new source,
fork, client set, root provenance, before/result setting and snapshot identity.

| Scenario | Required observation |
|---|---|
| First eligible old root/worktree: stored manual | One manual-to-essential transition and per-root receipt in the existing transaction; unrelated env bytes, business index/merge/target and saved Vanessa setting intact |
| First eligible scope: off, auto, essential or missing/empty | Retained explicit modes or essential default without unrelated rewrites; completion receipt also for no-op; invalid input retains upstream manual fallback, not migration eligibility |
| Repeated update after deliberate manual | Manual remains; no second migration, no reset based only on absent local receipt |
| New project and inherited new branch | New project defaults to essential; migrated-baseline branch inherits completion and preserves intentional manual |
| Busy/deferred old branch and stopped pending operation | Existing defer/retry/continuation applies; idle stopped root can receive only the workflow/settings update while original lifecycle target and recovery survive |
| Failure/resume and rollback | Existing owner keeps receipt/value consistent and preserves later user changes with scoped recovery; no second coordinator or recovery protocol |
| Every file-only update above | No infobase load/update, UI/native test runner, saved Vanessa, YAxUnit or Gate 6 is launched by migration |
| SkipAiRules with actual unsupported old rules | Original manual remains and no completed Q23 receipt is written; record pre-update installed support as false without treating a new helper/ref as support |
| Subsequent supporting rules install at the same workflow pin | Recorded installed support changes false-to-true; the first supported update performs the transition once, and the next update preserves a later manual |
| Missing/invalid prior manifest backup at a current package with manual | Unknown support does not become proved unsupported; manual and absent completion are retained, with the missing proof reported |
| Deferred missing/empty setting at first proved supporting rules installation | Persist essential once, matching the new upstream default; resume its applying receipt and preserve a later manual |
| Legacy parent snapshot without new policy receipt ownership | Child refuses before policy writes with UI_TESTING_POLICY_LEGACY_SNAPSHOT and clean exact source-side -Recovery update continuation; original target/snapshot/recovery remain |
| Same legacy snapshot through the new parent | Parent atomically owns added receipt paths before post-copy; resume and rollback keep value/receipt coherent and preserve original target; no child-only snapshot extension or second coordinator |
| Newer recovery executor with recorded OLD target | Q23 is skipped if the recorded package target did not own it; executor version does not manufacture policy eligibility |
| Existing/new-default dotenv with UTF-8 BOM and CRLF | Setting/default write and interruption/resume retain BOM, line endings and bytes outside the value; unrelated settings and saved Vanessa remain exact |

Late settings edits remain under existing expected-post-state guards. Preserve
the refusal and qualify the original update/recovery task through its supported
continuation; do not weaken the guard or remove the conflict to hide it.

These scenarios are acceptance requirements, not reports of executed migration.
Source-owner implementation and focused setting/receipt/snapshot checks must keep
their exact identities and limitations. They do not establish live recovery from
an old helper, complete c1 integration, managed UI execution or standalone QA.
Strict source document validation passed; tasks 12.1–12.2 still require the paired candidate. Do not mutate a live
project env now to realize a choice accepted for its future update.

## Behavioural acceptance (EV9, D4.1)

After a separately authorized important UI change reaches an owned dev/test base,
capture a fresh managed ITL Vanessa UI expected/actual trace on the exact artifact
and target. Record effective UI/provider policy and actual observed steps/result.
Prove independence from `ITL_VANESSA_TESTING`, including a retained off value;
policy migration itself is not permission to deploy or run saved suites.

Check that essential limits automatic work to important new/changed user-visible
behaviour, while auto/manual/off retain their upstream meanings and the broader
no-UI instruction retains precedence. An unavailable or unauthorized route leaves
the scenario unverified with a precise prerequisite; an explicit permitted UI
request blocks at that prerequisite. Static checks, scenario files or a generic
saved-suite pass cannot replace real interactive evidence. The repeated test-fix
loop remains opt-in. Standalone QA is not implemented or qualified by these runs.

Reuse existing proof only for unchanged owner inputs and an explicitly applicable
acceptance contract. Record new identity and limitations rather than promoting
historical 9ec/source/host evidence to c1 qualification. Close the new tasks only
from actual results; preserve the previous failures, checkbox history and all
remaining unverified client/provider variants.
