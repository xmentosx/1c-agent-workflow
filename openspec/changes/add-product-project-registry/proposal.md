# Proposal

## Why

Разработчику нужен один выбор проекта из каталога, который определяет продукт, автоматически подключает настроенные MCP и задаёт связи СППР/Mantis, сохраняя локальные настройки и возможность начать работу с незаполненными интеграциями. Техническая инвентаризация выявила, что существующий реестр публикует только MCP endpoints, а объявленная в настройках область данных ещё не гарантирует её соблюдение серверами; факты и ограничения закреплены в [inventory.md](inventory.md).

## What Changes

- До первого выпуска функции каталога обязательно наполнить и подтвердить выпускной набор продуктов, проектов, их настроек и карту основной функциональности. Минимальный seed G2 не заменяет это условие; состав, доказательства и связь с первым выпуском памяти определены в design и AC-36–38.
- Добавить отдельный каталог в существующий Git-реестр: `catalog.json` для продуктов, проектов, источников и связей; `product-relations.json` для настраиваемого происхождения, состава и зависимостей продуктов. Сохранить `registry.json` schema v2 под управлением существующего издателя endpoints.
- Ввести стабильные разные `productId` и `projectId`, один базовый продукт проекта и необязательный профиль для редких фиксированных версий/вариантов. Обычная работа использует актуальную конфигурацию без обязательного профиля версии.
- Заменить при инициализации вопрос «PM4 или PM5?» выбором проекта из каталога. Для заполненной записи автоматически определять продукт и подключать все настроенные проектные и общие MCP без отдельных вопросов о серверах, hosts, источниках или подтверждения каждого подключения; учитывать явные overrides/disabled.
- Описать применимость знаний между КОРП, ПРОФ и составными продуктами через именованные области функциональности, зависимости, условия и доказательства. Добавить необязательное `knowledgeAreas.<area>.memoryHomeProductId`: одно каноническое место общего продуктового знания, отдельно от проекта возникновения и права чтения. Агент использует известную карту; человек подтверждает новые/изменённые общие правила, включая home.
- Настраивать роли `code`, `graph`, `productDocs` независимо: `inherit`, `own`, `disabled`; приоритет — локальное переопределение → проект → продукт/выбранный профиль. Проверять реальное соблюдение выбранного источника на стороне MCP.
- Связывать проект с одним проектом СППР и несколькими проектами Mantis, отдельно задавая область поиска и маршруты создания ошибок/развития. Использовать существующие внешние объекты и существующий Mantis writer.
- После заполнения и проверки сразу сохранять новый проект в Git-реестре при наличии прав записи; иначе выдавать готовую заявку без её отправки. Обрабатывать конкурентные изменения без перезаписи чужих данных.
- Разрешить незаполненные СППР/Mantis/MCP при создании локального проекта с понятным статусом отложенного. Дополнительные вопросы о настройках задавать только при создании или осознанном дополнении неполной записи, не повторять уже заполненное. Различать отложенную настройку, намеренное отключение и ошибку предусмотренного подключения; готовность интеграций не определяет готовность локального проекта.
- При запуске обычных команд workflow в привязанном проекте автоматически проверять реестр и применять изменения наследуемых MCP, СППР/Mantis связей и маршрутов до основной фазы команды. Сохранять локальные overrides, показывать краткое «как было → как стало»; при конфликте спрашивать пользователя. Использовать трёхстороннее сравнение и существующего владельца настроек/recovery, без фоновой службы и отдельного подтверждения неконфликтных изменений. Справка, read-only диагностика и восстановление остаются доступны без автоприменения; при недоступном реестре валидный applied snapshot сохраняет локальную работу.
- Для старой установки после первого успешного интерактивного обновления с поддержкой каталога предложить выбрать/создать проект либо «позже». Сохранить defer в прежней ignored selection; unattended/отсутствие ответа не назначают проект и не портят успешное обновление пакета. Первая ассоциация показывает preview, сохраняет custom settings и имеет owned recovery без повторного init/reset; включение памяти остаётся отдельным opt-in.

## Capabilities

### New Capabilities

- `product-project-registry`: каталог, стабильная идентичность, согласованный Git-снимок, проверка ссылок и добавление проектов.
- `product-knowledge-applicability`: декларативные отношения продуктов, каноническое место общего знания и проверяемая применимость с участием агента и человека; чистый контракт для внешних потребителей памяти.
- `registry-source-binding`: независимые роли источников, техническая идентичность, проверяемые области BookStack/СППР/Mantis и маршрутизация задач.
- `registry-project-configuration`: выбор при bootstrap, отложенные интеграции, автоматическое обновление наследуемых настроек при запуске команд, разрешение конфликтов, offline, совместимость и восстановление.

### Modified Capabilities

Отсутствуют: `openspec list --specs --json` не содержит основных спецификаций. Связанные незавершённые changes перечислены в [inventory.md](inventory.md#связанные-постановки); их требования и файлы эта постановка не переписывает.

## Impact

Checkpoint G3 одобрен пользователем; source срезы G3.0–6 реализованы и зарегистрированы в границе owner fixtures. После failed server capabilities 2026-10-19 пользователь отдельно разрешил обновить BookStack/Mantis/СППР на dev-ermakov. На 2026-10-20 все три attested G3 builds активны; 29 live scope/compatibility controls и десять исходных Python suites прошли. G3.7/AC-39 целиком не приняты: full code/graph binding, installed/client/platform и startup matrix остаются открытыми. Результаты и продолжение — test-plan. G4, миграция действующих установок и публикация workflow/каталога запрещены текущим запросом. Функциональная готовность G3 отделена от installed canary и первого выпуска, для которого AC-36–38 обязательны. Memory change потребляет тот же план/контекст, не реализует свой updater.

Владельцы изменений: ITL bootstrap/lifecycle и MCP helpers, шаблон `project.json`, существующий writer клиентских MCP, издатель host registry и серверы BookStack/СППР/Mantis. Точки расширения и границы ответственности описаны в [design.md](design.md); этапы — в [tasks.md](tasks.md), доказательства приёмки — в [test-plan.md](test-plan.md).

Продолжение квалификации 2026-10-20 расширило Code/Graph, client-file и startup proof. Выявленный native PM5 hidden-console blocker затем исправлен у общего input owner: [повтор исходного update](test-plan.md#исправление-скрытой-консоли-и-повтор-pm5-2026-10-20) из прежней sealed capsule завершился штатно без association/consent/defer и вмешательства в console. Исходный failed terminal/copy сохранён. Общий G3 не принят: остальные installed/client/platform критерии остаются открытыми. G4, миграция рабочих проектов и публикация не начинаются.

Не входят: система прав и сопоставление учётных записей ПК/терминального сервера; сервис памяти и автоматический классификатор знаний; создание внешних проектов, индексов и новых сервисов; изменение controlled fork; автоматическое обновление исходной конфигурации, публикация или развёртывание. Существующие серверные разрешения сохраняются. Новые данные подключаются постепенно и явно; непомеченные локальные проекты сохраняют прежнее поведение.

Связанный потребитель — `add-scoped-cognee-memory`: он переводит canonical product IDs в штатные datasets и проверяет grants/актуальность записей. Реестр выдаёт только business IDs, применимость и ревизию правил, без native dataset IDs, четвёртой проектной MCP-роли или собственного endpoint Cognee. Отсутствие home допустимо для каталога и обычной работы; потребитель не обобщает такой кандидат автоматически. Реализация/приёмка памяти не становятся зависимостью выпуска реестра.

Общий порядок G0–G6 и первый переход согласованы 2026-10-19 в design обоих changes: native Cognee Q1–Q7 обязательны до зависимой разработки памяти, но могут идти параллельно основе/установленному каталогу и не задерживают registry-only выпуск. Сам план не является разрешением проверок, реализации, миграции или публикации; фактически разрешённые и выполненные срезы указаны отдельно.

Исходный planning запрос разрешал только документы OpenSpec; последующий G2 apply указан в конце этого proposal. Архитектурный checkpoint для будущего installed-state изменения вынесен в [design.md](design.md#архитектурный-checkpoint); реализация и её приёмка требуют следующего явного запроса. План не является разрешением менять живой реестр, устанавливать MCP или публиковать пакет.

Уточнение 2026-10-19: конкретный G2.1–5 и граница handoff описаны в design. Чистый G2 даёт один reader/resolver/publisher contract без installed writes; пользовательское Git save, migration/startup и client reload относятся к G3. Memory G4 требует qualified G2 interface, native G1 и отдельно одобренный D9. Подготовленный D9 не блокирует независимую основу каталога; на том этапе код G2 и G4 не был начат; фактический G2 apply зафиксирован ниже.

Предыдущий apply G2 2026-10-19: пользователь одобрил D9, разрешил только G2 и подтвердил PM5 КОРП как пилот. G2 реализован/проверен на актуальном изолированном source base; evidence — test-plan. На том этапе G3/installed migration, память G4, публикация каталога/пакета и изменение controlled fork не были разрешены. Последующий source G3 apply и квалификация имеют отдельное разрешение, указанное выше; прежние planning-only ограничения не отменяют его.


Первый source срез G3 после одобрения checkpoint реализовал Git authoring и server scope/metadata contracts; последующие G3.3–6 и native квалификация описаны в test-plan. Полный installed путь не принят. G4 и миграция действующих установок явно отложены; публикация и обязательное выпускное наполнение пока не выполнены.
