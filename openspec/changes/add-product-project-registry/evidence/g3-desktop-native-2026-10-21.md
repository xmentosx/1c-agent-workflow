## Нативные результаты Kilo и семантический failure

Один приватный Ask session, две пользовательские реплики, три tool calls с отдельным **Allow once**, без постоянного auto-approve. В native session записаны только разрешённые read tools; shell/filesystem/edit/reindex/subagent tools не вызывались. Оба положительных чтения происходят из actual VS Code extension session с точным исходным directory, а не из отдельного `kilo serve`, direct MCP или переупакованного Codex RPC.

Приватный VS Code/extension процесс унаследовал тестовый `KILO_EXPERIMENTAL_MCP_APPS=1`; actual reads шли обычным Ask model-tool путём, experimental HTTP call-tool route в этом срезе не использовался. Global/default настройки не менялись. GUI/model repeat с flag off не выполнялся и не объявляется принятым по этому варианту.

- Code `stats`: `status=success`, полезные коллекции/индексы; raw output 10 858 UTF-8 bytes. Native IDs/generation поля не превращаются в business product ID или новое требование index stamp.
- Исходный canary prompt ошибочно указал `mcp_namespace` как аргумент `get_graph_project_status`; здесь namespace задаётся source scope/результатом. Модель дополнительно отправила строки `generation="null"`, `operation_id="null"`. Реальный ответ — **`generation_not_found`**, хотя native part имеет `status=completed`. Это корректный отказ для указанного поколения, не доказательство отсутствующего/недоступного `pm5corp`. Ошибка исходного prompt, фактический input, ответ и неточный пересказ модели сохранены. Namespace `null` в error context не принят за успешную привязку.
- Отдельный положительный контроль `list_graph_projects({})` вернул ровно один доступный `pm5corp`, namespace `default`, `ready`, `is_accessible=true`. Этот success не переписывает failed status call. `active_generation=null`/`ingestion_state=inherited` сами по себе не являются блокером действующей registry-only модели; Code/Graph producer/manifest patches не требуются.

Client/model argument compatibility для status call остаётся непроверенной; backend не менялся ради принятия строки `"null"`. Future acceptance использует корректную native schema и полезный scoped result; HTTP/part completed или модельный текст по отдельности не являются pass.

Никакого fallback на default project, изменения registry IDs, прямого MCP вместо frontend или внедрения неподдерживаемого route/state для pass. [Desktop troubleshooting](https://docs.opencode.ai/docs/troubleshooting/) полезен для следующей диагностики; текущий blocker основан на сохранённых native receipts.

Первый OpenCode запуск не создал renderer/logging в свежем длинном профиле с неполными home known folders. Отдельный диагностический профиль был короче и содержал `home/AppData/Roaming`/`Local`; тот же EXE и исходный root запустили renderer/backend. Изменились **два** параметра fixture, поэтому MAX_PATH/конкретная первопричина не доказаны, первый запуск не стал pass. Профили, логи и исходный workload сохранены.
