## Сквозной установленный canary

На заранее определённом разрешённом stand, через существующие bootstrap/update/lifecycle entrypoints:

1. Для заполненных записей PM4 и PM5 выбрать только проект из каталога и заполнить обязательные локальные параметры. Записать последовательность вопросов: отдельного PM4/PM5, mandatory version profile и per-MCP опроса нет. Настроенные code/graph/docs и общие MCP подключаются автоматически, явные disabled/overrides соблюдены; безопасные вызовы подтверждают ожидаемые bindings.
2. Создать внешний проект на том же продукте с неполными СППР/Mantis/MCP связями. Продолжение подключает настроенное, локальная часть завершается, status показывает отложенное без обязательного опроса о каждой интеграции. Отдельно выбранное дополнение спрашивает только неизвестное. Обязательная неполнота и сбой предусмотренного автоматического подключения по-прежнему дают исходную ошибку.
3. Добавить проект в временный разрешённый Git-реестр; проверить путь read-only прав с готовой заявкой и одинаковым стабильным ID. Не выполнять эти проверки записью в production registry.
4. Назначить собственный code, общие СППР/Mantis связи и ручной disabled документации. Изменить наследуемые Mantis scope/routes и graph MCP в тестовом каталоге; запустить обычную команду workflow без отдельного update. Проверить автоматическое применение до основной фазы, краткий diff и отсутствие вопросов при сохранённых overrides, custom MCP/втором client/другом worktree. Отдельно полностью переопределённый локальный список Mantis не должен объединяться с общим.
5. Создать неоднозначный конфликт manual managed edit vs registry. Проверить вопрос с тремя значениями до записи, все варианты ответа и non-interactive запуск без решения. Затем прервать начавшийся apply после client A и изменить client B извне: основной command path ещё не выполнен, status/marker честны, pinned resume/owned restore сохраняют чужую правку даже при новом remote tip. Это исходная topology восстановления.
6. Запустить обычную команду offline по валидному applied snapshot в пределах deadline; проверить freshness, no-op counters и вложенные calls. Создать ветку обычным lifecycle и проверить rematerialized root. Отдельно проверить opt-in legacy PM4/PM5, несовместимый downgrade/restore и доступные help/status/recovery paths без автоприменения.
7. Для опубликованной тестовой версии серверов выполнить read-only BookStack view controls, СППР UUID/exact-link и Mantis multi-project search. Если сервер ещё не развёрнут, отметить live критерий невыполненным, а не заменить его fixture proof.
8. На выделенных legacy PM4/PM5 установках пройти package update → choose/create/later → preview/association. Проверить сохранённый defer, поздний явный выбор, unbound unattended/нет ответа, отсутствие повторного выбора bound проекта, custom settings и partial recovery без reset. Результаты package/association показываются раздельно. Memory step проверить выключенным fixture; его реальный opt-in/начальный cycle и paired cost относятся к memory G5 и не нужны для registry-only выпуска.

Фактическое создание обращения Mantis не требуется для приёмки каталога/маршрутизации: используется доказанный existing writer contract и fixture. Если потребуется доказать live запись, это отдельный разрешённый тест с выделенным Mantis project и проверкой operation ID; постановка не разрешает запись в рабочие проекты.
