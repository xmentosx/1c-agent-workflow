# Spec Delta

## Purpose

Связать бизнес-проект с фактическими источниками MCP и внешними объектами так, чтобы выбор области действительно соблюдался сервером, а поиск и создание задач использовали явные проектные настройки.

## ADDED Requirements

### Requirement: Независимые роли и приоритет настроек

Система SHALL разрешать `code`, `graph`, `productDocs` независимо в состояниях `inherit`, `own`, `disabled`, с приоритетом локальное переопределение → проект → продукт с необязательным выбранным профилем. `inherit` SHALL продолжать разрешение на следующем уровне; `own` SHALL задавать полный binding роли; `disabled` SHALL прекращать наследование. Остальные MCP SHALL сохраняться общими, включая Cognee при его отдельном qualified opt-in: `memoryHomeProductId` выбирает продуктовую область данных, SHALL NOT вводить проектное наследование endpoint или четвёртую роль. Отсутствие binding SHALL NOT неявно выбирать произвольный источник.

#### Scenario: Разные code и graph
- **WHEN** проект задаёт собственный code, наследует graph, а локально отключена документация
- **THEN** разрешаются три независимых результата; code `configId`/host не копируются в graph, документация не включается обновлением продукта

#### Scenario: Внешний проект без своего индекса
- **WHEN** выбран собственный code, но его binding ещё не заполнен
- **THEN** роль требует настройки без silent fallback; пользователь может явно выбрать типовой source как основной с назначением «базовый продукт», но он не объявляется собственным кодом проекта

### Requirement: Проект и источник описаны раздельно

Каталог SHALL явно задавать бизнес-происхождение источника Code/Graph: productId и, для исходников конкретного проекта, projectId. Выбранный binding SHALL обозначать назначение источника в проекте: собственный проект, базовый типовой продукт или справочный продукт. Эти данные и ограничения SHALL задаваться в бизнес-реестрах человеком через существующий authoring path, SHALL NOT определяться по имени сервера, версии, совпадению native ID или автоматическим сканированием функциональности. Режим подключения `own` SHALL означать явно выбранный sourceId, SHALL NOT сам доказывать принадлежность исходников проекту.

Продукт источника SHALL иметь право отличаться от продукта проекта при явно разрешённом использовании и заданных ограничениях. Система SHALL сравнивать подключение с выбранным source binding, SHALL NOT требовать равенства source productId и project productId. Состав и общие различия продуктов SHALL принадлежать product-relations/knowledgeAreas; собственные доработки и правила проекта SHALL принадлежать записи проекта и её первичным ссылкам, без копии всей карты продукта.

#### Scenario: Доработанный проект использует типовой MCP
- **WHEN** проект основан на PM5 КОРП с подтверждёнными собственными доработками, а роли явно указывают типовой PM5 КОРП как базовый источник
- **THEN** настройка допустима; контекст различает проект и типовой источник, а наличие/отсутствие клиентской доработки не выводится только из MCP типового продукта

#### Scenario: ПРОФ использует источник КОРП
- **WHEN** для PM5 ПРОФ явно выбран MCP типового PM5 КОРП как справочный источник
- **THEN** настройка не отклоняется из-за различия продуктов; доступность найденной функции определяется подтверждённой картой ПРОФ, исключённые области КОРП не объявляются доступными в ПРОФ

#### Scenario: Принадлежность источника не описана
- **WHEN** endpoint существует, но его бизнес-происхождение или разрешённое назначение в проекте неизвестно
- **THEN** контекст показывает конкретный пробел без угадывания по строке версии или названию; заполнение идёт через существующий каталог, независимая локальная работа сохраняется

### Requirement: Registry является источником сведений о конфигурации MCP

Название и версия конфигурации, сведения о состоянии/времени индексации и имеющиеся fingerprints SHALL читаться из существующего registry.json в том же Git snapshot, что каталог и отношения. Система SHALL использовать действующий путь индексации/публикации этих полей; SHALL NOT требовать доработки Code/Graph, доступа к их исходникам, нового sourceKey, manifest активного индекса либо generation/revision stamp в каждом ответе для приёмки G3 или памяти.

Версия из registry SHALL обозначаться как версия подключённого MCP-источника с происхождением из registry, SHALL NOT автоматически становиться версией локального доработанного проекта или гарантией побайтного равенства его исходников. Неизвестные/устаревшие поля SHALL сохранять свой статус и дату; недостающее поле SHALL NOT угадываться из MCP/SDK version. Уже доступные сведения о revision допустимы как дополнительное evidence, их отсутствие само по себе SHALL NOT делать источник неподтверждённым или все выводы из него кандидатами. Обычная работа SHALL NOT требовать профиля каждой версии; явные ограничения проверяются по имеющимся registry данным без обязательного нового серверного протокола.

#### Scenario: Публикация после индексации
- **WHEN** существующий publisher опубликовал сведения о конфигурации и индексации
- **THEN** после штатного обновления snapshot контекст показывает эти поля registry и их происхождение без чтения внутренних index manifests или пересчёта исходников

#### Scenario: Graph не сообщает ревизию активного индекса
- **WHEN** выбранный Graph доступен в ожидаемой native области, registry содержит сведения о его конфигурации, но API не сообщает generation/hash каждого ответа
- **THEN** отсутствие этих дополнительных полей и исходников Graph не является блокером G3; используются опубликованные сведения без заявления точной ревизии конкретного ответа

### Requirement: Проверяемая техническая идентичность

Binding SHALL различать бизнес-проект, бизнес-происхождение источника и технические host/server/configuration/endpoint/native selectors. Проверка востребованного подключения SHALL использовать штатный handshake и безопасное функциональное чтение в выбранной области через существующий MCP/client owner. URL/config/applied marker SHALL NOT заменять фактическую активацию в клиенте. Native namespace/project SHALL проверяться там, где API их поддерживает; отсутствие namespace у Code или одинаковые внутренние IDs SHALL NOT требовать доработки сервера или нового идентификатора: источники различаются полным registry binding.

Expected подключение SHALL происходить из одного applied snapshot с overrides/disabled. Неверный фактический endpoint или native selector SHALL исключаться из evidence выбранного источника с продолжением через прежний sync/reload и повторное чтение. Явно выбранный КОРП для ПРОФ или типовой продукт для доработанного проекта SHALL NOT считаться техническим mismatch. Routine startup/status и pure resolver SHALL NOT получать новые probes, состояние readiness, services, tools или обязательное чтение всего каталога. Недоступность вспомогательного MCP SHALL NOT блокировать независимые init/update/branch/restore; deploy/reindex/смена продукта SHALL NOT выполняться автоматически.

#### Scenario: Одинаковый внутренний ID
- **WHEN** два endpoints возвращают одинаковый внутренний Code ID
- **THEN** они остаются разными источниками по полному registry binding; новый sourceKey или серверный патч не требуются

#### Scenario: Неожиданный namespace
- **WHEN** клиент фактически обращается к другому endpoint/native scope, чем явно выбран для роли
- **THEN** подключение не объявляется готовым; показывается ожидаемая и фактическая область без подмены соседним источником

#### Scenario: Настройки записаны, клиент использует старое подключение
- **WHEN** новый endpoint записан, а открытый клиент не выполнил reload
- **THEN** активация остаётся неподтверждённой до native вызова; штатный reload и повторное чтение проверяют выбранный source, а не равенство продукта source продукту проекта

### Requirement: Соблюдение области документации

Выбранная роль `productDocs` SHALL обеспечивать одну и ту же серверную область для cache, semantic, live fallback и чтения страницы. Стабильные selectors SHALL валидироваться; неизвестный selector SHALL NOT расширять поиск до всех документов. При отсутствии серверного механизма область SHALL показываться неподтверждённой, а глобальный endpoint SHALL NOT молча заменять выбранный.

#### Scenario: Несуществующая книга
- **WHEN** поисковый запрос содержит несуществующий ID/selector книги
- **THEN** сервер возвращает понятную ошибку либо пустую область по документированному контракту и не возвращает чужие страницы через live fallback

#### Scenario: Чтение чужой страницы в выбранном источнике
- **WHEN** клиент выбранной области запрашивает page ID вне её состава
- **THEN** область соблюдается и при чтении; глобальная доступность страницы в BookStack не делает её частью выбранного источника

### Requirement: Связи с существующими СППР и Mantis

Проект SHALL поддерживать необязательную связь с одним проектом СППР и списком проектов Mantis внутри явно указанных установок систем. Каталог SHALL ссылаться на существующие native IDs и показывать доступные проверенные названия. Регистрация связи SHALL NOT создавать внешние проекты, расширять сбор индекса или изменять серверные права. Общие MCP SHALL позволять явное чтение известного объекта/обращения без заполненной проектной связи.

#### Scenario: Ещё не заполнена СППР
- **WHEN** локальный проект не имеет связи СППР, но разработчик указывает существующий объект явно
- **THEN** доступное серверу чтение разрешается, а отсутствие связи не блокирует локальную работу

#### Scenario: Ссылка на неиндексируемый проект
- **WHEN** запись ссылается на существующий проект СППР вне текущей области коллектора
- **THEN** система сообщает недоступность данных и необходимую отдельную настройку; каталог не запускает сбор автоматически

### Requirement: Поиск Mantis по нескольким проектам

Mantis SHALL поддерживать явный список project IDs как одну область поиска, сохраняя совместимость скалярного фильтра и прежнего поиска без фильтра по доступным проектам. Область SHALL применяться до ограничения кандидатов, во всех способах поиска и на всех страницах; ответ SHALL честно показывать ограничение полноты. Пустая область SHALL NOT означать поиск по всему Mantis.

#### Scenario: Ошибки и развитие
- **WHEN** область поиска содержит проекты 699 и 815
- **THEN** результаты относятся к объединению этих двух проектов, без третьих проектов; cursor продолжает ту же область

#### Scenario: Совпадение за пределами глобальных кандидатов
- **WHEN** релевантная задача выбранного проекта находится за первыми 10000 глобальными кандидатами
- **THEN** фильтрация до ограничения сохраняет её доступность; результат не объявляет пустоту проекта из-за чужих кандидатов

### Requirement: Маршрутизация создания и точные связи

Настройки SHALL различать область поиска Mantis и целевой проект по назначению задачи, например `bug`, `feature`, `improvement`. При отсутствии или неоднозначности маршрута создание SHALL требовать явный целевой проект и использовать существующий writer/idempotency contract. Связь объекта СППР с задачей SHALL подтверждаться точным полем/ссылкой, а сходство текста SHALL обозначаться только как рекомендация.

#### Scenario: Разные цели создания
- **WHEN** `bug` направлен в 699, а `feature` в 815
- **THEN** создание использует назначение задачи и правильный target; первая запись списка поиска не считается универсальным primary project

#### Scenario: Нет маршрута
- **WHEN** пользователь хочет создать задачу, но её назначение не сопоставлено проекту
- **THEN** требуется явный target для этой операции; другие действия workflow продолжают работать

#### Scenario: Точная ссылка СППР
- **WHEN** объект имеет `итлКодMantis=59095`, а семантический поиск также нашёл похожую другую задачу
- **THEN** только 59095 показывается фактической связью; другая задача помечается похожей
