# Spec Delta

## Purpose

Создавать и обновлять локальный проект по выбранной записи общего каталога, позволяя отложить необязательные интеграции и сохраняя пользовательские настройки, совместимость и проверяемое восстановление.

## ADDED Requirements

### Requirement: Отдельный checkpoint G3 и совместимый переход

Реализация installed binding/recovery/startup G3 SHALL требовать отдельно одобренной границы checkpoint и разрешения соответствующего apply; approval D9 памяти или completed G2 SHALL NOT заменять их. Один существующий MCP/client owner SHALL владеть local plan до первой записи, receipts, applied marker и pinned resume/owned restore; dispatcher SHALL использовать этот owner после прежнего lifecycle admission. Новая общая очередь/lock family/coordinator SHALL NOT требоваться. Capability SHALL проверяться до первой binding записи. Штатный downgrade к неподдерживающему пакету SHALL сначала выполнить совместимый owned restore либо остановиться до замены helper; исторический permissive parser SHALL NOT объявляться проверяющим новые поля. Legacy unbound SHALL сохранять прежнее поведение. Наполнение AC-36–38 SHALL оставаться обязательным до выпуска, а не новым startup barrier.

#### Scenario: Документ checkpoint готов
- **WHEN** G2 завершён, D9 согласован и G3 checkpoint подготовлен, но G3 apply не разрешён
- **THEN** допускается только проработка документов, G3/G4 и миграция установок не начинаются; критерии runtime остаются открытыми

#### Scenario: Downgrade активной привязки через updater
- **WHEN** штатный updater готовится заменить поддерживающий helper старым пакетом при активном binding
- **THEN** сначала подтверждается совместимый owned restore либо замена останавливается с продолжением через прежнего owner; чужие settings и данные сохранены

### Requirement: Выбор проекта вместо PM4 или PM5 до unattended

Bootstrap SHALL заменить вопрос «PM4 или PM5?» выбором проекта из каталога и определять базовый продукт/семейство по выбранной записи. Для заполненной записи он SHALL автоматически подключать все настроенные проектные и общие MCP с учётом overrides/disabled, без отдельных вопросов о каждом MCP, provider, host, конфигурации источника или подтверждении подключения. Выбор проекта и обязательные локальные параметры SHALL быть определены до unattended/download/1C/Git baseline; отдельный выбор профиля версии SHALL NOT быть обязательным.

Дополнительные вопросы об интеграциях SHALL возникать только при создании новой записи либо осознанном дополнении недостающих данных неполной записи, не повторяя заполненные значения. При продолжении с неполной записью система SHALL подключать настроенное, показывать отсутствующее как отложенное и сохранять возможность локальной работы; стандартный bootstrap SHALL NOT превращать это в обязательный опрос о каждом MCP. Отложенная интеграция SHALL NOT препятствовать готовности локального проекта при выполненных обязательных локальных проверках; поздние скрытые вопросы SHALL NOT появляться.

#### Scenario: Заполненная запись проекта PM4 или PM5
- **WHEN** разработчик выбрал заполненную запись каталога с базовым продуктом PM4 либо PM5
- **THEN** семейство определяется из записи, настроенные проектные и общие MCP подключаются автоматически; повторного вопроса «PM4 или PM5?» и отдельных вопросов о MCP нет

#### Scenario: Намеренное отключение в заполненной записи
- **WHEN** выбранный контекст содержит явно отключённый MCP либо сохранённый локальный override
- **THEN** автоматическая настройка соблюдает его без повторного вопроса и без включения отключённого сервера

#### Scenario: Новый проект без внешних связей
- **WHEN** разработчик выбрал неполную запись проекта либо создал новую, заполнил обязательные локальные параметры и продолжил с отложенными СППР/Mantis/MCP
- **THEN** настроенные MCP подключаются, проект создаётся через обычный lifecycle, список отложенного и действия дополнения видны без обязательного опроса о каждой интеграции и без нового общего состояния draft

#### Scenario: Дополнение неполной записи
- **WHEN** разработчик отдельно выбирает создание новой записи или заполнение отсутствующих интеграционных данных
- **THEN** вопросы касаются только недостающих значений, уже известный продукт и готовые MCP не запрашиваются повторно

#### Scenario: Случайно неполный выбор
- **WHEN** отсутствует обязательный выбор проекта/его базового продукта либо обязательный локальный параметр
- **THEN** неполнота выявляется до unattended по существующему контракту, без позднего вопроса или молчаливого defer

### Requirement: Агент получает различия проекта и MCP-источника

Preview и on-demand context SHALL из одного applied snapshot показывать выбранный проект/базовый продукт, краткие собственные доработки, происхождение и назначение каждого настроенного Code/Graph source, название/версию конфигурации и сведения об индексации из registry, применимые ограничения/ссылки. Различие продуктов SHALL быть допустимым при явной настройке источника по registry-source-binding. Проектная версия SHALL NOT выводиться из версии типового MCP. В context SHALL входить только выбранная проекция и нужные правила; вся карта функциональности, документация и список всех проектов SHALL NOT добавляться в always-on prompt. Новые MCP probes при startup/обычном чтении context SHALL NOT появляться.

#### Scenario: Предпросмотр ПРОФ с источником КОРП
- **WHEN** пользователь выбирает PM5 ПРОФ с явно настроенным типовым MCP КОРП
- **THEN** preview показывает оба продукта и ограничение применимости, не требует заменить MCP или продукт проекта и не скрывает отличия

#### Scenario: Доработки проекта меняются
- **WHEN** существующий updater применяет новые подтверждённые ограничения проекта или новую версию источника из registry
- **THEN** агент получает новый selected context с сохранением overrides/disabled и прежнего recovery; бизнес-ID, настройки памяти и исходные доказательства не меняются автоматически

### Requirement: Отложено, отключено и ошибка различаются

Результат SHALL различать желаемое состояние роли и её вычисленную готовность: отложено/не заполнено, намеренно отключено, готово, ошибка предусмотренного подключения. Defer SHALL NOT превращаться в постоянное `disabled` или перезаписывать ручное отключение. Сбой настройки, предусмотренной выбранным контекстом для автоматического подключения либо явно начатой пользователем, SHALL сохранять обычный путь диагностики/восстановления, без молчаливой деградации.

#### Scenario: Наследуемый источник появился позже
- **WHEN** желаемое состояние `inherit`, ранее не было binding, а каталог получил его
- **THEN** при следующей обычной команде workflow источник подключается автоматически, если нет локального отложенного применения или конфликта; причина прежнего отсутствия сохраняется в provenance, ручной `disabled` остаётся отключённым

#### Scenario: Автоматическое подключение завершилось сбоем
- **WHEN** выбранный контекст предусматривает подключение настроенного endpoint, но он не отвечает
- **THEN** операция сообщает ошибку и продолжение через существующего владельца; она не объявляет настройку успешно отложенной

### Requirement: Автоматическое обновление наследуемых настроек при запуске команд

Startup SHALL иметь одну remote tip/fetch попытку с общим network deadline 10 s на top-level operation; nested/broker SHALL переиспользовать закреплённый контекст без повторного check/guard expansion. При timeout/ошибочном новом snapshot и валидном applied baseline независимая основная задача SHALL продолжаться на прежней revision с WARN актуальности. Help/status/read-only preview и pinned recovery SHALL оставаться доступны. Пробы изменённого источника/основная операция и существующее ожидание lifecycle lock SHALL сохранять отдельные owner budgets; Mantis search SHALL NOT входить в metadata startup. Engineering цели no-op overhead из design SHALL измеряться отдельно и SHALL NOT становиться runtime FAIL.

Для привязанного к каталогу проекта обычная верхнеуровневая команда workflow SHALL перед своей основной фазой автоматически проверять актуальность выбранного контекста и применять неконфликтные изменения наследуемых настроек, включая MCP, СППР/Mantis связи, области поиска и маршруты создания. Отдельный запуск команды обновления или подтверждение каждого изменения SHALL NOT требоваться. Система SHALL выполнять трёхстороннее сравнение ранее применённого снимка, текущего локального состояния и нового контекста, показывать краткое «как было → как стало» и основание Git. Полный preview SHALL оставаться доступным по запросу.

Локальные overrides, ручной `disabled`, неуправляемые MCP, другие clients/worktrees и посторонние настройки SHALL сохраняться. Явное переопределение SHALL NOT считаться конфликтом только из-за изменения наследуемого значения; новые элементы SHALL NOT неявно добавляться в целиком переопределённый локальный список Mantis. Обновление SHALL NOT менять базовый продукт или исходную конфигурацию 1С неявно.

Справка, просмотр статуса, read-only диагностика/preview и продолжение/восстановление прерванной операции SHALL оставаться доступны без автоприменения. Вложенные вызовы одной команды SHALL использовать один закреплённый контекст, без повторного старта синхронизации. Фоновая служба SHALL NOT требоваться. Если эффективный контекст не изменился, клиентские файлы SHALL NOT переписываться, а дорогостоящие проверки неизменённых MCP SHALL NOT повторяться только из-за запуска команды.

#### Scenario: В реестре изменились проекты Mantis и MCP
- **WHEN** общий каталог изменил наследуемые связи Mantis и MCP выбранного проекта и пользователь запускает обычную команду workflow
- **THEN** до основной фазы команды изменения применяются автоматически и отражаются в её контексте без повторного init и отдельного подтверждения, с кратким отчётом об изменениях

#### Scenario: Локальный code override
- **WHEN** общий продукт меняет code, а проект имеет локальный собственный code
- **THEN** автоматическое применение сохраняет override без вопроса, обновляя только наследуемые значения и происхождение

#### Scenario: Локальный список Mantis
- **WHEN** проект локально переопределил список Mantis, а общий реестр изменил исходный список
- **THEN** локальная область сохраняется целиком, остальные неконфликтные наследуемые настройки обновляются без вопроса

#### Scenario: Изменился только heartbeat publisher
- **WHEN** Git SHA изменился, но разрешённый контекст выбранного проекта имеет тот же hash
- **THEN** система не требует переподключения и не переписывает клиентские файлы только из-за нового SHA

#### Scenario: Диагностика и вложенные вызовы
- **WHEN** пользователь просматривает статус/диагностику или продолжает прерванное применение, а другая обычная команда вызывает вложенные helpers
- **THEN** диагностические/восстановительные пути не запускают новое автоприменение; вложенные helpers обычной команды используют её один pinned snapshot без повторной проверки реестра

### Requirement: Разрешение конфликтов пользователем

Если сравнение applied/current/new обнаружило неоднозначную ручную правку управляемого значения, система SHALL до записи конфликтного плана показать «применённое / локальное / новое из реестра» и запросить решение пользователя. Она SHALL предлагать сохранить локальное значение как override, принять значение реестра или отложить всё обновление с продолжением по валидному текущему локальному контексту на прежней ревизии каталога. Откладывание SHALL сохранять уже существующие ручные правки без отката к baseline. До решения SHALL NOT происходить частичного применения нового плана или выполнения основной фазы команды. После сохранения override тот же конфликт SHALL NOT запрашиваться повторно без нового изменения локального состояния.

В запуске без возможности диалога конфликт SHALL завершать запуск результатом «требуется решение пользователя», без записи и выполнения основной фазы; пользователь SHALL получать конкретный способ продолжить через того же владельца. Отсутствие ответа SHALL NOT считаться согласием. Конкурентное изменение после начавшейся записи SHALL использовать существующий partial recovery контракт.

#### Scenario: Конфликт ручной правки и реестра
- **WHEN** одна управляемая настройка изменилась локально вне явного override и одновременно в реестре относительно applied baseline
- **THEN** пользователь видит три значения до записи; его выбор определяет override, принятие реестра или продолжение по валидному текущему контексту без нового update, а чужая правка не затирается автоматически

#### Scenario: Повтор после сохранения локального значения
- **WHEN** пользователь разрешил конфликт сохранением локального override и запускает следующую обычную команду
- **THEN** override сохраняется и тот же вопрос не повторяется; другие наследуемые настройки продолжают автоматически обновляться

#### Scenario: Конфликт без диалога
- **WHEN** автоматический запуск обнаружил конфликт, но не может получить ответ пользователя
- **THEN** возвращается «требуется решение пользователя» с diff и продолжением; файлы неизменны, основная команда ещё не выполнена

### Requirement: Отмена, конкуренция и восстановление

Операция SHALL иметь ограниченное ожидание, понятный status и восстановление того же закреплённого плана через существующего владельца MCP-настроек. Отмена до записи SHALL оставлять файлы неизменными. После частичной записи SHALL сохраняться receipts и возможность продолжения либо восстановления прежних управляемых секций; чужие конкурентные изменения SHALL NOT откатываться. Отметка полного применения SHALL записываться только после всех обязательных записей и проверок.

#### Scenario: Конфликт после записи первого клиента
- **WHEN** первый client записан, а второй изменён другим процессом после preflight
- **THEN** операция показывает частичный результат, сохраняет receipts, не объявляет полный успех и не затирает внешнее изменение при resume/restore

#### Scenario: Возобновление после прерывания
- **WHEN** разработчик повторяет сохранённую операцию
- **THEN** используется тот же pinned Git SHA и план либо явно строится новый preview; новый startup hook не подменяет ревизию, молчаливое смешивание ревизий исключено

#### Scenario: Точный restore descriptor после позднего выбора
- **WHEN** после первого обновления старой установки разработчик выбирает проект и выполняет restore, а descriptor после owned записи больше не менялся
- **THEN** существующий settings writer возвращает исходные bytes descriptor из receipt, включая порядок JSON, BOM и переводы строк; clean descriptor не становится dirty только из-за сериализации. Receipt сохраняется до физической записи и доступен pinned resume/restore
- **AND** при последующей чужой правке восстановление всего файла не применяется: несвязанные значения сохраняются, конфликт самой привязки останавливает запись; исторический receipt без исходных bytes допускает прежний semantic restore без обещания точного формата

#### Scenario: Согласованное восстановление тестового стенда из capsule
- **WHEN** raw seed недоступен и отдельно согласован повтор G3 из сохранённой sealed capsule
- **THEN** существующий source fixture factory по явным path/SHA и capacity budget создаёт новый Develop target из проверенных DT/source.bundle/state/context прежнего published N-1 baseline; обычный live-seed admission и Release/publication route не переключаются на recovery автоматически
- **AND** исходный seed и failed copy сохраняются; admission нового target явно отмечен как sealed-capsule, currentness raw seed остаётся unavailable; native first update → later → select → restore сохраняет workload и проверяет точные bytes/clean roots, private later и выключенную память, не закрывая full G3 либо G4

#### Scenario: Сбой автоприменения перед основной командой
- **WHEN** автоматическое применение началось, но завершилось частичной записью или ошибкой проверки нового подключения
- **THEN** основная команда не выполняется по смешанному контексту, результат сообщает о незавершённом обновлении и штатном resume/restore; доступ к диагностике/восстановлению сохраняется

### Requirement: Снимок и offline без угадывания

Tracked настройки SHALL хранить общую привязку проекта, а личные пути/credentials/overrides и применённый runtime snapshot SHALL оставаться ignored. Snapshot SHALL содержать основание Git, hash разрешённого контекста и provenance binding. При offline существующий проект SHALL продолжать работу по последнему валидному применённому снимку с указанием свежести; новый выбор SHALL использовать валидный cache или явную ручную/отложенную настройку.

#### Scenario: Реестр недоступен
- **WHEN** при запуске команды существующий проект имеет применённый валидный снимок, но проверка remote недоступна или истекло ограниченное время ожидания
- **THEN** команда продолжает локальную работу по этому снимку; статус показывает его основание и невозможность проверить обновления, без бесконечного ожидания или выдуманного нового источника

#### Scenario: Нет ни каталога, ни cache
- **WHEN** создаётся новый проект без доступа к каталогу
- **THEN** пользователь выбирает продукт и локальные параметры явно и может отложить интеграции; источники и внешние IDs не угадываются

### Requirement: Первое предложение привязки при обновлении

После первого успешного интерактивного обновления совместимого пакета локальный проект без `projectId` и без сохранённого пользовательского defer SHALL получать предложение выбрать проект из каталога, создать новый или сделать позже. Existing setup/MCP owner SHALL сохранять явное «позже» в ignored user-local selection текущего проекта и SHALL NOT повторять вопрос при каждой команде/обновлении; явный вход в настройку SHALL позволять вернуться к выбору. В unattended или при отсутствии ответа новая ассоциация SHALL NOT приниматься, отсутствие ответа SHALL NOT сохраняться как согласие/defer; package update SHALL иметь отдельный результат и сохранять legacy работу. Путь/семейство/endpoint SHALL только подсказывать кандидатов, SHALL NOT назначать business project. Создание SHALL использовать существующий validated save/готовую заявку без отправки сообщений.

#### Scenario: Первое интерактивное обновление старого проекта
- **WHEN** совместимый package update завершён, project ID отсутствует и пользователь ранее не откладывал привязку
- **THEN** показаны три действия; проект автоматически не назначен, legacy settings действуют до явного выбора

#### Scenario: Старый caller ещё не знает catalog offer
- **WHEN** неизменённая legacy установка впервые обновляется из исходной foreground консоли, а её caller не содержит hook предложения каталога
- **THEN** новый post-copy задаёт доступный пользователю вопрос в этой же операции после успешного package/branch завершения; предварительная установка нового caller, следующий update или ручной select не требуются и не заменяют эту приёмку

#### Scenario: Пользователь выбрал позже и затем вернулся
- **WHEN** пользователь отложил ассоциацию, повторил update/обычную команду и позднее явно открыл настройку проекта
- **THEN** повторного автоматического вопроса нет, а явный вход снова позволяет выбрать/создать проект; defer другого пользователя/рабочей копии не меняется

#### Scenario: Unattended или ответ отсутствует
- **WHEN** обновляется unbound проект без интерактивного выбора или пользователь не ответил
- **THEN** package update может завершиться, ассоциация и memory opt-in не записаны, показан способ продолжить позже; отсутствие ответа не разрешает изменение настроек

### Requirement: Первая ассоциация имеет preview и прежнего владельца восстановления

До первой записи binding existing owner SHALL показать project/product/profile, MCP/СППР/Mantis и сравнение с current settings, сохранив overrides/disabled/custom sections. При отсутствии прежнего applied snapshot SHALL фиксироваться current hashes/owned секции и новое основание, SHALL NOT выдумываться registry baseline. Неоднозначный конфликт SHALL разрешаться до writes; отсутствие каталога/cache SHALL NOT порождать guessed IDs. После выбора/решения конфликтов SHALL использоваться существующие preflight/receipts/marker-last/pinned resume/owned restore и штатный client reload. Миграция SHALL NOT запускать повторный init/reset базы, самостоятельно менять базовый продукт или затрагивать соседние worktrees. Успех package update SHALL NOT скрывать failed/partial association.

#### Scenario: Старая установка с нестандартным MCP
- **WHEN** выбран проект каталога, но legacy endpoint вручную настроен иначе и прежнего registry snapshot нет
- **THEN** preview сохраняет custom настройку/предлагает разрешить реальный конфликт; после выбора есть reproducible snapshot/receipts без выдуманного старого base, база и другие worktrees не меняются

#### Scenario: Отмена и partial первой привязки
- **WHEN** первая ассоциация отменена до записи либо прервана после записи одного client файла
- **THEN** отмена сохраняет прежние bytes; partial имеет status/pinned resume/owned restore и не объявляется готовой привязкой, независимо от успеха package update

### Requirement: Привязка к каталогу и включение памяти независимы

Выбор проекта, package update или существующая MCP entry SHALL NOT сами активировать managed memory route. В existing setup path SHALL допускаться отдельный явный выбор включить память/позже только при qualified provider/registry context и совместимых helper/fork; `TOOL off/required` и personal settings SHALL сохраняться. Отсутствующая/неквалифицированная память SHALL NOT блокировать каталог или требовать OpenViking; required gap SHALL оставаться только у зависимой memory operation. Native Q1–Q7 текущей редакции memory change, local identities/cycle и старые заметки SHALL принадлежать memory owner, без обязательного запроса на каждую из шести областей. Q5 SHALL проверять административный допуск после контролируемого restore, Q7 — ограниченный профиль и достаточные измерения всего прогона; полная детализация internal usage и paired сравнение SHALL NOT становиться условиями работы каталога. Restore admission/caches/measurement state SHALL NOT переноситься в registry schema, второй updater или отдельный ACL/restore реестр. Registry-only приёмка SHALL проверять этот контракт fixture, а не требовать работающий Cognee; изменение требований SHALL NOT считаться новой native квалификацией.

#### Scenario: Каталог выбран без включения памяти
- **WHEN** пользователь связал legacy проект и выбрал память позже либо native квалификация ещё не выполнена
- **THEN** каталог работает самостоятельно, память не активирована, прежние off/disabled/External MCP сохранены; результат не объявляет memory readiness

### Requirement: Opt-in совместимость и наследование ветками

Проекты без новой привязки SHALL сохранять прежний контракт до явной миграции. Ветки SHALL наследовать выбранную привязку через существующий lifecycle с материализацией текущего корня, без массовой записи в другие worktrees. Старый workflow, неспособный представить новую настройку, SHALL требовать совместимую версию либо восстанавливаемое предыдущее состояние, не удалять только новый ID для видимости совместимости. Работа SHALL сохранять поддержку обычного пользователя Windows 10/11 и Windows Server 2019+ в локальной и терминальной сессии.

#### Scenario: Старый PM4 проект
- **WHEN** проект без новой привязки обновляет пакет
- **THEN** его прежний выбор MCP и PM4/PM5 поведение сохраняются до явного opt-in с preview

#### Scenario: Создание новой ветки
- **WHEN** lifecycle создаёт ветку из привязанного проекта
- **THEN** сохраняются ID и выбранные общие настройки, локальные пути разрешаются для новой ветки, чужие worktrees не обновляются

#### Scenario: Старый helper и новый профиль
- **WHEN** старый helper не понимает выбранный профиль документации
- **THEN** он не подключает глобальную документацию молча; доступно обновление helper или совместимое восстановление прежнего состояния
