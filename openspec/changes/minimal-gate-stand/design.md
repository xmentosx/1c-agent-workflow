# Design

## Context

Гейты Develop и Release проверяют механику workflow: обновление, init, ветки, проверку, отказ production-загрузки, экспорт, refresh, close, расширения, on-demand MCP. Сейчас всё это выполняется на копии PM5 КОРП, и время каждой операции 1С определяется размером этой конфигурации (см. proposal). Стенд создаётся вручную по `docs/release-checklist.md` и общий для всех сессий; 2026-10-29 Develop Capture отказал из-за ручного коммита другой сессии на ветке этого стенда.

Решения пользователя 2026-10-29: своя минимальная конфигурация; Release тоже на ней; стенд собирается скриптом из репозитория; PM5-стенд остаётся вне гейтов.

## Goals / Non-Goals

Цели:

- Сократить холодную публикацию в `develop` минимум на 30% (база ~100 мин) и Release qualification пропорционально, без ослабления утверждений сценариев и этапов.
- Сделать стенд воспроизводимым: один скрипт и фикстура в репозитории дают тот же стенд на любой машине с платформой 1С.
- Позволить каждому clone/сессии иметь свой стенд.

Не цели:

- Менять поведение установленного workflow или `/itl-*`.
- Автоматически выделять стенд публикации: `-E2EProjectRoot` остаётся явным параметром.
- Настраивать серверный стенд: он остаётся опциональным и `unverified` при отсутствии.
- Сохранять покрытие специфики больших конфигураций в гейтах (осознанный trade-off, см. Risks).

## Decisions

1. **Фикстура — XML-исходники в `tests/fixtures/gate-stand/`.** Положительный вариант — полная конфигурация; негативный — та же конфигурация с одним изменением формы, при котором `/CheckConfig` сообщает «Отсутствует обработчик». Формат XML соответствует минимальной поддерживаемой версии платформы. Состав намеренно покрывает не зависящие от размера риски: длинные кириллические имена объектов и форм (бюджет длины путей), модули форм и объектов, общий модуль с серверным вызовом, макет с двоичными данными, роль, режим совместимости, допускающий расширения, Vanessa TestClient и YAxUnit. Фикстура не содержит объектов PM5. Она даёт то, что гейты получали от PM5 неявно: поддержку поставщика с разрешённым редактированием, пользователя без защиты от опасных действий (роль связана с пользователем шаблона `assets/vanessa-service/service-infobase.dt`, на который сборщик загружает конфигурацию) и две серверные точки входа БСП, которые вызывает встроенная EPF автообновления; обработчиков обновления нет.
   Альтернатива: небольшая готовая конфигурация (демо БСП). Отклонена пользователем: её нельзя положить в репозиторий, а операции займут минуты.

2. **Сборщик `scripts/new-gate-stand.ps1 -StandRoot <path>` выполняет только штатные шаги.** Он создаёт файловую ИБ из фикстуры через общий helper `CREATEINFOBASE` и загрузку конфигурации (с per-infobase guard), кладёт её как in-stand source snapshot, выполняет configured init через `install-agent-1c-workflow.ps1`, создаёт Develop и Release worktree, коммитит golden-фикстуру Release и её фичу Vanessa, собирает positive-проект и пишет `release-e2e.json` со своими `developConfigurationRejection` (`sourcePath`, `sourceSha256`, `diagnostic`, `positiveProjectRoot`). Сборщик отказывается работать с непустым чужим каталогом; при сбое его можно повторить на новом каталоге. Собственного жизненного цикла, состояния или recovery у стенда нет: дальше работают существующие Prepare/Capture/update.
   Альтернатива: автоматизировать только копирование готовой ИБ. Отклонена: тогда воспроизводимость и стенд на каждый clone зависят от внешнего файла.

3. **Код сценариев и этапов не меняется, кроме мест, где зашиты свойства PM5.** Ожидания (`expected` отказа, golden-изменение, фичи) берутся из `release-e2e.json` и фикстуры. Если найдётся зашитое в коде свойство PM5, оно переносится в конфигурацию стенда, а не ослабляется.

4. **Переход холодный.** Stand identity, капсулы, journey- и stage-proofs PM5 не переносятся на новый стенд: их входы другие, поэтому существующие проверки identity сами потребуют свежего прогона. Миграции кэша не делаем.

5. **Документация.** `docs/release-checklist.md` заменяет ручную настройку командой сборщика; примеры `-E2EProjectRoot` в `docs/local-quality-gate.md` указывают на стенд из сборщика; правило «один стенд — одна публикация» дополняется рекомендацией собрать свой стенд на clone.

## Risks / Trade-offs

- **Не покрываются дефекты, проявляющиеся только на больших конфигурациях:** таймауты, память, размер выгрузки, производительность индекса и Gate 6. Пользователь принимает этот риск; PM5-стенд остаётся для ручных продуктовых пилотов. Таймауты и бюджеты этапов не уменьшаются, поэтому медленная, но корректная операция не станет отказом.
- **Выигрыш не измерен.** Оценка: Develop E2E с ~73 до 15–25 мин, публикация с ~100 до ~35–45 мин. Если измерение покажет меньше 30%, изменение не считается принятым, пока не найден остающийся крупный шаг.
- **Совместимость XML-фикстуры с версиями платформы.** Формат выбирается по минимальной поддерживаемой версии; несовместимость проявится отказом загрузки в сборщике, а не тихой ошибкой.
- **Новая фикстура — новое сопровождение**, но маленькое: десяток объектов, без следования за релизами PM5.

## Migration Plan

1. Добавить фикстуру и сборщик; собрать стенд (например, `D:\Git\itl gate stand Стенд`) рядом с PM5-стендом.
2. Выполнить холодные Develop и Release qualification на новом стенде, записать времена и сравнить с базой.
3. Переключить документацию и команды публикации на новый стенд; PM5-стенд больше не передаётся в `-E2EProjectRoot`.
4. Откат: вернуть `-E2EProjectRoot` на PM5-стенд; его капсулы и proofs остаются в его собственном common git dir.

## Architecture Checkpoint

Триггер по `docs/package-architecture.md`: сокращение поддерживаемого покрытия гейтов (большая конфигурация уходит из Develop и Release). Новой общей runtime-власти, состояния, блокировок, восстановления, миграции установленных проектов или elevation нет.

Предмет одобрения: заменить стенд гейтов PM5 КОРП на стенд, собираемый из минимальной фикстуры репозитория, для Develop и Release, сохранив утверждения сценариев и этапов; PM5 остаётся вне гейтов. Решения пользователя по составу приняты 2026-10-29; одобрение checkpoint — первая задача в tasks.md.
