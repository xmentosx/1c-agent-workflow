# Design

## Context

Мотивация и измерения — в proposal.md, раздел Why. Текущее устройство:

- **Привязка.** `binding/<hash>.json` для каждой копии хранит `bindingId`, цикл,
  контекст реестра, подтверждения политики и провайдер. Новый `bindingId`
  выдают `Sync-ItlMemoryContext` (при любом изменении хеша контекста или цикла) и
  `Invoke-ItlMemorySetup enable` (при изменении настроек или политики). MCP-процесс
  `cognee-memory-mcp.ps1` читает привязку при старте, а
  `Assert-ItlMemoryBindingCurrent` отклоняет вызов, если `bindingId` в файле другой.
  В обычную сессию это доходит ошибкой `MEMORY_STALE_CONTEXT` после параллельного
  update или reset. Смена `bindingId` — единственный сигнал, по которому уже
  запущенный процесс узнаёт об изменении настроек подключения.
- **Workspace.** `identity.workspaceId` строится по корню копии
  (`Get-ItlMemoryWorkspace`). Им ключуются каталоги pending и source, файл
  continuation, `memoryCycle.workspaceId` в состоянии ветки, ID заметки по
  умолчанию и датасет `itl_workspace_<id>`. У ветки уже есть `mainWorktreePath`.
- **Workplace.** `hash(developerId, machineId)`. `developerId` — общая техническая
  учётка, а `machineId` — GUID в `%LOCALAPPDATA%`, то есть фактически «пользователь
  Windows на машине».
- **Продолжение.** Файл continuation лежит по ключу копии ветки, а цикл проверяется
  внутри файла (`Get-ItlMemoryLocalContext`). После reset прежнее продолжение уже
  не выдаётся.
- **Заметки.** Создание идёт текстовым полем `raw_data`, обновление — отправкой
  файла с постоянным именем `memory.txt`. `recall` возвращает только `verified`;
  `remember` по умолчанию пишет `candidate`. ID по умолчанию —
  `hash(workspaceId, projectId, datasetName, data)`. Pending сохраняется до
  проверки назначения.
- **Чтение локальных записей.** `Read-ItlMemoryJson` превращает в
  `MEMORY_RECORD_INVALID` любой сбой чтения, включая превышение размера и ошибку
  ввода-вывода.
- **Ленивые датасеты.** `Resolve-ItlMemoryPrivateDataset` ищет датасет по имени и
  владельцу, только если резервация уже есть в привязке этой копии; иначе сразу
  отправляет `POST /datasets`.
- **Ресурсы сервера Cognee 1.6.5.** Проверены 2026-11-11, см.
  [evidence](evidence/metadata-qualification-2026-11-11.md):
  - `labels` и `external_metadata` задаются только при создании и после
    `PATCH /update` не меняются;
  - поле `name` в листинге равно имени отправленного файла без расширения и
    заменяется при каждом обновлении; `data_id` при обновлении сохраняется;
  - уникальность имени проверяется при создании (второй документ с тем же именем —
    `409`), но не при обновлении: две заметки можно обновить с одним именем файла;
  - `/` и `\` обрезают имя до последнего сегмента, предел при создании — 255 байт
    вместе с расширением и служебным суффиксом;
  - листинг упорядочен по `createdAt`, страница до 1000 записей; 0,27–0,31 с на
    малом датасете, 0,49 с на 120 заметках;
  - чтение оригинала — 0,29 с;
  - `POST /datasets` с существующим именем возвращает тот же датасет, в том числе
    при двух одновременных запросах.
- **Корень форка.** `root-contract.json` помечает каждый upstream-раздел, включая
  `## Project memory`, как `upstream-root`. Корень собирается как точный upstream
  плюс ITL-приложение `templates/ai-rules-overlay/AGENTS.md` (2 373 байта, в нём
  уже есть строка про память, ~190 байт).
- **Размеры:**
  - установленный AGENTS.md — 14 028 байт при потолке корня 14 КБ (14 336 байт;
    значение взято из ledger, валидатор форка в этой работе не открывался);
  - `project-memory.md` — 10 978 байт;
  - описания четырёх инструментов памяти — около 1,8 КБ.

## Goals / Non-Goals

**Goals:**
- Один владелец каждого инварианта, в рамках существующего модуля памяти:
  привязка — `agent-1c.memory-context.ps1`, операции с заметками и журнал —
  `agent-1c.memory.ps1`, протокол и схемы — `cognee-memory-mcp.ps1`.
- Без нового сервиса, фоновой синхронизации, кеша между операциями и записи
  состояния lifecycle.
- Постоянная добавка к контексту: ядро ~1,2 КБ в корне, описания инструментов
  ≤ ~0,6 КБ прироста, выдача `memory_status` ≤ 2000 токенов.

**Non-Goals:**
- Наполнение общих слоёв, права по сотрудникам, изменения сервера Cognee.
- Автоматическое перенесение старых записей.
- Блокирующие проверки использования памяти.
- Выдача кандидатов через `recall`: кандидаты становятся видимыми только в
  оглавлении.

## Decisions

### D1. Ядро в ITL-приложении корня, справочник по запросу

Ядро (~1,2 КБ) добавляется в `templates/ai-rules-overlay/AGENTS.md` отдельным
заголовком. Upstream-раздел `## Project memory` не меняется. Существующая строка
приложения про память объединяется с ядром после семантической сверки:
сохраняются запрет неявного включения нового провайдера и доступность
`templatesearch`. Корень форка пересобирается из upstream и приложения.

Ядро условное: «если доступен инструмент `memory_status`». Проекты без включённой
памяти получают тот же текст, но он для них не действует.

Корень вырастет с 14 028 до ~15,1 КБ. Потолок корня в валидаторе форка
поднимается с 14 до 15 КБ в том же релизе, с замером и кратким обоснованием.

Из `project-memory.md` убирается повтор того, что теперь в ядре. Для управляемых
ITL-проектов общая маршрутизация трёх провайдеров уходит под явное условие «вне
управляемого проекта», текст upstream сохраняется. Изменение ведёт
`ITL-SCOPED-MEMORY-001`. Clause hash и `rulesCandidateCommit` в
`scoped-memory-policy.json` обновляются вместе с релизом форка.

Корневой AGENTS.md — общий файл для всех клиентов проекта и сверяется один раз,
поэтому ядро получают Codex, Claude, Cursor и Kilo.

*Альтернативы:*
- Заменить upstream-раздел ядром: отклонено, нарушает контракт корня и возвращает
  «полную замену корня».
- Ядро только в описаниях инструментов и `instructions` MCP-сервера: не растит
  корень, но доставка `instructions` модели в Codex не подтверждена.
- Уложиться в действующие 14 КБ ядром ~0,5 КБ: отклонено пользователем; критерии
  слоя организации и выбор уровня остаются в постоянно загружаемом тексте.
- Управляемый блок USER-RULES: он уже 13,7 КБ, и политика памяти оказалась бы в
  двух владельцах.

### D2. Поводы для вызова в описаниях инструментов

Описания `recall`, `remember`, `retire_note` и `memory_status` переписываются как
«когда вызывать + что передать». Изменения схемы:

- `remember.status` — перечисление `candidate`, `verified`, `standing`;
- `remember.title` — необязательная строка до 80 символов;
- `retire_note.dataset_name` — необязательный, только для локальной pending-записи.

Описание `remember` задаёт форму evidence для слов пользователя:
`{source:'user', reference:'чат <дата>'}`. Исправление и правило пользователя
сохраняются сразу как `verified` или `standing`. Политика остаётся одна: описания
говорят о поводах, а правила выбора уровня и формат остаются в ядре и справочнике.

Строка `instructions` MCP-сервера меняет «шесть областей» на семь.

### D3. Статус standing и имя документа как носитель оглавления

**Статус.** Для агента `standing` — третье значение `status`. В заметке
(`itl-memory-v1`) хранится `status: verified` и отдельное поле `standing: true`,
а также `title`. Старый код видит обычную подтверждённую заметку и лишние поля
игнорирует. Хеш намерения учитывает `title` и `standing`, чтобы смена только этих
полей была обновлением, а не повтором.

Ограничения `standing`:
- требует evidence, как `verified`;
- факт не длиннее 400 символов, иначе отказ с продолжением «сократи факт или
  сохрани как `verified`»;
- в слое задачи не допускается;
- лимит на уровень проверяется листингом целевого датасета.

**Имя.** Полный оригинал остаётся авторитетным. Имя документа Cognee — производная
от него, которая уходит тем же запросом, что и содержимое:

```
<status>~<область знаний>~<заголовок>~<id8>.txt
```

- `status` — `candidate`, `verified` или `standing`;
- область знаний заполняется только у заметок слоя продукта;
- заголовок — `title` или первое предложение факта; `/`, `\`, `~` и управляющие
  символы заменяются пробелом;
- `id8` — первые 8 hex-символов хеша `note_id`; делает имя уникальным в датасете;
- всё имя — не больше 200 байт UTF-8, заголовок обрезается под этот предел.

Создание заметки переводится с `raw_data` на отправку файла, как уже сделано для
обновления. Обновление отправляет файл с новым именем.

Имя, не разобранное по этому формату, означает заметку старого формата или правку
из ещё не обновлённой копии. Для таких строк заголовок и статус берутся чтением
оригинала, не больше 6 на вызов; остальные учитываются в «ещё N».

*Альтернативы:*
- `external_metadata`: отклонено, замораживается при создании.
- Читать оригинал каждой строки оглавления: работает, но стоит 0,3 с на заметку
  на старте каждой сессии.
- Обновление как удаление и новая запись: меняет `data_id` при каждой правке и
  добавляет два шага со сбоем между ними.
- Отдельный документ-индекс на датасет: второе состояние с гонками при общей
  учётке.

### D4. Серверный memory_status

`Invoke-ItlMemoryStatus` без `local_only` после локальной части за один срок
(15 секунд):

1. получает листинг каждого допущенного датасета текущего контекста (не больше
   7 уровней, у продукта — по датасетам продуктов композиции), по 2 параллельно,
   одной страницей до 1000 записей;
2. разбирает имена; строки продукта отсеивает по применимости области знаний тем
   же правилом, что `Test-ItlMemoryNoteApplicable`;
3. сортирует: `standing` и `verified` раньше `candidate`, затем по `updatedAt`;
4. читает оригиналы постоянных заметок в пределах лимита уровня, полностью
   проверяет применимость и сверяет отметку по оригиналу;
5. собирает ответ под потолок 2000 токенов (`Measure-ItlMemoryTokens`): сначала
   постоянные заметки, затем строки оглавления. Порядок уровней: проект,
   workspace, организация, продукт, host, workplace, задача. Что не поместилось —
   «ещё N, ищите через recall».

Строка оглавления: заголовок, уровень, статус. ID в оглавлении нет; постоянная
заметка приходит с `note_id` и `data_id`. Тонкие условия применимости (версия,
состав продуктов, `projectId` в общих слоях) для строк оглавления не проверяются:
содержимое агент получает только через `recall`, где проверка полная.

Датасет больше 1000 заметок даёт частичное покрытие. Кеша между операциями нет.
Сводка `memory_status` попадает в журнал как обычный вызов.

Ожидаемое время в худшем случае: 8 листингов и 21 оригинал по 2 параллельно —
около 5 секунд.

### D5. Слой host

- `hostId = hash(MachineGuid из HKLM\SOFTWARE\Microsoft\Cryptography, имя хоста
  в нижнем регистре)`. Чтение без прав администратора; если значения нет —
  `unavailable` без записи.
- Датасет `itl_host_<hostId>` — приватный в терминах адаптера и создаётся лениво,
  как task, workspace и workplace, под той же технической учёткой. Это отдельная
  область в `Get-ItlMemoryPrivateScopes` и допустимый `scopeKind` в проверке
  провайдера.
- Слой общий для пользователей машины, только пока они работают под одной
  технической учёткой Cognee. Если появятся персональные учётки, `host` переходит
  в общие датасеты, которые готовит оператор. Это граница совместимости, а не
  часть этой работы.

**Создание ленивых датасетов.** `Resolve-ItlMemoryPrivateDataset` при отсутствии
резервации сначала ищет датасет по точному имени и владельцу; создаёт, только
если его нет; после создания проверяет, что совпадение одно. Резервация в привязке
остаётся защитой внутри одной копии. Между копиями и пользователями дубль
исключает сам сервер (квалифицировано). Это касается и общего workspace, и `host`.

### D6. Workspace — локальный проект

Идентичность дополняется, а не переименовывается:

- `identity.workspaceId` сохраняет прежний смысл — ID копии ветки. Им по-прежнему
  ключуются pending, source, continuation, `memoryCycle.workspaceId` и ID заметки
  по умолчанию;
- новое поле `identity.localProjectId` — ID записи workspace основной копии
  (`mainWorktreePath` ветки или корень самой основной копии). Им ключуется только
  датасет слоя workspace: `itl_workspace_<localProjectId>`;
- новое поле `identity.hostId` — см. D5.

У основной копии `localProjectId` совпадает с `workspaceId`, её датасет workspace
не меняется. Состояние веток, pending и continuation остаются валидными без
миграции. Ключ `checkpoint` не меняется: файл уже привязан к копии ветки, цикл
проверяется внутри.

*Альтернативы:*
- Перенести `memoryCycle.workspaceId` на новый смысл: миграция чужого состояния
  lifecycle.
- Новый ключ continuation «копия + цикл»: требование уже выполнено, смена ключа
  только потеряла бы продолжение текущей задачи при обновлении.

### D7. Идентичность привязки, дополнение и перечитывание

- `bindingId` меняется только при смене `cycleId`, `projectId` или `productId`, при
  выключении памяти и один раз при дополнении привязки (ниже). В
  `Sync-ItlMemoryContext` и в повторном `enable` той же копии при совпадении этих
  трёх значений остальное содержимое обновляется на месте с прежним `bindingId`.
- **Дополнение привязки.** `schemaVersion` остаётся 1. Привязка без
  `identity.localProjectId` и `identity.hostId` дополняется владельцем при первом
  вызове `Sync-ItlMemoryContext` или `enable` новым кодом, до раннего выхода по
  неизменному контексту. В той же записи `bindingId` меняется один раз. Процесс
  со старым кодом получает прежний `MEMORY_STALE_CONTEXT` и перезагружается уже с
  новым кодом. До дополнения слои workspace и `host` для нового процесса
  `unavailable`, остальные работают.
- MCP-процесс перед каждым `tools/call` перечитывает файл привязки (один локальный
  JSON до 256 КБ) и проверяет подтверждение политики по свежей записи.
- Если `bindingId` другой, но совпадают корень и копия ветки, память включена и
  нет `resetting`, процесс переходит на новую привязку и добавляет `contextChanged`
  с прежним и новым циклом и причиной.
- После смены цикла или проекта процесс выставляет флаг в своей памяти: первая
  запись (`remember`, `retire_note`) отклоняется с продолжением, флаг снимает
  `memory_status`. Флаг живёт только в процессе: ни файла, ни lock, ни
  межпроцессного состояния.
- `schemaVersion` неизвестный процессу — отказ «перезагрузи клиент».

Это осознанное ослабление требования «Старый контекст не становится новым» из
`add-scoped-cognee-memory`: старый чат после одного `memory_status` может писать в
новый цикл. Продолжать тот же чат после reset — обычный сценарий, и он дал три
ошибки `MEMORY_STALE_CONTEXT` из пяти. Поздняя запись не попадает в новый цикл
молча: она отклоняется один раз, и агент видит смену контекста.

### D8. Pending и ID заметки

- ID заметки по умолчанию — `hash(workspaceId, projectId, data)`, без датасета.
  Повтор `remember` с выбранным датасетом попадает в ту же pending-запись.
  Существующие заметки и pending хранят свой ID и не затрагиваются.
- `remember` с тем же `note_id`: если у pending нет `attempt`, допускается смена
  `datasetName` и intent, а прежний исходник уходит в архив. Если `attempt` есть,
  поведение прежнее: сначала сверка.
- `retire_note(note_id)` без `data_id` для pending без `attempt` переносит запись в
  `pending-archive/` и удаляет её из выдачи.
- Тексты `MEMORY_PENDING_CONFLICT` и `MEMORY_DESTINATION_REQUIRED` называют оба пути.
- Правило «исходник сохраняется даже при отказе назначения» не меняется.

### D9. Чтение локальных записей

`Read-ItlMemoryJson` разделяет причины:

- ошибка ввода-вывода — до 3 попыток с короткой паузой, затем
  `MEMORY_RECORD_BUSY` с продолжением «повтори ту же операцию»;
- превышение размера — `MEMORY_RECORD_TOO_LARGE`, как и задумано;
- повреждённый JSON — `MEMORY_RECORD_INVALID` с видом записи (привязка, состояние
  ветки, pending, квитанция, продолжение).

Причина двух `MEMORY_RECORD_INVALID` из исходных измерений по логам не
восстанавливается: все локальные записи сегодня читаются. Вид записи в сообщении
и в журнале позволит диагностировать следующий случай.

### D10. Журнал

- Файл `usage/<hash(workspaceId)>.json` в домашнем каталоге памяти. Последние 200
  записей, запись через существующий `Update-ItlMemoryJson` с его двухсекундной
  защитой. Ошибка журнала проглатывается.
- Запись: инструмент, время, идентификатор сессии (GUID процесса MCP), цикл,
  результат или код ошибки с видом записи, число карточек, сохранённых,
  обновлённых и удалённых заметок. Без текста запроса и фактов.
- Читатели — `vibecoding1c-mcp-status` и `/itl-check`. Они только читают, через
  функцию модуля памяти, без собственного парсинга.
- `/itl-check` выводит строку справочно и только при включённой памяти; статус
  проверки не меняется.

### D11. Связь с add-scoped-cognee-memory

Этот change уточняет четыре требования открытого change. Новые формулировки:

| Требование | Было | Становится |
|---|---|---|
| Шесть областей с устойчивой идентичностью | `taskCycle`, `workspace`, `workplace`, `product`, `project`, `organization`; workspace — отдельная локальная установка | Семь областей: добавлен `host`. Workspace — локальный проект: основная копия и её копии-ветки. Две основные копии одного `projectId` остаются разными workspace |
| Продолжение задачи читается напрямую | Привязка к workspace/cycle | Привязка к копии ветки и циклу; ключ хранения не меняется |
| Старый контекст не становится новым | После reset старый чат не пишет в новый цикл | Процесс сам переходит на новую привязку. Первая запись после смены цикла или проекта отклоняется с продолжением; `memory_status` снимает запрет. Чтения продолжаются сразу |
| Поиск и сохранение не превращаются в фоновую фабрику контекста | Отдельный standing query на первом reader | Постоянные заметки приходят в выдаче `memory_status`; отдельного standing query нет |

Порядок sync:
- если `add-scoped-cognee-memory` попадает в `openspec/specs` раньше, перед sync
  этого change четыре формулировки оформляются как MODIFIED к перенесённым
  требованиям;
- если раньше синхронизируется этот change, те же формулировки вносятся в спеки
  `add-scoped-cognee-memory` через `openspec-update-change` до его sync.

Квалификация G5 открытого change этим изменением не закрывается и не
переоткрывается.

### Architecture checkpoint

Статус: **одобрен пользователем 2026-11-11** в указанных ниже границах (задача 0.1).
Новый затронутый владелец, класс ресурсов или миграция установленного состояния —
изменение границ и требует нового одобрения.

| Поле | Значение |
|---|---|
| Инварианты и владельцы | Идентичность привязки, её дополнение и правила перехода — `agent-1c.memory-context.ps1`. Слои, заметки, имя документа, standing, потолок выдачи, чтение записей и журнал — `agent-1c.memory.ps1`. Протокол и флаг первой записи в процессе — `cognee-memory-mcp.ps1`. Цикл ветки остаётся у lifecycle и читается без записи. |
| Новое общее состояние | Датасет `host` на сервере, общий для пользователей машины под одной учёткой. Датасет workspace, общий для копий одного локального проекта. Локальный журнал на копию ветки. Других координаторов, очередей и lock нет. |
| Почему не обойтись внутри одного владельца | Ядро правила обязано жить в постоянно загружаемом корне: справочник агенты читают, но не исполняют. `host` — новая граница данных по определению. |
| Минимальный воспроизводитель | Сессия `2-branch1` 2026-11-10: параллельная операция владельца меняет `bindingId`, следующий вызов памяти в открытой сессии получает `MEMORY_STALE_CONTEXT` до перезагрузки клиента. |
| Затронуты | ITL-приложение корня и ledger; controlled fork (корень, `project-memory`, потолок корня); модуль памяти; MCP-сервер памяти; вывод status и `/itl-check` (только чтение журнала); lifecycle reset и применение контекста реестра (вызов `Sync-ItlMemoryContext` без изменения контракта). |
| Не затронуты | Сервер Cognee, реестр продуктов, результат и статус верификации, delivery, guard 1С, прочие MCP. |
| Клиенты | Ядро в общем корне получают все клиенты проекта. Описания инструментов видит клиент с зарегистрированным сервером памяти. Пилот — только Codex; Cursor, Claude и Kilo не проверяются. |
| Установленное состояние | Привязка дополняется на месте полями `localProjectId` и `hostId`, версия формата не меняется, `bindingId` меняется один раз. Старые pending, continuation и состояние веток не трогаются. |
| Одна машина состояний | Привязку пишет только её владелец под существующей защитой записи. Флаг первой записи — память процесса. Теневого координатора нет. |
| Ожидание и восстановление | `memory_status` с ограничением 15 секунд, при недоступности — частичное покрытие. Чтение записи — до 3 попыток. Восстановление записи заметки прежнее (квитанции, сверка по точному ID). Переход привязки без ожидания. |
| Совместимость | Процесс со старым кодом после обновления пакета получает `MEMORY_STALE_CONTEXT` один раз и перезагружается. Ещё не обновлённые копии видят новые заметки как обычные `verified`; их правки дают имя старого формата, которое читается через оригинал. Старые заметки без `title` — заголовок из факта. |
| Canary | Одна копия PM5 получает обновление первой и проходит проверку фактическими вызовами (задача 11.1) до остальных. |
| Постоянный контекст | Корень +~1,1 КБ (14 028 → ~15,1 КБ), потолок 14 → 15 КБ. Описания инструментов +~0,6 КБ. Ответ `memory_status` ≤ 2000 токенов, один раз за сессию. Замер в бюджетных тестах — в этом же изменении. |
| Откат | Предыдущий релиз форка и пакета через штатный `update-workflow`. Старый код не видит новых полей привязки и заметок. Датасеты `host`, общий workspace и журнал остаются и ни на что не влияют. |
| Elevation и Windows | Не требуются. `MachineGuid` читается обычным пользователем на Windows 10, 11 и Server 2019+. |
| Решающая приёмка | Исходная задача: агент в обычной сессии PM5 вызывает память и получает результат без ошибок привязки. Проверяется фактическими вызовами клиента и пилотом, а не тестами helper. |

## Risks / Trade-offs

- [Имя документа расходится с оригиналом] → имя и содержимое уходят одним
  запросом; постоянные заметки сверяются по оригиналу; строка оглавления — только
  указатель, содержимое выдаёт `recall`.
- [Другой образ Cognee ведёт себя иначе с именами] → квалификация привязана к
  профилю; непрошедшее имя уходит на чтение оригинала, а не в ошибку.
- [Ещё не обновлённая копия правит заметку и стирает формат имени] → сервер такие
  обновления принимает (квалифицировано), отказов у старых копий нет; новый код
  читает оригинал в пределах 6 строк, а следующая правка новым кодом
  восстанавливает имя.
- [Агент ставит `standing` слишком щедро] → лимиты по уровням, предел длины факта,
  отказ сверх лимита, видимость в строке `Memory:`, для организации — только по
  слову пользователя.
- [Гонка лимита `standing` между сессиями] → лишние заметки не теряются: выдача
  режет по лимиту и сообщает «ещё N».
- [Слой организации и общая учётка: случайное удаление] → подтверждение
  пользователя на удаление чужой заметки организации; обновление на месте сохраняет
  `updatedByOrigin` и `supersedes`.
- [`host` на клонированных ВМ] → имя хоста в составе ключа.
- [`host` и слой организации видны всем проектам машины или организации] →
  ограничение только правилом для агента; данные клиента в эти слои не пишутся.
- [Старый чат пишет в новый цикл после `memory_status`] → принятое ослабление, см. D7.
- [Выдача `memory_status` занимает контекст] → потолок 2000 токенов; пустые уровни
  ничего не стоят.
- [Пилот не достигает порогов] → правка формулировок ядра и описаний, повтор пилота;
  блокирующих проверок не добавляем.

## Migration Plan

1. Architecture checkpoint одобрен 2026-11-11.
2. Квалификация имён завершена 2026-11-11 (задачи 1.1 и 1.2).
3. ITL-изменения модуля, MCP-сервера, вывода и приложения корня — с тестами в source.
4. Ветка апгрейда controlled fork: пересборка корня, сокращение `project-memory`,
   потолок корня, ledger, clause hash, релиз форка, пины в ITL.
5. Обычная регистрация и публикация develop. Установленные проекты получают
   изменения через `update-workflow`. Миграции данных нет.
6. Canary на одной копии PM5, затем пилот по порогам `test-plan.md`.

**Откат:** предыдущий релиз форка и пакета через штатный `update-workflow`.
Заметки с новыми полями старый адаптер читает как обычные: лишние поля
игнорируются.
