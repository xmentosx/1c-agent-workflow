# Proposal

## Why

Scoped Cognee memory включена в 20 рабочих копиях PM5 и технически работает, но
агенты ею почти не пользуются. Анализ сессий Codex и сервера за 2026-10-28 — 2026-11-11:

- 25 сессий в копиях PM5, около 18 из них меняли BSL; память использовали только 4;
- 17 вызовов памяти (`memory_status` 11, `recall` 4, `remember` 2), из них 5 с ошибкой
  (`MEMORY_STALE_CONTEXT` ×3, `MEMORY_RECORD_INVALID` ×2), то есть около 30%;
- на рабочем сервере `cognee-qwen-prod-20261028-v1` из 19 датасетов только в двух
  есть по одной заметке; слой организации, все продуктовые и 7 из 8 проектных пусты;
- правило `project-memory` агенты прочитали в 24 из 25 сессий, но recall-first,
  отдельный standing query и строку `Memory:` почти не выполняют;
- одна pending-заметка висит с 2026-11-08: тот же факт записан заново под другим ID,
  а старая запись выводится в каждом `memory_status`;
- при этом общий проектный слой между копиями работает: копия `1-branch10`
  нашла заметку, записанную из `2-branch4`.

Значит, проблема не в загрузке правила и не в сервере. Обязательные шаги спрятаны
внутри 11 КБ общей политики трёх провайдеров. Описания инструментов не говорят,
когда их вызывать. Постоянные договорённости агент должен искать отдельным
запросом. Устаревшая привязка отключает память до конца сессии. Workspace и
workplace не совпадают с тем, как реально организованы копии и машины.

Ревью 2026-11-11 добавило три причины, найденные в коде и логах:

- `remember` по умолчанию сохраняет `candidate`, а `recall` возвращает только
  `verified`: заметка без явного статуса не находится никогда;
- ID заметки по умолчанию зависит от выбранного датасета, а pending сохраняется до
  проверки назначения: каждый `remember` без датасета оставляет запись-сироту;
- `MEMORY_RECORD_INVALID` вернул `memory_status(local_only=true)` при исправных
  локальных записях: код ошибки скрывает временный сбой чтения.

Решения ниже согласованы в grill 2026-11-11 и в интервью по ревью того же дня.

## What Changes

**Правило и инструменты**
- Обязательное ядро памяти (~1,2 КБ) добавляется в ITL-приложение корневого
  AGENTS.md (`templates/ai-rules-overlay/AGENTS.md`). Upstream-раздел
  `## Project memory` не меняется: корень форка остаётся «точный upstream +
  ITL-приложение». Потолок корня поднимается с 14 до 15 КБ с замером.
  `project-memory.md` становится справочником по запросу.
- Ядро условное: действует, если клиенту доступен инструмент `memory_status`. В нём:
  один `memory_status` в начале сессии; `recall` перед изменением 1C, в незнакомой
  области и в любой момент работы; `remember` в том же ходе после исправления от
  пользователя; обновить или удалить заметку, если она противоречит проверенному
  источнику; критерии для слоя организации; строка `Memory:` со счётчиками.
- Описания MCP-инструментов `recall`, `remember`, `retire_note` и `memory_status`
  говорят, когда их вызывать и как обновлять заметку через `note_id` + `data_id`.

**Постоянные заметки и оглавление**
- У `remember` три значения `status`: `candidate`, `verified`, `standing`.
  `standing` — подтверждённое правило работы, сформулированное пользователем. В
  заметке оно хранится как `verified` плюс отдельная отметка, чтобы ещё не
  обновлённые копии видели обычную подтверждённую заметку. Для организации — только
  по явному слову пользователя.
- Исправление и правило со слов пользователя сохраняются сразу как подтверждённые,
  с evidence фиксированной формы `{source:'user', reference:'чат <дата>'}`.
- Статус, область знаний и заголовок заметки записываются в имя документа Cognee.
  Имя уходит на сервер тем же запросом, что и содержимое, и заменяется при каждом
  обновлении (квалифицировано 2026-11-11). Метаданные Cognee не используются.
- `memory_status` без `local_only` за ограниченный срок получает листинг допущенных
  датасетов и возвращает постоянные заметки целиком плюс оглавление остальных, в
  том числе кандидатов с пометкой. Оригиналы читаются только для постоянных заметок.
  Отдельный standing query больше не нужен. `local_only` остаётся путём без сети.
- У `remember` появляется необязательное поле `title` (до 80 символов).
- Ответ `memory_status` ограничен 2000 токенами; лимиты по уровням — максимумы.

**Слои**
- Новый слой `host`: общий для всех пользователей и проектов одной машины под одной
  технической учёткой, только факты об окружении.
- **BREAKING (локальная идентичность):** слой workspace теперь означает локальный
  проект, то есть основную копию вместе со всеми её копиями-ветками. Старые записи
  не переносятся, но остаются доступными по точному ID. Ключ продолжения
  (`checkpoint`) не меняется: он уже привязан к копии ветки и циклу.
- Критерии для слоя организации: никаких данных клиента и конкретного проекта.
  Удалить чужую заметку организации можно только с подтверждения пользователя.

**Устойчивость**
- Новый `bindingId` выдаётся только при reset ветки или смене проекта либо продукта.
  Обновление workflow, MCP, правил, настроек и областей знаний меняет привязку на
  месте.
- Привязка дополняется новыми полями без смены версии формата. При первом
  дополнении `bindingId` меняется один раз, чтобы процессы со старым кодом получили
  отказ и перезагрузились.
- Сервер памяти перечитывает привязку при каждом вызове и сам переходит на новую,
  возвращая `contextChanged`. После смены цикла или проекта первая запись
  отклоняется до `memory_status`.
- ID заметки по умолчанию не зависит от датасета: повтор `remember` с выбранным
  датасетом попадает в ту же pending-запись. Застрявшую pending-заметку можно
  доотправить (`remember` с тем же `note_id`) или удалить локально (`retire_note`).
- Временный сбой чтения локальной записи повторяется и получает свой код
  `MEMORY_RECORD_BUSY`; `MEMORY_RECORD_INVALID` остаётся только для повреждённой
  записи и называет её вид.
- Перед созданием ленивого датасета адаптер ищет его по имени и владельцу.
- В списке destinations области знаний одного продукта сворачиваются в одну запись.

**Наблюдаемость**
- Локальный приватный журнал вызовов памяти без текста запросов, с идентификатором
  сессии.
- Сводка журнала в `vibecoding1c-mcp-status` и информационная строка в `/itl-check`
  при включённой памяти, без блокировки.

**Вне работы:** наполнение общих слоёв (это работа оператора), права по сотрудникам,
изменения сервера Cognee, изменение поведения `recall` для кандидатов.

## Capabilities

### New Capabilities
- `memory-agent-adoption`: обязательное ядро правила, описания инструментов как
  поводы для вызова, обновление и удаление устаревших заметок, критерии слоя
  организации, строка `Memory:`, журнал вызовов.
- `memory-standing-context`: статус `standing`, `title`, имя документа как носитель
  оглавления, серверный `memory_status` с постоянными заметками и оглавлением,
  потолок и порядок выдачи.
- `memory-scope-identity`: слой `host`, workspace как локальный проект, правила
  смены `bindingId`, дополнение привязки и автоматический переход, разбор
  застрявших pending-заметок, коды сбоя чтения, компактные destinations.

### Modified Capabilities
- Нет в `openspec/specs`. Требования памяти пока живут в незаархивированном change
  `add-scoped-cognee-memory`. Этот change уточняет четыре его требования; новые
  формулировки записаны в design, раздел D11, и оформляются как MODIFIED при sync:
  - «Шесть областей с устойчивой идентичностью» — семь областей, workspace как
    локальный проект;
  - «Продолжение задачи читается напрямую» — ключ назван точно: копия ветки и цикл;
  - «Старый контекст не становится новым» — автоматический переход с отказом
    первой записи после смены цикла или проекта (осознанное ослабление);
  - «Поиск и сохранение не превращаются в фоновую фабрику контекста» — standing
    query заменён выдачей `memory_status`.

## Impact

- **ITL, корневое приложение:** `templates/ai-rules-overlay/AGENTS.md` (ядро вместо
  строки про память), запись `AGENTS.md` в `templates/ai-rules-overlay/sections.json`.
- **controlled fork `ai_rules_1c`, ветка апгрейда:**
  - корень `AGENTS.md`, пересобранный из upstream и приложения;
  - `content/rules/project-memory.md`;
  - потолок корня в `tools/validate-rules.ps1`;
  - запись `ITL-SCOPED-MEMORY-001` в ledger, clause hash и `rulesCandidateCommit` в
    `assets/scoped-memory-policy.json`, пины форка.
- **ITL, код:**
  - `.agents/skills/1c-workflow/scripts/lib/agent-1c.memory.ps1`;
  - `agent-1c.memory-context.ps1`;
  - `scripts/cognee-memory-mcp.ps1` (схемы и описания инструментов, перечитывание
    привязки);
  - lifecycle reset и применение контекста реестра (вызовы `Sync-ItlMemoryContext`);
  - вывод `vibecoding1c-mcp-status` и `/itl-check`;
  - `references/scoped-memory.md`;
  - `tests/pester/ScopedCogneeMemory.Tests.ps1`;
  - бюджеты в `tests/pester/ParserDocsBudgets.Tests.ps1`.
- **Сервер Cognee 1.6.5:** без изменений. Заметка создаётся отправкой файла вместо
  текстового поля. Используются `name`, `updatedAt` и `id` из листинга датасета.
  Квалификация: [evidence](evidence/metadata-qualification-2026-11-11.md).
- **Установленное состояние:** новые поля привязки, датасеты workspace локального
  проекта и `host`, файлы журнала и архива pending. Миграции данных нет: на сервере
  нет ни одного датасета workspace. Привязка дополняется на месте с однократной
  сменой `bindingId`.
- **Architecture checkpoint обязателен; одобрен пользователем 2026-11-11.** Причины: растут
  правила, которые агент держит в контексте всегда, и описания инструментов;
  появляется общее состояние на уровне машины (`host`); дополняется установленная
  привязка.
