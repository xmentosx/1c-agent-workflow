# Приёмка СППР MCP

Этот план описывает будущую проверку реализации. Подготовка документов и `openspec validate` не подтверждают работу MCP. Каждое свидетельство реализации должно указывать source commit, версию компонента, время, конфигурацию корпуса/embedding-профиля и способ воспроизведения; секреты и полный текст закрытых карточек в Git не сохраняются.

## Уже полученные свидетельства

| Проверка | Результат и граница доказательства |
|---|---|
| OData с `dev-ermakov`, стандартная авторизация 1С | `$metadata` и ограниченные GET успешны. Это не массовый сбор и не проверка всей схемы. |
| Область PM5 | UUID подтверждён; 4 392 непомеченных объекта в семи основных типах. Шаги и общие LCM-объекты ещё не посчитаны. |
| Тексты и связи | Выборочно найдены реализации на строках ТП–идея и XDTO FormattedDocument. Полное покрытие форматов не проверено. |
| Code/Graph | Подтверждено использование remote query embeddings и кеша Code как ориентира. Новый MCP не создан. |
| Веб-публикация | HEAD корня вернул 200. Навигация к конкретной карточке не проверена. |

## Проверки реализации

В таблице «локально» означает синтетические данные и управляемые ответы HTTP. Они проверяют поведение без отправки реальных карточек OpenRouter. «Хост» означает отдельно разрешённую установку/приёмку на `dev-ermakov`. Повторно опрашивать живую базу вместо точного воспроизводимого regression-теста не требуется.

| ID | Уровень, сценарий | Наблюдаемое доказательство успеха |
|---|---|---|
| A01 | Локально: разрешённый PM5, чужой проект, шаг с владельцем-процессом, функции двух видов, папки и завершённые идеи | В поиске и чтении только допустимые типы/владельцы; завершённые карточки сохранены, папки отмечены отдельно. HTTP-фикстура содержит уникальные запрещённые строки и считает попытки чтения: чужой текст не запрошен, не сохранён и не отправлен provider-двойнику. |
| A02 | Локально: LCM-цикл, два корня, общий статус, чужая обратная ссылка | Конечный обход сохраняет корректные пути включения; нет полного чтения справочника/чужой карточки. Отзыв одного корня сохраняет второй; отзыв последнего закрывает выдачу и embeddings немедленно. |
| A03 | Локально: смена allowlist во время embedding-пакета, поиска, продолжения и отката | После принятия новой политики нет новых отправок/выдач отозванного текста; курсор старой политики отклонён; старое поколение не возвращает старые права. Уже отправленный до изменения пакет отдельно учтён. |
| A04 | Локально + выборочная проверка адаптера: все разрешённые поля и отсутствующие реквизиты | Проекции исключают секретные поля. Различимы empty/not-applicable/unreadable; статусы, Mantis, разработчик/тестирующий и оба спринта проверены на типах, где существуют. Контрольные секреты отсутствуют в журнале, SQLite, MCP и HTTP-телах provider-двойника. |
| A05 | Локально: обычный текст, FormattedDocument, длинный текст, неизвестный XDTO, malformed XML, внешняя сущность | Читаемый текст и абзацы совпадают с эталоном без UUID разметки; неизвестный формат отмечен как пробел покрытия; внешние обращения отсутствуют; ограничения размера работают с понятной причиной. |
| A06 | Локально: одна идея в двух ТП, несколько строк, полиморфная ссылка | Два различных текста реализации находятся и читаются со своими источниками; число строк и направление связей сохранены; неподдержанный тип не превращён в идею. |
| A07 | Локально: ID/version сверка, обновление строки и общей зависимости, удаление, пометка и перенос проекта | Только успешный полный обход публикует ожидаемый состав/тексты; неизменённые фрагменты не вызывают embeddings. Изменение общей зависимости обнаруживается независимо от версии ссылочной карточки. |
| A08 | Локально: HTTP 401/403, таймаут средней страницы, повторы страниц, конкурентное редактирование | Ошибка не становится удалением; неполный снимок не активируется. Нет потерянных/дублированных ключей при заявленном алгоритме пагинации; нестабильная карточка повторяется ограниченно либо сохраняется прежнее поколение с диагностикой. |
| A09 | Локально: одинаковый текст, изменённый текст, несовместимый профиль, неверная размерность | Provider-двойник подтверждает экономию вызовов для совместимых фрагментов; старый вектор не прикрепляется к новому тексту; смешанное пространство отклоняется; состояние покрытия честное. |
| A10 | Локально: LRU, eviction, перезапуск, новый профиль и новая генерация | Число вызовов query embeddings соответствует попаданиям/промахам; размер ограничен; кеш не переживает рестарт. При повторном запросе вектор прежний, а результат соответствует новой генерации. |
| A11 | Локально: недоступны источник и/или OpenRouter | Последняя копия читается; кешированный запрос использует доступную семантику, новый — точный/лексический поиск; причины, возраст и покрытие видны. Дозаполнение векторов не вызывает полный сбор источника. |
| A12 | Локально: точный ID/Mantis, смысловой запрос, сочетания фильтров, большие карточки и циклический граф | Точное совпадение объяснимо; фильтры применены ко всем каналам; весь текст/все реальные связи достижимы через ограниченные страницы; top-k не выдаётся за полный обход. |
| A13 | Локально: поколение меняется между страницами и удаляется после срока хранения | Каждый ответ однороден; старый курсор либо продолжает удержанную копию по текущей политике, либо даёт инструкцию начать заново; данные не смешиваются. |
| A14 | Локально + хост: два сборщика, остановка в staging/при публикации, нехватка диска, перезапуск контейнера | Единственный writer; ни разу не открыта частичная БД; активная копия восстановлена без изменения текущего allowlist. Доказана работа атомарного манифеста через фактическое Windows/Docker монтирование. |
| A15 | Локально + хост: ночь, день, пропущенный запуск, открытый/отключённый/завершённый сеанс | Полный опрос идёт только в установленное окно и при допустимом сеансе; вход/рестарт днём не запускает догоняющий scan; выход останавливает сбор без порчи индекса; MCP продолжает читать последнюю копию. |
| A16 | Локально + хост: кириллица и пробелы в пути, кириллический логин | Точный Unicode round-trip через общий процессный транспорт, отсутствие mojibake и подмены аргументов. Не использовать ASCII-путь как замену исходному воспроизводителю ошибки. |
| A17 | Локально + хост/UI: ссылки для каждого типа, эталоны из самой 1С, переименование | Сначала побайтовые/структурные эталоны ссылок; затем установленный и веб-клиент открывают тот же тип/UUID в нужной базе. Проверены поиск, карточка и списки связей. HTTP 200 корня и наличие URL в JSON не заменяют это свидетельство. |
| A18 | Хост: регистрация через существующий proxy и два MCP-клиента | Успешны initialize → notifications/initialized → tools/list, поиск, чтение, продолжение связей и статус; оба клиента имеют одинаковый разрешённый корпус. Нет произвольных write/SQL/OData/full-scan инструментов. |
| A19 | Хост: установка, восстановление и отключение нового компонента | Сравнение настроек/состояния до и после показывает неизменность моделей, данных и расписаний Code/Graph, BookStack и Mantis; новый компонент можно отключить отдельно. |
| A20 | Хост: первый индекс и повторная ночь без изменений | Сохранены количества объектов/строк/фрагментов по типам, пробелы извлечения, покрытие vectors, число HTTP-вызовов/байты/ошибки, время фаз, фактическое потребление токенов/стоимость. Повтор неизменённых текстов не оплачивается заново. |

## Приёмка пользовательского результата

После установки выбрать реальные PM5-примеры с заранее проверенными в СППР ожидаемыми карточками и связями. В контролируемом локальном отчёте хранить типы/UUID и ожидаемые цепочки; не публиковать полный корпус вместе с тестами.

1. По номеру Mantis найти связанную идею/ТП, получить актуальные статусы, разработчика, тестирующего и спринты там, где эти поля существуют.
2. По описанию проблемы без точного заголовка найти релевантную карточку, затем перечислить все её ТП/идеи и тексты реализации через фактические связи. Сверить результат с исходными строками СППР, включая один пример «идея в нескольких ТП».
3. Пройти цепочку через процесс/шаг/системную функцию и связанную LCM-проблематику/решение. Отдельно показать реально записанную связь и смысловую рекомендацию.
4. Открыть каждый участвующий тип обеими навигационными ссылками. Проверить infobase, тип и идентичность объекта, а не только похожий заголовок.
5. Повторить запрос после обновления карточки/удаления тестовой записи, выполненного оператором в разрешённом тестовом контексте: вектор запроса переиспользуется, состав результата обновляется. Сам MCP не создаёт и не меняет записи в рабочей СППР; если безопасной записи нет, живое свидетельство ограничивается естественным изменением, а полный сценарий остаётся доказанным фикстурой и явно отмеченным.

Зафиксировать не менее 10 предметных запросов из этих сценариев: точные и смысловые, короткие и требующие обхода. Для каждого указать ожидаемые релевантные объекты, фактическое место в top-10, пропуски и причину. Пропуск обязательной карточки/связи требует диагностики источника, извлечения, области или ранжирования; успешный один пример не доказывает качество всего поиска.

Измерить раздельно p50/p95 для тёплого кеша, cache miss с OpenRouter, чтения и обхода; не менее 30 запросов на режим после прогрева, с явной конкуренцией клиентов и размерами страниц. Сохранить объём корпуса/векторов, память, диск и загрузку хоста. Целевые задержки пока не были согласованы числом: отчёт должен позволить оценить пригодность быстрого поиска; при неприемлемой задержке обосновать локальную оптимизацию или смену хранения до объявления live-приёмки. Не выдавать сетевую задержку OpenRouter за скорость локального индекса.

## Условная проверка инкрементального режима

Не входит в обязательную реализацию ночного режима. Если обнаружится надёжный серверный механизм изменений, отдельно доказать: создание, изменение каждого индексируемого поля и табличной части, изменение общей зависимости, пометку/удаление, перенос в другой проект, перезапуск после пропуска и повтор одного события. Измерить успешное отражение за ≤15 минут и подтвердить по журналу HTTP, что это не полный обход. До такого свидетельства статус остаётся nightly reconciliation.

## Завершение этапов

- Постановка: все артефакты созданы, `openspec validate add-sppr-knowledge-mcp --strict` проходит; implementation checkboxes остаются пустыми.
- Реализация: локальные сценарии пройдены, инструкция эксплуатации и откат готовы, непроверенные live-сценарии перечислены. Обычная исходная доставка — единый commit и `RegisterChange` по правилам репозитория; её статус читается у helper, а не дублируется checkbox.
- Развёртывание/приёмка: только после соответствующего разрешения и фактических A14–A20/пользовательских сценариев. Если проверка заблокирована или покрытие неполно, задача остаётся открытой с точной причиной. Архивирование change до завершения согласованной приёмки недопустимо.
