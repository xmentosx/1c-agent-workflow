## Context

СППР хранит содержание доработок в карточках и табличных частях. Для ответа на вопрос о проблеме недостаточно найти похожий текст: требуется собрать технические проекты, идеи и описания реализации на каждой связи, показать текущие реквизиты и открыть оригиналы. Контекст и доказательства перечислены в [proposal.md](proposal.md); специфичные термины — в [CONTEXT.md](../../../docs/sppr/CONTEXT.md), граница внешней обработки — в [ADR-0001](../../../docs/adr/0001-sppr-corpus-access-and-external-embeddings.md).

Источник: `Srvr="pskov";Ref="itland_work_SPPR";`, публикация `http://pskov.itland.local:8080/itland_work_SPPR/odata/standard.odata/`. Чтение выполняется с `dev-ermakov` под стандартным пользователем 1С; пароль остаётся во внешнем конфиге. Сборщик работает только при открытом пользовательском Windows-сеансе. Все допущенные пользователи MCP видят одинаковый разрешённый корпус.

Проверено 4 392 непомеченных объекта в семи основных типах PM5; шаги и общие объекты ещё не посчитаны. Метаданные дают `DataVersion`, но надёжная выборка изменений без полного перечисления не обнаружена. XML/XDTO-описания и полиморфные ссылки требуют явного адаптера.

## Goals / Non-Goals

**Goals:**

- Поиск по смыслу, точным идентификаторам и реквизитам; полный обход записанных связей с продолжением.
- Индексация только разрешённого корпуса с доказуемым происхождением общих объектов.
- Читаемые описания, реализация идеи в каждом ТП, актуальные структурированные поля и две ссылки на каждый объект.
- Ограниченные расходы на embeddings, видимая свежесть, сохранение поиска при сбое источника или OpenRouter.
- Размещение в существующей инфраструктуре MCP с отдельными данными и расписанием компонента.

**Non-Goals:**

- Запись в СППР, индивидуальные права внутри общего корпуса, история карточек и удалённых версий.
- Индексация других проектов, функций механизмов, файлов вложений, страниц Mantis или документов 1С:ДО.
- Автоматическое признание смыслового сходства фактической связью.
- Пятнадцатиминутный полный опрос, общая перестройка Code/Graph или изменение их embedding-профилей.
- Реализация, установка или публикация endpoint в рамках подготовки этой постановки.

## Decisions

### 1. Отдельный компонент и один владелец состояния

Компонент `vibecoding1c-mcp-host/sppr-mcp/` содержит адаптер OData, нормализацию, индексатор и HTTP MCP на существующем Python/FastMCP маршруте хоста. Используются существующий реестр и прозрачный `toolsListProxy`; ответы имеют основной `structuredContent` и короткий текст без повторения всего JSON. Установленный workflow обнаруживает `sppr` в реестре и формирует подключение `sppr-knowledge` через существующий клиентский адаптер. Для этого сервера выбирается remote provider; сборщик и пароль 1С не копируются в проекты.

Сборщик — Windows CLI, запускаемый задачей с `InteractiveToken` существующего пользователя. Открытый, в том числе отключённый от RDP, сеанс допускает работу; после выхода пользователя сбор не продолжается. Конкретные настройки задачи и поведение при выходе проверяются на хосте. Пароль 1С не используется как пароль Windows. MCP в контейнере может читать последний индекс независимо от сеанса сборщика.

У компонента собственные конфиг, данные, журнал и блокировка одного сборщика. Существующий установщик хоста владеет регистрацией его контейнера и задачи; индексатор не управляет соседними MCP. Watchdog не получает обязанность сканировать СППР. Встроенный ночной маршрут Code/Graph для `sourcePath`/dump не расширяется этим сбором.

По архитектурному контракту это локальное состояние нового владельца. Новая Windows-служба, повышение прав, общий координатор восстановления или блокировка чужих операций не входят в дизайн. Если фактическая установка потребует такого расширения, сначала нужен checkpoint по `docs/package-architecture.md`; наличие этой постановки его не заменяет.

### 2. SQLite и неизменяемые поколения индекса

Для исходного объёма предлагаем SQLite: таблицы объектов, полей, фрагментов, связей и оснований включения; FTS5 для текста; нормализованные векторы float32 и пакетный cosine/dot-product через NumPy. Это позволяет держать реквизиты и связи в одной модели без отдельного векторного или графового сервиса. Реальный объём фрагментов, память и задержка подлежат измерению; проверенные 4 392 карточки не равны числу векторов.

Альтернатива — отдельная векторная БД плюс графовая БД. Пока не доказано, что её эксплуатационная стоимость оправдана. При недостаточной производительности сначала измеряется узкое место; изменение хранения должно сохранять договорённые выдачу, связи и границу корпуса.

Windows-сборщик единолично готовит новое поколение SQLite во временном каталоге, завершает транзакции/WAL, проверяет целостность и публикует небольшой манифест активного поколения. MCP монтирует данные только для чтения и удерживает одно поколение на запрос/страницу. Между Windows и Linux нет совместной записи в открытый SQLite-файл. Замена манифеста и повторное открытие файлов через фактический bind mount проверяются на хосте; неподтверждённая атомарность не считается рабочей.

Публикация — только после полного успешного сбора источника в выбранной области. Предыдущее поколение остаётся доступным при прерывании; незавершённые staging-файлы не становятся активными. Очистка удерживает используемые поколения и ограниченный резерв для отката. Откат данных не отменяет текущий allowlist.

### 3. Идентичность, состав и принадлежность корпусу

Ключ объекта включает источник, метаданный тип и UUID, а не название. Allowlist содержит UUID проекта и ожидаемое имя для проверки; начальное значение — `76bcfc1f-e8c2-4cd6-80ef-997b99bca476`, «Кейс проект PM5». Переименование не меняет идентичность. Папки сохраняются как папки для иерархии; их количество отделяется от карточек.

| Бизнес-тип | EntitySet / путь допуска |
|---|---|
| Технический проект | `Catalog_ТехническиеПроекты`, владелец — проект |
| Идея | `Catalog_Идеи`, владелец — проект |
| Процесс | `Catalog_Процессы`, владелец — проект |
| Шаг процесса | `Catalog_ШагиПроцесса`, владелец → разрешённый процесс → проект |
| Раздел проекта | `Catalog_РазделыПроекта`, владелец — проект |
| Функция системы | `Catalog_ФункцииСистемы`, владелец — проект |
| Целевая задача | `Catalog_ЦелевыеЗадачи`, владелец — проект |
| Протокол | `Document_итлПротоколВстреч`, поле `Проект_Key` |
| Решение, проблематика, функциональное решение | `Catalog_LCM_Решения`, `Catalog_LCM_Проблемы`, `Catalog_LCM_ФункциональныеРешения`; явная связь от допущенного объекта и разрешённое продолжение по связям LCM |

Проверка допуска предшествует чтению содержимого и каждому внешнему embedding-запросу. Для ссылки на объект другого проекта разрешена заглушка с типом/UUID и причиной недоступности без чтения его названия и текста. Принадлежность проверяется минимальной проекцией; это не разрешение выгружать чужую карточку целиком. `Catalog_ФункцииМеханизмов` исключён.

Общие LCM-объекты не имеют своего проекта: хранят полный разрешённый текст и путь от допущенного корня. Циклы обходятся с учётом посещённых типизированных ключей. Нельзя перечислить весь LCM-справочник или через обратные связи включить карточки иных проектов. Названия статусов, спринтов, участников и других нужных справочных значений читаются адресно. Общий объект остаётся допустимым, пока существует хотя бы одно разрешённое основание.

Allowlist — оперативная политика, независимая от активного поколения. При исключении проекта его данные и утратившие основание общие объекты сразу перестают выдаваться и отправляться наружу; физическая очистка выполняется компонентом. Политика повторно проверяется перед отправкой пакета, а активные ответы/курсоры инвалидируются при её изменении. Уже отправленные до изменения запросы отозвать невозможно. Добавленный проект появляется только после успешного сбора.

### 4. Поля, форматированный текст и связи

Адаптер использует фиксированные разрешённые `$select` и табличные части по типам, не произвольный GET всех реквизитов. Контракт включает статус работы, заметки, разработчика, тестирующего, тип, Mantis, спринты, подробное описание, цели/концепцию, реализацию и необходимые ссылки. Значение «реквизита нет у этого типа» отличается от пустого значения и ошибки чтения. Служебные секреты исключены: например, метаданные ТП содержат поле пароля хранилища, которое не должно читаться в бизнес-проекции.

Base64/XDTO разбирается ограниченным XML-парсером без внешних сущностей и загрузки ресурсов. Из `FormattedDocument` извлекаются текстовые узлы, абзацы и значимые ссылки без служебных UUID разметки. Текст и исходный путь поля сохраняются для цитирования. Неизвестный формат отражается в покрытии извлечения; двоичные данные не отправляются в embeddings, молчаливое «описание пустое» запрещено. Оригинальные файлы и внешние страницы не загружаются.

Связь хранит тип, направление, пару ключей, исходный путь и идентичность строки. В `Catalog_ТехническиеПроекты_ИдеиИОшибки` реализация и комментарий относятся к конкретной паре ТП–идея; они не перезаписывают единственное поле идеи. Несколько строк и ТП остаются различимыми. Полиморфное `Идея_Type` проверяется; неожиданный тип помечается неподдержанным и не расширяет список индексируемых сущностей автоматически.

Описание делится на фрагменты по полям/абзацам с ограниченным перекрытием; связь может иметь собственные фрагменты и ссылку на карточку ТП. Смысловое сходство создаёт только результат поиска с оценкой, а не ребро в таблице фактических связей.

### 5. Ночная сверка и честная свежесть

Базовый режим — полный ночной обход идентификаторов, версий, принадлежности и пометок удаления только выбранного проекта/разрешённых зависимостей. Затем читаются изменённые бизнес-поля и табличные части. Неизменившиеся фрагменты сохраняют векторы. Это экономит embeddings и передачу полных карточек, но остаётся полным перечислением источника, поэтому не запускается каждые 15 минут.

Изменения версий общих справочных значений и LCM-зависимостей учитываются отдельно от версий ссылающихся карточек. Отсутствие объекта подтверждается только завершённой сверкой; ошибка страницы, таймаут или отказ авторизации не являются удалением. При удалении, пометке или смене проекта объект и недействительные связи исключаются в новом поколении.

Порядок страниц должен быть стабильным, с дедупликацией по ключу и обнаружением неполного обхода. Проверка версии вокруг чтения изменяемой карточки и ограниченный повтор защищают от смешивания её реквизитов/строк. OData не обещает общую транзакционную фотографию базы: сохраняются начало/конец сбора и версии прочитанных объектов, а не фиктивное единое время состояния всей СППР.

Инкрементальный режим допустим после доказательства фильтруемого журнала/маркера, который покрывает создание, изменение полей и строк, удаление, перемещение и зависимые общие значения. Тогда задержка успешного обновления — не более 15 минут при доступных зависимостях. `DataVersion` и дата изменения статуса сами по себе такой выборки не доказывают.

Ночное окно и часовой пояс задаются при установке. Начальная загрузка и догоняющий полный обход вне окна не запускаются автоматически при входе пользователя/рестарте. Уже начатый обход при завершении окна прекращает обращения к источнику и сохраняет предыдущее поколение. Отдельный явный запуск вне окна требует отдельного распоряжения оператора.

### 6. Embeddings и кеш запросов

Выбран OpenRouter `qwen/qwen3-embedding-8b`; наружу передаются тексты допущенного корпуса и пользовательский поисковый запрос. Утверждённая граница допускает весь текст выбранной карточки, включая цитаты, и не обещает автоматического смыслового удаления упоминаний других проектов. Это не даёт права загружать сами чужие карточки.

Embedding-профиль фиксирует provider/model, фактическую размерность, инструкцию для запроса/документа, нормализацию и версию извлечения/разбиения. Размерность и формат ответа проверяются при реализации. Вектор повторно используется по хешу текста и совместимому профилю. Незаметная замена модели или смешивание несовместимых пространств запрещены.

Кеш векторов запросов — ограниченный LRU в памяти MCP, начальная ёмкость 256 с настройкой. Ключ включает текст запроса и embedding-профиль. После перезапуска кеш пуст. Результаты поиска не кешируются: повторный запрос с прежним вектором читает текущее поколение и текущий allowlist. Логи не содержат полный текст запросов по умолчанию.

При недоступности OpenRouter используются совместимые уже вычисленные векторы. Для нового запроса доступен точный/лексический поиск с явным признаком деградации. Новый полностью собранный корпус можно опубликовать с неполным покрытием векторов: изменённый текст никогда не сопоставляется со старым вектором. Ответ сообщает покрытие; недостающие embeddings дозаполняются из сохранённых разрешённых текстов без новой полной выгрузки. Ошибка сборщика источника, в отличие от недоступного провайдера векторов, не публикует частичный корпус.

### 7. Четыре читающих инструмента MCP

| Инструмент | Контракт |
|---|---|
| `search_sppr` | Запрос, разрешённые типы и структурированные фильтры; точные совпадения ID/Mantis, FTS и семантические кандидаты объединяются с объяснимыми источниками совпадения. Top-k не объявляется всей цепочкой объектов. |
| `read_sppr_object` | Типизированный ключ, выбранные разделы/продолжение; полные доступные поля и тексты, включая пояснение отсутствия/ошибки. |
| `list_sppr_relations` | Ключ, тип/направление ребра, ограниченный обход или продолжение; реальные связи с текстом строк, границей корпуса и полнотой перечисления. |
| `sppr_index_status` | Поколение, активный allowlist, начало/конец успешного сбора, режим, покрытие типов/полей/векторов, последний исход и следующая допустимая попытка. |

Все инструменты ограничивают размер страницы и ответа. Курсор фиксирует поколение, параметры и политику; при недоступности поколения или изменении политики выдаётся понятное предложение начать чтение заново. Циклы и пределы обхода видны через `has_more`/причину остановки; завершённый обход означает полноту только записанных связей указанной области. Произвольных SQL/OData и инструментов записи или запуска полного скана в общем MCP нет.

Каждый результат имеет типизированный ID, название, принадлежность/основание, релевантный фрагмент и поле-источник, навигацию, время наблюдения, поколение и предупреждения о покрытии. Общие реквизиты отсутствующих типов не выдумываются. Статус не раскрывает секреты и содержимое недопущенных объектов.

### 8. Навигация из каждого представления объекта

Единый генератор строит внутреннюю ссылку 1С, внешнюю ссылку для установленного клиента с привязкой к `pskov/itland_work_SPPR` и ссылку веб-клиента на тот же объект. Веб-база задаётся отдельно: `http://pskov.itland.local:8080/itland_work_SPPR/`. Ссылка OData на строку не заменяет пользовательскую навигацию.

Формат метаданного имени и кодирование UUID проверяются по ссылкам, сгенерированным самой 1С, включая её порядок байтов/представление. Простое удаление дефисов UUID не принимается без доказательства. Название карточки и секреты не участвуют в адресе. Во всех результатах поиска, карточках и списках связей один объект имеет одинаковые две пользовательские ссылки. Для заглушки вне корпуса допускается навигация по уже известному типу/UUID без чужого текста; если тип невозможно преобразовать, причина отсутствия ссылки явна.

HEAD веб-публикации подтверждает доступность корня, но не открытие объекта. Приёмка требует открыть конкретные карточки обоими способами, в правильной базе и после переименования. Запуск 1С для проверки выполняется через допустимый для среды механизм, без обхода существующего ограничения сеансов.

## Risks / Trade-offs

- Общий доступ переносит границу конфиденциальности на включение проекта и допуск к MCP. Ошибка фильтра до внешнего запроса необратима; проверки корпуса выполняются до извлечения/embedding, тестируются ловушками чужих данных.
- HTTP-публикация и стандартная авторизация требуют защиты конфигов и исключения учётных данных из URL/логов. Изменение сетевого транспорта не выполняется скрытно в установке этого компонента.
- Открытый сеанс ограничивает свежесть: ночью без сеанса обновления не будет. Индекс остаётся доступным, просрочка видна.
- Неизвестные форматы XDTO и полиморфные ссылки могут дать неполное покрытие, которое должно быть измерено и показано до заявления готовности.
- Полный ночной обход увеличивает время OData-чтения; число запросов, байты, длительность и стоимость embeddings измеряются, чтобы выбрать окно и лимиты без выдуманных оценок.
- Локальный точный векторный поиск и копирование поколений просты в сопровождении, но требуют измерить память, диск и p50/p95 на полном разрешённом корпусе.

## Migration Plan

1. Реализовать компонент и контракт конфигурации в изолированном checkout; существующие серверы не переустанавливать и не переводить на другую модель.
2. Проверить локальные сценарии из [test-plan.md](test-plan.md), подготовить установку и откат; source commit и `RegisterChange` подтверждают только локальную доставку исходного изменения.
3. После отдельного разрешения на установку настроить внешний секрет 1С/OpenRouter, UUID allowlist, ночное окно/часовой пояс и лимиты на `dev-ermakov`. Не копировать пароль из чата в репозиторий или постановку.
4. Выполнить первый сбор в разрешённое окно/по явно согласованному разовому запуску, проверить покрытие, стоимость, ссылки и расследование на реальных примерах. Подключение MCP считать подтверждённым после `initialize → notifications/initialized → tools/list` и функциональных вызовов.
5. При отказе отключить только новый MCP/задачу и вернуть предыдущее поколение с текущим allowlist. Остальные серверы и СППР не требуют отката. OpenSpec архивируется только после выполнения согласованных задач и приёмки.

## Open Questions

Это точки проверки реализации, а не повторное интервью о принятых требованиях:

- Полное покрытие полей и XDTO-форматов каждого типа, допустимые типы полиморфных ссылок и правила изменения `DataVersion` табличных частей.
- Реальная кардинальность шагов/LCM/фрагментов и нагрузка полного скана; устойчивость пагинации при параллельном редактировании СППР.
- Наличие поддерживаемого серверного механизма выборки изменений; до доказательства остаётся ночной режим.
- Доступный runtime Windows, поведение задачи при выходе пользователя и атомарное переключение поколений между Windows и контейнером.
- Точный формат и фактическое открытие клиентских/веб-ссылок для всех поддержанных типов.
- Измеренные время поиска, расход памяти/диска, длительность и стоимость первого/повторного индекса. План приёмки фиксирует методику и отдельно согласует порог, если измерения потребуют изменения архитектуры.
