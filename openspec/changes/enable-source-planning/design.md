## Context

В исходном репозитории есть контракты архитектуры и source delivery, но нет собственного OpenSpec workspace и навыков grill. Этот change подготовлен вручную через существующий OpenSpec CLI 1.4.1 после двух раундов grill; он не доказывает автоматическую доступность будущих навыков. База пилота — `origin/develop@6633f5bc229b676675a77693206f0c901f5d4d42`; работа изолирована в ветке `codex/source-planning-pilot`.

## Goals / Non-Goals

**Goals:** сохранить выбор процесса за пользователем; сделать согласованное достаточное решение и доказательства приёмки доступными следующему контексту Codex; использовать стандартные инструменты без собственной системы задач.

**Non-Goals:** обязательный OpenSpec, полный набор 1С rules/agents в исходном репозитории, изменение установленных проектов, новый runtime/координатор/gate, обещание исключить регрессии за счёт документов.

## Decisions

### 1. Repository-local навыки с явным выбором процесса

Размещаем навыки в `.agents/skills`, без изменений пользовательских настроек Codex. Для пилота достаточно `grill-me`, `grill-with-docs`, их зависимостей `grilling` и `domain-modeling`, а также четырёх канонических OpenSpec навыков: `openspec-explore`, `openspec-propose`, `openspec-apply-change`, `openspec-archive-change`. Отдельные алиасы `$opsx-*` сейчас не добавляем: они дублируют доступные точки входа.

Source-local invocation metadata сохраняет явный выбор: агент может предложить любой подход, но не включает его вместо пользователя. `allow_implicit_invocation: false` применяется к этим восьми навыкам; внутренние зависимости grill загружаются выбранным wrapper. Это не отменяет уже данное пользователем разрешение продолжать выбранный этап.

Альтернатива — личная глобальная установка — не воспроизводится из checkout. Собственный plugin/installer/cache для восьми наборов инструкций добавляет ненужный механизм.

### 2. Переиспользование зависимостей без 1С overlay

Четыре общих навыка grill берём из immutable controlled fork commit `451c5a52e5b614c67406445d4af4b636da043aec` вместе с необходимыми sibling references и атрибуцией. Сами инструкции не редактируем в workflow; изменение общей механики остаётся задачей их владельца. Потребительская политика invocation отделена от импортированных текстов.

Для OpenSpec используем generic upstream templates из `@fission-ai/openspec@1.4.1`. В этой версии `dist/core/shared/skill-generation.js` предоставляет `getSkillTemplates` и `generateSkillContent`: генерируем только explore/propose/apply/archive в repository-local каталоги. Это разовая подготовка checked-in зависимостей по зафиксированному рецепту, без нового исполняемого установщика.

Не используем fork bundle с 1С overlay. Не запускаем обычный `openspec init --tools codex`: изученный адаптер 1.4.1 записывает команды в глобальный Codex prompts и выбирает `.codex` как skill directory. Для пилота нужны только project-local навыки. Не запускаем автоматический `openspec update`.

Версия CLI, commit grill, исходные пути и рецепт обновления фиксируются в `docs/source-planning.md`; checkout содержит готовые инструкции и не зависит от наличия локального `D:\Git` автора. CLI остаётся явным developer prerequisite. При его отсутствии grill доступен, OpenSpec сообщает о недоступной предпосылке и не имитирует выполненную валидацию.

### 3. Один владелец правил постановки

`docs/source-planning.md` владеет выбором процесса, пятью элементами достаточной постановки и передачей результатов. Корневой `AGENTS.md` содержит только короткое правило предложения и ссылку. `openspec/config.yaml` выбирает стандартную `spec-driven` схему и указывает на source contracts, без копирования их содержимого или новой схемы.

Grill отвечает за обнаружение неопределённости; OpenSpec хранит выбранные требования, дизайн и задачи. `CONTEXT.md` создаётся только для реально согласованных специфичных терминов, ADR — для трудно обратимого выбора с реальным trade-off. Этот пилот не требует пустого glossary или отдельного ADR: принятые решения обратимы и уже объяснены здесь.

### 4. Существующая архитектура и доставка сохраняют ответственность

После выбора OpenSpec его статус не заменяет архитектурный checkpoint, подтверждение реализации, Targeted или публикацию. В применении сохраняется путь из `docs/local-quality-gate.md`: законченная доработка → один связный commit → RegisterChange. Archive описывает завершённый change; регистрация не выдаётся за доставку пользователям.

Уточнение по результату пилота: checkbox-задачи заканчиваются реализацией и приёмкой. Обязательное commit/RegisterChange сохраняется отдельным действием доставки с доказательством в общем Git ledger; checkbox «этот commit уже зарегистрирован» потребовал бы изменить сам проверенный commit. Отдельный журнал состояния доставки не вводится.

Добавленные source-only навыки, config и docs не включаем в `Get-WorkflowPackageCopyDirectoryPaths`, `Get-WorkflowUpdateManagedPathSpecs` или bootstrap managed-copy. Проверка границы должна покрывать фактический список файлов копирования, а не только отсутствие названия в одном файле. В установленном проекте уже могут быть одноимённые навыки от controlled fork; это не разрешает заменять их source-only вариантом.

### 5. Приёмка по сценариям, соразмерная задаче

Проверяем фактическое обнаружение и поведение навыков в свежем контексте Codex, прямой путь для ясного бага, предложение при существенной неопределённости, передачу grill → OpenSpec и сохранение source boundaries. Статическая проверка файлов не считается поведением нового контекста.

Ретроспектива `test-plan.md` связывает известный сбой обновления с недостающей формулировкой конечного результата. Это проверка полезности постановки, не live replay и не доказательство предотвращения всех регрессий. Выявленные изменения исполнимых gates оформляются отдельно.

## Risks / Trade-offs

- Checked-in зависимости требуют ручного обновления → сохранять origin/version и воспроизводимый рецепт; не изменять импортированные инструкции на месте.
- Восемь навыков увеличивают metadata context → измерить UTF-8 bytes новых name/description и прирост корневых правил; подробности загружать по требованию. Не копировать каталог 1С правил.
- Стандартный apply может преждевременно считать задачу готовой → source routing и acceptance требуют доказательств из `test-plan.md`, включая незавершённые проверки; галочки задач не являются доказательством.
- Ручной bootstrap пилота создаёт благоприятный контекст → проверять доступность в новой сессии и не считать эту историю чата независимой проверкой.

## Migration Plan

Миграции установленного состояния нет. После реализации новые checkout/worktree получают checked-in навыки. Для rollback удаляется source-only подключение; документы change остаются историей договорённостей. Существующие source gates и клиентские настройки не восстанавливаются вручную, поскольку этот change их не меняет.

## Open Questions

Неразрешённых пользовательских решений нет. Технические детали размещения и версии выбраны выше с rationale. Фактическая доступность новой сессии Codex и объём контекста проверяются в реализации; при невозможности проверки результат остаётся неподтверждённым, а не закрывается предположением.
