# Design

## Context

Мотивация и scope: [proposal.md](proposal.md). Базовый source commit: `c900620e6569ce4cec39e30abfa3f8ce2c150ce1`.

`Save-DevBranchCheckpoint` уже коммитит работу до refresh. `New-DevBranchCore` требует чистоту до создания worktree. `Assert-DevBranchLifecycleMergePostMerge` проверяет транзакцию и затем всё дерево; `Resolve-DevBranchLifecyclePostMergeHead` уже поддерживает ограниченное продолжение refresh по линейным потомкам recorded checkpoint. Это существующие владельцы, которые следует развить.

## Goals / Non-Goals

**Goals:** один контракт допуска по фазе; локальный коммит агента при необходимости; продолжение с независимыми изменениями; исходная операция как критерий успеха.

**Non-Goals:** общий автокоммит любого dirty-дерева, новая машина состояний, автоматический stash/reset/clean, публикация, изменение verification-policy или форка общих правил.

## Decisions

1. **Владелец исключений — `Ensure-GitIgnore`.** Корневой `/handoffs/` входит в template, fallback и обязательное дополнение для старого template. Сохраняются пользовательские строки и tracked-файлы. Локальный `info/exclude` допустим как адресное восстановление старой установки, не как параллельный постоянный менеджер. Не расширять специализированный `Ensure-Agent1cLifecycleLocksIgnored` на произвольные документы.
2. **Владелец допуска — существующий lifecycle, общий разбор — stateless core.** Получать Git-пути через существующий NUL-delimited helper. Разделять известные локальные артефакты, изменения входов этапа, доказанно независимые изменения и неустановленные случаи. Фаза передаёт свои source roots, исполняемый runtime, зависимости/управляющую конфигурацию и evidence inputs. Обычные docs допускаются только при непересечении с этими входами; неоднозначность возвращает агенту точную проверку, а не новое разрешение пользователя. Перед мутацией перепроверять входы; повторно использовать существующие fingerprint-контракты и не вводить постоянный реестр.
3. **Локальный коммит — действие агента в уже разрешённой задаче.** Перед branch creation подготовить точный pathspec после просмотра diff/index, сохранить unrelated staged/unstaged bytes и index entries. Если файл содержит смешанные правки и отделить их безопасно нельзя, объяснить конкретный конфликт. Штатный helper повторяется после коммита. Native OpenCode использует тот же preflight в Get-DevWorkspacePlan и повторяет свой itl_create_dev_workspace, сохраняя запрет внешней worktree-подмены. При незавершённом merge агент делает разрешённый repair/stage, а merge commit и state переход остаются у helper. Действующий полный checkpoint refresh не превращать в новую выборочную процедуру.
4. **После merge независимые изменения остаются на месте.** Для refresh/refresh-lite заменить blanket clean-check проверкой входов фазы после строгой проверки transaction/HEAD. Проверки branch/operation/parents/checkpoint/target и freshness сохраняются; не принимать произвольный HEAD лишь потому, что рабочее дерево чистое. Если нужен штатный repair, использовать существующий pending merge и его recovery. Не повторять master sync и не редактировать journal вручную.
5. **Продолжение использует имеющийся run result.** Заполнять существующие errorCategory, requiredAction, blockerOwner, blockerRequiresUserDecision, blockerRetryOriginalCommand и точные пути в ограниченной диагностике. Генерируемые команды всех клиентов выполняют agent-owned continuation и возвращаются к исходной команде. Повтор без изменения причин запрещён; при гонке пересматривается только изменившийся набор. Успешный `userReport` передаётся по действующему контракту.

Альтернативы: только ignore решает один симптом; общий `git add -A` включает чужую работу; удаление `Assert-CleanGit` теряет фазовые гарантии; общий recovery-менеджер дублирует существующий lifecycle. Выбран owner-local путь со stateless разбором.

## Architecture checkpoint

Это граница реализации, согласованная запросом пользователя применить данный OpenSpec. Инвариант: посторонние изменения не останавливают этап при сохранённых входах и идентичности операции. Все записи, ожидание, completion/cancel/recovery остаются у текущего lifecycle и его locks/journal; межвладельческая authority не расширяется. Чужие процессы не останавливаются, состояние других worktree не меняется. Нет новых locks, очередей, schema migration, elevation или always-on collector. Поддержка Windows/terminal sessions и клиенты сохраняются. Увеличение контекста ограничить профильной reference и короткой маршрутизацией команды; измерить bytes и время на том же workload. Новое пересечение с иным владельцем требует отдельного checkpoint до реализации.

## Risks / Trade-offs

- Ошибочная независимость → конкретные входы фазы, консервативная обработка неизвестного и отрицательные регрессии; расширение файла не является allowlist.
- Параллельная запись → повторная проверка входов и отсутствие автоматического захвата чужой работы.
- Старый тест требует отказа на любом dirty path → сохранить исходный `branch.txt` case и его preconditions, добавить явную классификацию; тест изменения входов остаётся красным до корректного repair. Изменение ожидания допустимо только для доказанного независимого случая.

## Migration Plan

Новая установка/обычный update доставляют исключение и runtime. Старые транзакции читаются без смены схемы и восстанавливаются через исходного владельца. Для уже блокированной старой установки агент использует штатный разрешённый коммит либо адресное исключение только untracked-отчётов, затем повторяет команду. Rollback возвращает старый runtime штатным package update; оставшееся ignore-правило не скрывает tracked-правки. Доставка отдельно от разработки: coherent commit + RegisterChange, без push/PM5 update в этой постановке.
