## Goals / Non-Goals

**Goals:** поиск решений с проверяемыми источниками; обычная дельта до пяти минут; управляемая запись через текущий API; сохранение доступных функций при отказе зависимостей; восстановление без повторного создания опубликованных объектов и без возврата удалённых локальных данных.

**Non-Goals:** обновление/патч Mantis; полный регулярный обход; OCR и поиск содержимого файлов; персональные ACL сотрудников; атомарная транзакция с Mantis; абсолютная защита от конкурирующих клиентов; изменение Code, BookStack, 1С lifecycle; удаление обращений/комментариев через новые инструменты; запуск работ в production в рамках подготовки proposal.

## Decisions

### 1. Один владелец и две локальные проекции

Mantis остаётся источником истины. SQLite является авторитетным локальным состоянием: документы и фрагменты, FTS, метаданные и фильтры, проектные checkpoint, версии содержимого, задания обновления проекции, tombstone, журнал записи и расход эмбеддингов. Zvec содержит восстанавливаемую векторную проекцию. Файлы скачиваются существующим владельцем вложений; получение файла не означает его текстовую индексацию.

В одной SQLite-транзакции обновляются фрагмент, его версия, FTS и намерение обновить/удалить вектор. Работник Mantis применяет намерение к Zvec идемпотентно; перед выдачей vector hit сверяется с текущей версией и доступностью в SQLite. Сбой между базами оставляет восстановимое намерение, а не ложную готовность. Поисковые checkpoint не зависят от завершения эмбеддингов: текст может быть свежим при неполной семантике. Это внутренняя работа одного сервиса, без отдельного брокера/общей очереди.

Идентичность фрагмента включает проект, обращение, тип источника, ID комментария/вложения, номер фрагмента и профиль обработки. Полный исходный текст нормализуется детерминированно и разбивается на ограниченные фрагменты; границы и ссылки на источник сохраняются. Хеш содержимого отделён от метаданных фильтра: изменение статуса не пересоздаёт эмбеддинги текста, переименование файла затрагивает только его имя. Устаревший хвост фрагментов после сокращения текста удаляется. Эмбеддинги привязаны к версии модели, размерности и правилам разбиения.

Альтернативы SQLite-only с полным перебором векторов и отдельная БД были рассмотрены в ADR 4. Выбран SQLite + Zvec ценой проверки согласованности; общая очередь с Code/BookStack не нужна и расширяла бы чужую runtime authority.

### 2. Дельта по изменению, а не по созданию

Каждый проект имеет собственные `initializing / catching_up / current / retrying / access_removed` и checkpoint по **`updated_at`**. Для нового проекта выполняется возобновляемая первичная загрузка всех доступных статусов. После неё проходит догоняющая дельта от начала загрузки; остальные проекты продолжают обслуживаться. Первичный полный импорт не превращается в регулярный полный обход.

Для текущего проекта используется проверенный REST `filter_id=any` с компактным `select`, страницы читаются от самых новых до сохранённой временной границы с перекрытием. Сначала сохраняется верхняя граница наблюдаемого окна; обращения новее неё относятся к следующему проходу. Времена приводятся к единой шкале с сохранением timezone сервера, а не локально трактуются как даты создания. Точный timestamp и множество обработанных ID/версий на границе сохраняются; нельзя пропускать записи только потому, что их время равно checkpoint.

Опрос без серверного snapshot не доказывает полноту одним проходом. Выполнение дедуплицирует ID, дочитывает всю граничную timestamp-группу, повторно сверяет недавний префикс и сохраняет прежний checkpoint, если смещение страниц не позволило подтвердить окно. Ограниченные по времени попытки продолжаются со статусом задержки; регулярное продвижение watermark при неполном окне запрещено. Реализация должна продемонстрировать сценарии движения страниц из test-plan; если фиксированного overlap недостаточно, увеличивается только недавнее окно либо выбирается иной подтверждённый API-способ. Полный обход и фиктивная гарантия не являются скрытым fallback.

Содержимое новых/изменённых обращений записывается в SQLite до атомарного продвижения checkpoint завершённого окна. При сбое повторное чтение безопасно благодаря хешам. Настраиваемый polling и ограниченная конкуренция проектов должны дать до пяти минут от обычного изменения до текстовой и семантической выдачи при исправных зависимостях и незаполненном бюджете. Время первичного наполнения измеряется отдельно.

Upstream 2.28.1 обновляет дату обращения при обычном добавлении/редактировании/удалении текста комментария, добавлении файла и прикреплении/откреплении метки. Но [смена приватности комментария](https://github.com/mantisbt/mantisbt/blob/release-2.28.1/core/bugnote_api.php), [удаление файла](https://github.com/mantisbt/mantisbt/blob/release-2.28.1/core/file_api.php), [переименование метки](https://github.com/mantisbt/mantisbt/blob/release-2.28.1/core/tag_api.php) и изменение прав не покрываются этим правилом. Поэтому найденные/открываемые обращения освежаются при доступном Mantis, каталоги проектов/прав и меток проверяются отдельно. Новый публичный комментарий без изменения даты может оставаться ненайденным до перечитывания обращения; пятиминутная полнота для этого случая не обещается. SOAP-фильтр с 500 не используется как обязательная зависимость.

### 3. Выдача и доступ

Пользователи MCP составляют одну доверенную группу с общим доступом служебного аккаунта. Точный ID обрабатывается детерминированно; лексическая и семантическая выборки объединяются, затем фильтруются и группируются по обращениям. Подстроки и точные имена файлов имеют самостоятельный путь. Определения доступных полей, enum и ограничений запрашиваются по проекту, а не зашиваются в схему каждого вызова.

Карточка содержит ID, тему, проект/статус, лучшие совпадения с типом источника, точным исходным именем файла и адресуемыми ID/ссылками. Если UI не имеет устойчивого anchor, показываются ссылка на обращение и точный ID источника, без выдуманной ссылки. Лимиты карточек, snippets и источников ограничены; продолжение связано с запросом и версией выдачи. Изменившаяся выдача явно требует перезапуска страницы, а не скрытно меняет смысл курсора. Режимы поиска комментариев/имён не отменяют общий контроль доступа.

Перед окончательной выдачей выбранных кандидатов и при открытии обращения сервис пытается освежить доступный текст и видимость источников. Изменившийся кандидат пересчитывается; удалённые совпадения не возвращаются как действующие. Проверка ограничена таймаутами и числом кандидатов. При ошибке связи остаётся кэш с временем последней успешной проверки и явным состоянием Mantis; без TTL отключения. Это выбранная доступность с возможным устаревшим доступом, а не гарантия актуальных ACL.

Отзыв доступа подтверждается авторизованным ответом о запрете/недоступности конкретного объекта либо согласованной проверкой успешно полученного полного доступного scope. Ошибка аутентификации, 5xx, timeout или отсутствие ID на движущейся странице сами по себе ничего не удаляют. Неподтверждённое отсутствие остаётся отдельным состоянием проверки. Успешное полное перечитывание обращения определяет доступные ему комментарии и файлы; API-проекция, умолчавшая notes, не является таким снимком.

Подтверждённый revoke/delete сначала блокирует источники в SQLite и фиксирует поколение запрета, затем очищает тексты/FTS, все активные и строящиеся векторы, скачанные файлы, содержательные поля журнала и принадлежащие сервису старые проекции/снимки. Выдача уже запрещена, пока физическая очистка повторяется. Очистка включает журналы хранения/WAL в пределах управляемых сервисом файлов; это логическое удаление, не обещание физического стирания блоков носителя или чужих внешних backup. Внешний backup нельзя подключить к выдаче без применения актуальных запретов и сверки доступа. Минимальная запись actor/ID/outcome без текста остаётся; regain заново загружает только затронутый scope.

### 4. API записи и полномочия

Новые write-инструменты работают по явному намерению с необязательным инициатором из клиентского профиля или аргумента. Отсутствие имени не блокирует чтение и запись: журнал и текстовые подписи сохраняют «инициатор не указан». Конкретная команда на определённый объект достаточна; неопределённые поля требуют уточнения, а черновик не запускает запись. Подпись «через MCP, инициатор …» добавляется к создаваемому/редактируемому тексту идемпотентно; редактирование чужого комментария не меняет исходного автора. Поле-only операция не создаёт служебный комментарий. Журнал клиентских операций содержит заявленного инициатора; автоматическая синхронизация обозначается как системная, без выдуманного человека.

Адаптер Mantis владеет единственной матрицей `действие → метод API → текущие права → условия объекта → проверка результата`. Перед шагом записи он получает актуальный аккаунт, effective access по проекту, конфигурационные пороги, состояние readonly, переходы статусов и метаданные полей. Значения 28.09.2026 — исследовательское доказательство, не будущие константы. Неподтверждённое разрешение отключает только соответствующее действие с конкретным объяснением, не чтение и не весь MCP.

| Действие | Проверки и маршрут |
| --- | --- |
| Создание/изменение обращения | REST, допустимые поля проекта и переходы, required/regex/enum/custom-field thresholds; для изменения — полное исходное представление и его ETag. |
| Добавление комментария | Порог добавления, readonly и доступ к private при соответствующем намерении; отдельный шаг, с последующей сверкой. |
| Изменение своего/чужого комментария | Подтверждённая принадлежность и видимость; числовой порог своего/чужого редактирования, readonly. Узкий `mc_issue_note_update` передаёт только текст/явно запрошенную видимость, не полный объект обращения. |
| Метки и настраиваемые поля | Проектные определения и отдельные права attach/create/detach/own; readback обязателен, даже при HTTP 200. |
| Загрузка файла | Порог загрузки, ограничения размера/имени, видимость и точный target; к обращению или создаваемому комментарию. Прикрепление к уже существующему комментарию пока не имеет подтверждённого маршрута и возвращает unsupported с вариантами без подмены действия. |

Актуальные project config получают через `GET /api/rest/config?option[]=...&project_id=...`; custom-field definitions — через доступный project API. На просмотренном сервере типичные пороги добавления были 25, редактирования чужой заметки 55, readonly issue 90 / update readonly 70, но эти числа не являются универсальными правилами.

Версия 2.28.1 входит в опубликованные диапазоны ошибок проверки прав [комментариев](https://github.com/mantisbt/mantisbt/security/advisories/GHSA-pq86-j2c2-47f6), [файлов приватных комментариев](https://github.com/mantisbt/mantisbt/security/advisories/GHSA-pw5x-2mf9-3xc8) и [статусов](https://github.com/mantisbt/mantisbt/security/advisories/GHSA-m7ph-9558-mrx3). Наличие локальных исправлений не подтверждено. Успех API сам по себе не доказывает разрешение; файлы заметок проходят проверку их родительской видимости. Проверки MCP не исправляют другие клиенты Mantis. Все write-маршруты квалифицируются отдельно на согласованном тестовом контуре этой версии; недоказанная ветка остаётся недоступной с объяснением.

### 5. Конфликты и составные операции

Для одного обращения записи этого MCP последовательно исполняются владельцем Mantis. Перед изменением перечитывается целый доступный объект, сравниваются известные версия и затрагиваемые поля; ETag от сокращённого `select` не применяется как версия полного объекта. При известном конфликте запись останавливается, возвращает актуальные отличия и путь обновить намерение. Стандартные [REST-проверки](https://github.com/mantisbt/mantisbt/blob/release-2.28.1/api/rest/restcore/issues_rest.php) не являются атомарным compare-and-swap; у SOAP note update нет If-Match. Окно гонки с UI принято пользователем и остаётся явно документированным.

Стабильный `operation_id` с хешем намерения присваивается до первого побочного действия и возвращается клиенту. Повтор того же ID/намерения продолжает журнал; другой payload под тем же ID отвергается. В SQLite одна машина выполнения операции хранит шаги `pending → dispatched → succeeded`, а при отказе — `failed`, `unknown`, `conflict` или `cancelled`. Перед сетевым запросом durable `dispatched`; отсутствие ответа переводит в `unknown`, а не снова в `pending`. Успех подтверждается перечитыванием и сравнением запрошенных полей/источников; несовпадение показывается как неполный результат.

При составном создании обращение, комментарий и каждый файл — отдельные шаги. Сохраняются серверные ID, ожидаемые hashes и результаты; успешные шаги не удаляются автоматически. Reconciliation сравнивает объект, автора, источник, время и содержимое, но сходство не считается уникальным доказательством при нескольких кандидатах. Неоднозначность возвращает «результат неизвестен» и найденные ID для ручного разрешения. Клиент может указать подтверждённый объект/результат и продолжить оставшиеся шаги; новое создание требует отдельного явного намерения, когда старое так и не доказано. Cancellation прекращает только ещё не отправленные шаги, отправленный запрос сначала сверяется. Журнал переживает смену модели/перестройку индекса и не теряет защиту от повторов после restart.

### 6. Эмбеддинги и измеряемая стоимость

Профиль модели закреплён как `qwen/qwen3-embedding-8b` через OpenRouter; ключи остаются runtime secrets. Лексика, фильтры и имена доступны без провайдера. Сохраняются backlog и степень готовности текущей версии каждого фрагмента; ответ различает недоступность query embedding и неполноту corpus. При изменении текста старый вектор не выдаётся как актуальный, даже если новый ещё не оплачен.

SQLite учитывает подтверждённый расход и резерв худшей допустимой стоимости перед каждым запросом, включая query embeddings и повторы. Месячный период — календарный UTC, лимит настраиваемый, начально $5. Неизвестная стоимость завершившегося по timeout запроса остаётся зарезервированной до сверки; неизвестный тариф не означает нулевую цену. Batch ограничен остатком, токенами и concurrency; достижение лимита останавливает новые платные запросы, а не текстовую загрузку. Для восстановления не требуется повторное согласование каждого дешёвого вызова в пределах будущего разрешённого режима работы.

[Тариф модели](https://openrouter.ai/qwen/qwen3-embedding-8b), проверенный 28.09.2026, различался по провайдеру ($0.01–0.04 за миллион input tokens); прежняя оценка 5–12 млн токенов давала $0.05–0.48 первичного наполнения. Это предварительная оценка, не измеренный объём/счёт и не разрешение оплачивать индексацию. Перед вводом квалифицируются доступный провайдер, размерность, ограничения и billing. Опора на [SQLite FTS5](https://www.sqlite.org/fts5.html) и [Zvec](https://github.com/alibaba/zvec) требует фиксации проверенных зависимостей образа, не копирования чужого mutable окружения.

### 7. Архитектурный checkpoint перед реализацией

**Статус: согласовано 28.09.2026 командой пользователя «приступай к реализации» после предъявления этого дизайна.** Реализация описанной границы разрешена; развёртывание, canary, изменение прав и реальные записи в Mantis остаются отдельным этапом. Выбранные SQLite + Zvec сохранены; этот пункт конкретизирует миграцию/rollback из ADR 4 согласно [границам пакета](../../../docs/package-architecture.md).

| Граница | Предложение |
| --- | --- |
| Инвариант и владелец | Только Mantis MCP изменяет свой индекс, checkpoint, журнал, budget и lifecycle локальных проекций. Текст/фильтры авторитетны в SQLite, векторы проверяются по версии. Ни подтверждённый revoke, ни уже выполненный write не забываются при rebuild. |
| Runtime authority | Один процесс-владелец на отдельный volume Mantis, ограниченный worker sync/embeddings и исполнение write. Второй владелец того же volume получает понятный конфликт запуска; чужие процессы/volume он не останавливает. Общего coordinator и shadow-state в агенте нет. |
| Почему эта граница | Чисто stateless-вариант не обеспечивает поиск всей базы, продолжение импорта и защиту повторов после restart. Owner-local state достаточен; расширять Code/BookStack/1С coordinator нечем обосновать, общего cross-owner reproducer нет. |
| Затрагиваемое | Образ/зависимости Mantis, его каталог данных/attachment cache, host installer wiring, MCP additive tools и health, целевые проверки. Журнал, расходы и tombstone не принадлежат поколениям поискового индекса. |
| Незатрагиваемое | Mantis server/schema, Code/BookStack DB/queues, 1С процессы/locks, Git lifecycle, клиентская Windows platform/support. Нет службы Windows, firewall или auto-elevation. |
| Ожидание и статус | Каждый внешний запрос имеет timeout и ограниченные попытки с backoff. Клиентская операция имеет deadline; при незавершённости возвращает durable ID и статус. Health показывает проектную задержку, backlog, семантику, cleanup и write availability без полного содержимого журнала. |
| Completion/cancel/recovery | Checkpoint продвигается после завершённого окна; write — после проверенного результата; вектор — после сверенной версии. Остановка/restart продолжает durable шаги, не повторяет неизвестный POST. Cleanup/rebuild ограничены scope владельца и возобновляемы. |
| Installed migration | Новый отдельный volume; versioned SQLite schema и profile generations Zvec. Проверка совместимости до подключения; старый несовместимый binary не открывает новый DB в write-режиме. Нет автоматической разрушительной миграции. |
| Совместимость/контекст | Существующие read tools/форматы сохраняются. Метаданные полей и журнал доступны on demand, не весь каталог в tools/list. Измеряются schema bytes до/после; материальное расширение требует пересмотра checkpoint, не скрытого роста. |
| Canary | Сначала fixture recovery и тестовый Mantis 2.28.1; затем явно разрешённый проект с контролируемой нагрузкой и проверками чтения, delta, revoke, write/unknown. Первичный импорт и внешние side effects только после отдельного разрешения на этот этап. |
| Rollback | Отключить новые write/index workers, сохранить независимые journal/budget/tombstone. Вернуть совместимый read-only режим с original images. Старую проекцию публиковать только после применения актуальных запретов; непроверенные snapshot не подключать. Откат не удаляет опубликованные объекты Mantis и не откатывает чужое состояние. |

Новые обязательства сопровождения: свободное место/размер volume, возраст checkpoint и backlog, схема и dependency lock, восстановление Zvec из SQLite, подтверждённая очистка и budget reconciliation. Эти обязанности принадлежат Mantis, а не человеку, вручную двигающему внутренние статусы.

## Risks / Trade-offs

### Реализованная граница локального владельца

Состояние schema v1 хранится только под Mantis `statePath`: SQLite DELETE journal
с secure_delete, owner marker и OS-lock; Zvec 0.7.0 в отдельных UUID-поколениях.
SQLite хранит версии фрагментов и незавершённые удаления; crash после flush Zvec
до SQLite completion сверяется без повторной покупки вектора. Переход поколения
сначала сохраняется в SQLite, затем удаляются старые управляемые каталоги.
Неподдерживаемые schema/profile не мигрируют автоматически. Восстанавливать можно
векторную проекцию из актуальной SQLite, сохраняя журнал, расходы и revocations;
импорт старого целого snapshot не предоставляется.

Первичный импорт имеет возобновляемую компактную сверку ID/дат до двух совпавших
полных проходов нового проекта: удаление перед текущей страницей иначе могло
пропустить неизменённый старый объект, который не попал бы в догоняющую дельту.
Для текущих проектов повторяются только недавние заголовки; две одинаковые
выборки и контрольная третья подтверждают checkpoint. Незавершённые fetch-порции
имеют durable progress, бюджет времени и продолжение следующим циклом.
Пятиминутное перекрытие сохраняет равные timestamps; HTTP Date позволяет не
перечитывать неизменённый старый объект вне этого перекрытия. Checkpoint остаётся
датой изменения объекта. Фактическая нагрузка и clock consistency требуют canary.

Поиск ограничен десятью карточками по умолчанию, двадцатью максимум и 12 000
символов структурированного ответа; каждый источник имеет snippet до 280 символов,
на карточку до трёх источников. Курсор считает фактически выданные карточки,
включая пустой/широкий запрос. Текстовая часть MCP не повторяет JSON.
Вектор точного текста запроса переиспользуется через owner-local LRU-кэш памяти
на 256 элементов (около 8 MiB векторов); ключ включает embedding profile и хеш
входа. Параллельные одинаковые вызовы разделяют Future одного вычисления.
Смена фильтра/страницы и обновление индекса не пересчитывают запрос; карточки и
доступ проверяются заново. Ошибки не сохраняются, перезапуск очищает кэш.
Нового состояния на диске, миграции схемы и общего владельца с BookStack нет.
Schema bytes: прежние три инструмента 1473, все восемь 4729 (+3256 UTF-8 bytes
при одинаковой сериализации FastMCP). Структурный контракт прежних трёх совпал
с исходным proxy hash; новые metadata загружаются on demand.

Запись сериализована одним lock внутри владельца Mantis (это также сериализация
каждого обращения). Пустые `writeActions` и `writeProjectIds` отключают её;
квалификация новых проектов не наследуется автоматически. Матрица прав,
неподдерживаемые ветки, подпись, unknown/partial и управляемое восстановление
описаны в [операторской инструкции](../../../vibecoding1c-mcp-host/mantis-ticket-mcp/README.md).
При возврате к прямому reader получение файла дополнительно проверяет родителя
перед старым file endpoint: +1 issue GET на файл. Задержка этого пути на реальном
сервере ещё не измерена. Включённый индекс дополнительно проверяет снимок чтения
и не разрешает завершившейся позднее загрузке воскресить удалённый cache file.

### Остаточные риски

- [Нет snapshot у REST-пагинации] → повторная сверка недавнего окна, дедупликация и сохранение старого checkpoint при неполноте; нагрузочная проверка с реальными объёмами остаётся обязательной.
- [Изменение без нового `updated_at`] → lazy refresh и отдельные каталоги; новый видимый текст может не находиться до перечитывания. Это принятая граница, не скрытый SLA.
- [Mantis недоступен при отзыве прав] → кэш продолжает показываться без TTL согласно ADR 2; ответ явно указывает последнее подтверждение. Гарантии актуальной видимости нет.
- [Известные дефекты прав 2.28.1] → MCP независимо проверяет узкие write/read-attachment ветки; недоказанная ветка не включается. Сервер за пределами MCP не становится исправленным.
- [Гонка с веб-интерфейсом] → pre-read, If-Match где доступен, сериализация MCP и post-read. Абсолютная защита от перезаписи не заявляется.
- [Две локальные проекции или crash посередине] → SQLite intent/version и восстановление векторов; serving фильтрует устаревшую версию.
- [Кириллица, длинные тексты, имена и subprocess] → исходное API содержимое не подменяется reader truncation; UTF-8 и существующие path/quoting helpers, при изменении процесса — regression на одном пути с пробелом и кириллицей.
- [Лимит/сбой эмбеддингов] → доступная лексика и честный semantic status, резерв расхода, bounded backlog. Бюджет влияет на semantic freshness явно.

## Migration Plan

1. Получить явное согласование checkpoint выше перед зависимой реализацией; затем реализовать owner-local модули и fixture acceptance из test-plan. Не менять Mantis server.
2. Зафиксировать версионирование данных/модели, read-only rollback и зависимости на отдельном тестовом состоянии. Проверить сбой между SQLite/Zvec, restart журнала и revoke во время rebuild.
3. Подготовить отдельно разрешённый тестовый Mantis 2.28.1 и минимальные права тому же служебному аккаунту; квалифицировать каждую write-ветку. До этого production writes выключены.
4. После разрешения canary подключить новый Mantis volume, выполнить один проектный импорт, оценить фактические объёмы, стоимость и соблюдение цели обновления до пяти минут, затем расширить по проектам. Запись включать только для доказанных действий/проектов.
5. При rollback остановить новые задания, согласовать in-flight/unknown, оставить journal/tombstone/budget; вернуть чтение совместимой версии и оригинальные файлы. Не восстанавливать content backup поверх последних запретов. Другие MCP не перезапускаются ради отката Mantis.
