## ADDED Requirements

### Requirement: Явное намерение и инициатор

Запись SHALL требовать конкретного намерения пользователя с определённым объектом/действием и необходимых полей; такая команда SHALL быть достаточным разрешением без обязательного второго подтверждения. Подготовка черновика SHALL NOT выполнять запись. Инициатор из клиентского профиля SHALL фиксироваться в журнале клиентских операций и компактной подписи создаваемых/редактируемых текстов как заявленная личность доверенной группы; он SHALL NOT представляться аутентифицированным личным аккаунтом Mantis.

#### Scenario: Конкретное изменение статуса
- **WHEN** пользователь требует установить определённый статус в конкретном обращении и все проверки проходят
- **THEN** MCP выполняет разрешённый шаг без повторного запроса согласия, пишет инициатора в журнал и не создаёт дополнительный комментарий

#### Scenario: Только черновик или отсутствующий инициатор
- **WHEN** пользователь просит подготовить текст либо профиль не сообщает обязательного инициатора
- **THEN** публикация не выполняется; для записи возвращается конкретно недостающее намерение или поле профиля

#### Scenario: Редактирование чужого текста
- **WHEN** разрешённая команда меняет чужой комментарий
- **THEN** подпись инициатора добавляется без дублирования при повторе, а исходный автор комментария не подменяется

### Requirement: Проверенные действия на существующем Mantis

Запись SHALL использовать текущий MantisBT 2.28.1 без его обновления/модификации и только подтверждённые методы/разрешения того же служебного аккаунта. MCP SHALL независимо проверять effective project access, числовые пороги своих/чужих комментариев, приватность, readonly, переходы статусов и права полей/меток/файлов. Успех HTTP SHALL NOT считаться доказательством разрешения. Неподтверждённая ветка SHALL быть недоступна с причиной и способом продолжить; существующее чтение SHALL сохраняться.

#### Scenario: Аккаунт остаётся наблюдателем
- **WHEN** права аккаунта недостаточны для добавления обращения или комментария
- **THEN** запрос записи не отправляется; MCP называет требуемую проектную возможность и продолжает чтение/поиск

#### Scenario: API допускает действие вопреки порогу
- **WHEN** сервер имеет известный дефект проверки прав, но текущий числовой порог запрещает служебному аккаунту изменение чужой заметки или статуса
- **THEN** MCP отвергает операцию до отправки даже при потенциальном HTTP 200 от сервера

### Requirement: Поля и корректная цель вложения

MCP SHALL поддерживать создание и изменение полей обращения, своих/чужих комментариев и файлов в пределах согласованного API-supported scope, получая проектные ограничения и обязательные поля. Неизвестные или неподдерживаемые поля/targets SHALL NOT игнорироваться или заменяться другим действием. Удаление обращений и комментариев не входит в новый write scope.

#### Scenario: Неподдерживаемое вложение к существующему комментарию
- **WHEN** пользователь требует добавить файл именно к существующему комментарию, а безопасный маршрут не подтверждён
- **THEN** MCP сообщает unsupported и варианты обращения/нового комментария, не загружая файл в другой target без уточнения намерения

#### Scenario: Обязательное поле проекта
- **WHEN** команда создания не содержит обязательное настраиваемое поле
- **THEN** MCP запрашивает именно недостающее значение по метаданным проекта и не создаёт заведомо неполный объект

### Requirement: Конкурентные изменения и проверка результата

Изменение существующих данных SHALL включать pre-read, сравнение версии/затрагиваемого содержимого, If-Match где метод его поддерживает, сериализацию записей MCP в одно обращение и post-read. Известный конфликт SHALL останавливать запись. Ответ SHALL отделять проверенный успех полей от неполного/неизвестного результата. Остаточная неатомарная гонка с другими клиентами SHALL оставаться явно признанным ограничением.

#### Scenario: Конфликт до отправки
- **WHEN** после исходного чтения другой клиент изменил затрагиваемые данные
- **THEN** MCP показывает конфликт и свежие отличия, не затирая их автоматически

#### Scenario: HTTP 200 с проигнорированным полем
- **WHEN** API вернул успех, но post-read не подтверждает запрошенное значение настраиваемого поля
- **THEN** MCP сообщает неполный результат конкретного поля вместо общего succeeded

### Requirement: Durable operation ID и неизвестный результат

До первого сетевого побочного действия операция SHALL получить durable ID и хеш намерения. Повтор ID с тем же намерением SHALL использовать журнал; иной payload SHALL отвергаться. Потеря ответа после возможного создания SHALL вести к сверке, а при неоднозначности — к unknown без автоматического повторного создания. Restart и перестройка индекса SHALL сохранять этот контракт.

#### Scenario: Комментарий создан, ответ потерян
- **WHEN** соединение оборвалось после возможного создания комментария и сверка находит несколько неразличимых кандидатов
- **THEN** состояние остаётся unknown, кандидаты и ID операции доступны для разрешения, POST автоматически не повторяется

#### Scenario: Повтор после restart
- **WHEN** клиент повторяет уже успешно завершённую операцию с тем же ID и намерением после перезапуска сервиса
- **THEN** возвращаются сохранённые подтверждённые результаты и серверные ID без дублирования объектов

### Requirement: Частичный успех и отмена

Составная операция SHALL хранить результаты отдельных шагов, сохранять успешные и продолжать только доказанно незавершённые. Отмена SHALL прекращать неотправленные шаги и сверять уже отправленные. Автоматическое удаление опубликованных обращений, комментариев или файлов в качестве отката SHALL NOT выполняться. Возвращаемый результат SHALL содержать IDs выполненных шагов, состояние остальных и конкретный способ продолжения.

#### Scenario: Файл не загрузился после создания
- **WHEN** обращение и комментарий созданы, а загрузка файла доказанно не выполнена
- **THEN** повтор операции продолжает только загрузку, сохраняя уже созданные ID

#### Scenario: Отмена во время отправки
- **WHEN** пользователь отменяет операцию, пока сервер мог выполнить отправленный шаг
- **THEN** последующие шаги не отправляются, текущий сверяется и при неоднозначности остаётся unknown, без автоматического удаления или повтора
