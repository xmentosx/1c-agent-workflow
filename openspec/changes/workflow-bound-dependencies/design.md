# Design

## Context

См. [proposal.md](proposal.md). Общая синхронизация lock исключает fork правил, а установщики отдельно трактуют режимы и manifest compatibility. Транзакционный update и rollout рабочих веток уже существуют; их продолжение и rollback сохраняются.

## Goals / Non-Goals

**Goals:** единое решение о версиях для всех consumers; временный хотфикс; безопасная миграция установленного состояния.

**Non-Goals:** новая версия самих компонентов, изменение controlled fork, обновление удалённых хостов, локальный vibecoding1c, заморозка OS/1С/AI-клиента и всех транзитивных библиотек.

## Decisions

1. **Один владелец выбора.** Общий dependency resolver получает baseline из `templates/dependency-lock.json` установленного package и явные исключения из project lock. Compatibility manifest подтверждает связанные версии/каталоги, а не выбирает независимую версию. Установщики правил, Vanessa/ROCTUP, facade, YAxUnit, OpenSpec и клиентских компонентов потребляют одно решение. Раздельные fresh/locked ветви удаляются; отдельный registry версий не вводится.
2. **Один формат исключения.** Расширить существующий project lock: identity артефактов, происхождение, причина и совместимый комплект. Применение/снятие выполняется существующим helper/update-install owner с его snapshots и guards. Новый worktree наследует выбранный комплект точки создания; изменение существующего worktree само по себе не переписывает соседние. Служебные source-build пути должны соответствовать SHA выбранного набора.
3. **Снятие по полной сборке.** Сравнивать версию, downstream revision и происхождение в пределах семейства; не сортировать произвольные tags/commits по строке или дате. Равный номер с другими bytes и несопоставимый fork дают отчёт и явный выбор. Несовместимое исключение снимается либо заменяется подтверждённым комплектом через helper с повтором исходной операции; общий status/help остаётся доступным.
4. **Существующий update владеет переходом.** Решение о наборе входит в per-root snapshot, post-copy, commit, resume и rollback. Сохраняются rollout всех доступных веток, deferred для живого владельца, клиентский reload и отдельная pending-подготовка расширений в ИБ. Обновление файлов не объявляет такую подготовку выполненной.
5. **Локальный vibecoding1c — отдельная задача.** Пользователь 2026-10-13 выбрал вынести его после обнаружения общей адресации контейнеров, портов, state и индексов. Одного versioned cache недостаточно; отдельная постановка должна согласовать изоляцию runtime и данных, включая повторную индексацию. См. [follow-up-local-vibecoding.md](follow-up-local-vibecoding.md).

Альтернативы: сохранить `locked` — оставляет независимую заморозку инструментов; выбирать upstream latest — нарушает согласованный комплект; новый updater/coordinator — дублирует имеющийся владелец восстановления.

## Risks / Trade-offs

- Старые custom pins → предварительный отчёт и явный выбор baseline/совместимого хотфикса до замены; чужие записи сохраняются.
- Hotfix MCP меняет tools/list → обязательны согласованный каталог, hashes и исходная runtime-проверка; проверки не ослабляются.
- Кеши артефактов должны различать версии и hashes; используемые сборки не перезаписываются.

## Migration Plan

1. Подготовить решение для старых CLI/JSON/env `fresh`/`locked`, убрать их самостоятельную власть после успешного перехода.
2. Снять per-root snapshot, применить выбранный набор через обычный update, завершить свободные roots и явно отложить занятые.
3. Проверить реальные init/update, необходимые reload и по одному исходному вызову ROCTUP/Vanessa на согласованном тестовом проекте. Сбои продолжаются тем же helper либо откатываются существующим owner; поздние edits проходят reconciliation.

## Architecture Checkpoint

Подтверждено пользователем 2026-10-13 запросом «реализуй»: installed lock/env/client state; существующие per-root update/install owners и одна recovery state machine. Затем пользователь явно вынес локальный vibecoding1c в отдельную задачу. Новых услуг, elevation, глобальных locks или фонового ожидателя нет; busy root получает bounded deferred. Поддержка клиентов и Windows сохраняется. Пользователь выбрал штатный E2E-стенд при условии его доступности. Реальные файловые update/rollback на изолированной копии выполнены; нативную init/CFE/MCP приёмку пользователь явно перенёс на отдельный прогон после отказа лицензии, см. test-evidence.md и follow-up-native-acceptance.md.
