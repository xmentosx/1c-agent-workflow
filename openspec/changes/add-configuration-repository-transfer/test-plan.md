# Проверки и приёмка

Приёмка требует живого стенда: тестовое хранилище с двумя пользователями, ветка основной конфигурации и подключённая ИБ с тестовыми данными (задача 1.1). Пользовательскую базу проекта как стенд не использовать. Перед подготовкой своего стенда проверить, можно ли переиспользовать стенд хранилища release E2E (`scripts/release-e2e/seed-parallel.ps1`, repository lock probe). Pester-fixture подтверждает контракт helper, но не результат объединения, обновления ИБ и помещения.

| ID | Сценарий | Наблюдаемый результат / задача |
|---|---|---|
| R1 | CF удаляет реквизит формы и меняет обработчик; в хранилище независимая правка той же формы | Отчёт и штатное сравнение показывают удаление и строки обработчика; после объединения и в версии независимая правка сохранена; 1.1–1.2, 2.3 |
| R2 | Ручной путь: принятие целиком, возврат с замечанием, деталь в штатном сравнении | Объединения до принятия нет; возврат ведёт в ветку; штатное сравнение открывается без конфликта с допуском агента; 1.3, 2.3 |
| R3 | Автоматический путь без вопросов; агент не может оценить деталь | Версия без промежуточного одобрения; непонятная деталь показана человеку; 2.3, 4.1 |
| R4 | Частичный захват с владельцем, отмашка, молчаливый повтор, новый объект с корнем, дозахват после конфликтов | Занятые объекты перечислены с владельцами; полученные захваты сохранены; неизвестный исход не считается успехом; 2.2 |
| R5 | Пересборка CF с тем же хешем, помещение другим пользователем во время ожидания, вмешательство в ИБ после просмотра | Устаревшее одобрение не достигает записи; доступно новое сравнение; 2.4 |
| R6 | Дымовой сценарий проведения; отсутствие пригодных данных; ошибка после первого CF | Движение подтверждено без полного прогона ветки; без данных решение у человека; после ошибки повторный просмотр включает уже применённый CF; 3.1–3.2 |
| R7 | Прерывание после объединения, после обновления ИБ, ожидание человека, отмена | Статус называет этап и подтверждённое; продолжение ответом и повторным запуском; отмена без отката и снятия захватов; 3.2 |
| R8 | Потеря ответа до и после создания версии; две версии с одинаковым комментарием | Нет дубликата; неоднозначность решает человек; захваты помещённых объектов сняты, прежний захват вне состава сохранён; 3.3 |
| R9 | Обращение из контекста, из параметров ветки, по вопросу; без обращения; прерывание между комментарием и статусом | Номер не берётся из имени ветки; «Решено» только при всех пунктах; число комментариев и статус сверены; без обращения нет вызова записи; 3.4 |
| R10 | Ветка расширения и проект без хранилища | Отказ до любого действия записи; 2.1 |
| R11 | Оба входа в поддерживаемых клиентах, локальная и терминальная сессии обычного пользователя | Отчёт доступен, продолжение после ожидания работает; 4.1–4.2 |
| R12 | Обновление `master` после версии в режимах `workflow` и `external`; сбой и прерывание выгрузки | Обновления из хранилища и `/UpdateDBCfg` нет; другая ветка получает изменения через `/itl-refresh-lite`; при сбое версия сообщена, помещение не повторено; 3.5 |

Все пути стенда содержат пробелы и кириллицу одновременно. Состав до объединения, после него и в версии сверять по объектам, свойствам и строкам кода, а не по совпадению комментария. Не выдавать helper-only проверку за прохождение R2, R3 и R7: нужен наблюдаемый прогон агента. Измерить время подготовки сравнения и дымового сценария отдельно от проверок ветки, а также байты новых клиентских поверхностей.

Во время apply запускать непосредственно затронутые owner-тесты одним набором. Доставка — существующим source-delivery: один coherent commit, RegisterChange владеет Targeted; Smoke/Full/Develop/Release не запускаются. Planning проверяется strict OpenSpec validation.
