# Квалификация платформенного пути (задачи 1.1–1.3)

Стенд: [evidence/stand](evidence/stand), запуск `run-stand.ps1 -Clean`. Он строится из `tests/fixtures/gate-stand/cf` (конфигурация на поддержке) в ignored `build/agent-artifacts/configuration-repository-transfer/` по пути с пробелами и кириллицей. Участники: файловая «ИБ разработчика» (подключённая ИБ), хранилище, второй пользователь «Коллега» со своей ИБ и две ИБ сборки CF. Пользовательские базы не используются.

Прогоны 2026-11-25: на 8.3.27.2130 — первый пошаговый и повторный с нуля; на 8.5.4.1878 — с нуля (`ITL_REPOSITORY_TRANSFER_PLATFORM`). Все отчёты сравнения трёх прогонов побайтно совпали; отличается только отчёт истории, потому что содержит время. Операция Designer на этой конфигурации занимает 2–3 с на 8.3 и около 5,5 с на 8.5. Время на конфигурации продуктового размера не измерено.

## Выводы для дизайна

- Способ применения — F5, а не `/MergeCfg` (F4). Конфликты с хранилищем решаются в Git при refresh ветки, поэтому CF ветки равен «хранилище + задача». Инвариант применения: после загрузки основная конфигурация совпадает с проверенным CF (пустое сравнение F5). Перед загрузкой последняя версия хранилища совпадает с основной конфигурацией (F6); при повторе совпадает с точностью до сохранённого состава первого применения.
- Просмотр строится из двух отчётов F1–F3; текстовый отчёт покрывает свойства и строки кода, поэтому штатное сравнение — запасной путь. Для него человек закрывает Конфигуратор перед ответом, а агент при F10 возвращает статус с этим действием.
- Корень захватывается и при удалении объекта верхнего уровня, а не только при добавлении. Нынешнее `Add-ConfigRepositoryRootLockDependency` учитывает только добавление.
- Повтор при уже применённом CF не выгружает подключённую ИБ в `master` (F9).

## Не проверено

Время на конфигурации продуктового размера, серверная ИБ, пароли пользователей хранилища, сборки платформы кроме 8.3.27.2130 и 8.5.4.1878, обрыв процесса посреди загрузки или помещения.

## Реализация (2026-11-26)

Действие `repository-transfer` (`agent-1c.repository-transfer.ps1`) с шагами `status`, `prepare`, `approve`, `reject`, `apply`, `smoke`, `commit`, `update-master`, `complete`, `cancel` и команды `/itl-repository-commit-review`, `/itl-repository-commit-auto`. Запись этапа хранится в состоянии ветки (`repositoryTransfer`), материалы — в игнорируемом `.agent-1c/dev-branches/<ветка>-repository-transfer/`.

| Проверка | Результат |
|---|---|
| [helper-native.ps1](evidence/stand/helper-native.ps1) на стенде 01–04 + обновление и захват формы, штатный `Invoke-Designer` пакета, 8.3.27.2130 | Поиск версии вернул 2; проверка «хранилище = ИБ» пуста; итог затрагивает только обработку задачи и проходит проверку состава; после загрузки ИБ = CF; помещение создало версию 3, найденную сверкой истории; версия 3 = ИБ; отсутствующая версия отклоняется |
| `tests/pester/RepositoryTransfer.Tests.ps1` | Разбор отчётов и истории; поиск версии без подсказки; отказ CFE и проекта без хранилища до нативных вызовов; полный ручной путь; запрет решения агента в ручном режиме; устаревшее решение после пересборки и изменения состава; посторонние изменения и объекты вне задачи; повтор по применённому CF и стоп при ушедшем вперёд хранилище; сверка прерванного помещения без второго помещения и выбор человека при двух кандидатах; отмена без отката |

Проверка свежести `master` сравнивает время последней выгрузки в `master` со временем создания последней версии хранилища; при серверном хранилище с расходящимися часами возможен ложный стоп или пропуск, его страхуют проверки «хранилище = ИБ» и состав итога.

Не выполнено и остаётся приёмкой на установленном проекте: задачи 2.1–4.2 с живым агентом в поддерживаемых клиентах, решение человека в чате, дымовой сценарий в пользовательском режиме, тестовое обращение Mantis, `update-master` на реальном `master`, терминальная сессия и время на конфигурации продуктового размера.
