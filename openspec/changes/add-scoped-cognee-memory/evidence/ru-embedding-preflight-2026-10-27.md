# Русскоязычный корпус: технический допуск embedding-сравнения

Результат 2026-10-27: **сравнение качества остановлено до измеряемых запросов**.
Qwen не принят как замена текущей модели. Это отдельный исследовательский
эксперимент после MO0–MO4; принятые G3/R6/G5 и MO не переоткрываются,
новый обязательный gate первого выпуска не вводится.

## Согласованный объём и воспроизводимость

Пользователь разрешил сравнение `BAAI/bge-small-en-v1.5` / FastEmbed / 384 и
`qwen/qwen3-embedding-8b` / OpenRouter / 4096: 50 коротких русскоязычных заметок,
24 вопроса, три повторения на модель (144 поисковых вызова) и шесть заранее
выбранных задач на модель в Codex CLI (12 полных ответов). Модель Qwen уже
используется другими MCP, но это не доказательство её пригодности в Cognee.

Исходный source: `6ddf95d34dea1e060b4f341ceeb6174c32d7c62f`.
Cognee 1.6.5, image
`sha256:e5de80619fd8d0c53cdaca2aea6020b046f57f8800e62120faa50807fa4f3820`;
2 CPU, RAM/swap limit 5 GiB, прежние GLiNER, queue 2 / LRU 6,
embedding batch 32 / input limit 512. Одновременно запущен максимум один
экспериментальный экземпляр. Нормативные policy, ai_rules_1c, scoped frontend,
runtime workflow, Git-реестр и существующие базы/индексы Cognee не изменены.
Экспериментальные подключения не выданы за квалифицированные G1 profiles.

Все шесть областей представлены отдельными штатными datasets; всего 12 datasets
с учётом чужих областей, прошлого cycle и отрицательных примеров. Идентичные
raw originals сериализованы для обеих моделей. Проверка tokenizer до inference:
все 50 укладываются в baseline 512 tokens, максимум 486.
Корпус — 44 514 UTF-8 bytes суммарно по сериализованным заметкам.

Часть продуктовых фактов основана на BookStack
[сравнении ПРОФ/КОРП](https://kb.itland.ru/link/458) и
[пакетной выдаче заданий](https://kb.itland.ru/link/527).
Остальное явно помечено как учебные данные, не производственное доказательство.
Private gold зафиксирован до embedding inference, не передавался Cognee или
агентам. До inference сохранено уточнение вторичной релевантности RU13/RU14/RU18
без изменения primary targets; обе версии retained. Текущий frozen manifest
`ru-embedding-1.1`, SHA-256
`fdb6e2e94f25db629e2b6f9caee3880764d18b9179a5852ffa7418e4b8a46a6d`.

## Фактический результат подготовки

| Профиль | Originals, проверенные native raw GET | Семантическая полнота | Результат |
|---|---:|---|---|
| BGE / FastEmbed | 50/50 | Контроль CHUNKS вернул 50 фрагментов; множество SHA-256 текстов точно совпало с корпусом | Допуск индекса получен, ingestion 398.738 s |
| Qwen / штатный `custom` → LiteLLM | 26/50; intent `ru-n27` unconfirmed | Полный индекс не подтверждён | `Server disconnected`, затем Docker `OOMKilled=true`, exit137 при лимите 5 GiB |
| Qwen / штатный `openai_compatible` → OpenAI SDK | 10/50; intent `ru-n11` unconfirmed | Полный индекс не подтверждён | Нативный remember получил HTTP422 с причиной `403 — Access denied by security policy` |

Вторая попытка использовала тот же image, workload, лимиты, GLiNER и параметры
фрагментов; изменён только поддерживаемый путь подключения: model
`qwen/qwen3-embedding-8b`, endpoint `https://openrouter.ai/api/v1`.
Создана отдельная пустая база с обычным пользователем и теми же правами;
UUID пользователя отличается от первого профиля. Первая неудачная база/контейнер
сохранены. Никаких исправлений исходников Cognee, ручной правки БД, урезания
корпуса, увеличения лимита RAM или подмены неудачного результата нет.

Во втором профиле последний успешный remember занял 163.589109 s, следующий
завершился отказом за 130.926739 s. Это подготовка индекса, **не latency поиска**.
Перед штатной остановкой cgroup сообщил peak 4 759 691 264 bytes (~4.43 GiB),
CPU usage 153.574 s, OOM events 0. Для первого failed профиля подтверждён OOM,
его точный peak не измерен. Эти неполные ingestion runs нельзя сравнивать как
стоимость двух завершённых индексов.

Метаданные штатной `dataset_database`, прочитанные только read-only, подтверждают
model/dimensions 384 у BGE и 4096 у обоих Qwen profiles. Один диагностический
запрос с точным текстом `ru-n01` непосредственно с host вернул HTTP200,
один вектор 4096, 2.442883 s, reported usage 269 tokens / $0.00000269.
Это единичная диагностика, не время запроса через Cognee и не полная стоимость.
Тот же read-only запрос через OpenAI SDK в контейнере дал APITimeoutError за
20.451438 s. Дополнительный urllib probe в контейнере не завершился за 35 s.
DNS-контроль в контейнере, Code и host дал одинаковые адреса без превышения
8 s; версия о постоянном DNS-отказе не подтверждена.

**Нельзя приписывать 403 конкретному владельцу или контенту запроса**:
полный embedding payload внутреннего вызова Cognee и корреляция с журналом
сервиса/сетевой политики не получены. Нельзя также утверждать, что сама модель
Qwen требует локально 5 GiB: inference удалённый, OOM относится ко всему
проверенному процессу Cognee. Повтор через SDK выявил самостоятельный отказ;
снижение памяти или устранение первоначального OOM им не доказано.

## Что не выполнено и какие выводы допустимы

Выполнено **0/144** измеряемых поисковых trials и **0/12** агентских ответов.
Единственный baseline CHUNKS control относится к допуску полноты, не к trial.
Recall@k/MRR, число ошибочных применений, final capped cards, agent tokens,
query latency и преимущество Qwen перед baseline остаются **unverified**,
а не нулевыми. Полная стоимость embedding/ingestion неизвестна; usage одного
host probe не экстраполируется на весь прогон. Парный files-only результат
также не получен и не заявляется.

Следующее продолжение ограничено тем же корпусом и вопросами:

1. Проверить конкретный исходящий embedding request и происхождение 403 по
   поддерживаемому журналу владельца endpoint/сети; согласовать разрешённый
   путь подключения без обхода security policy. Сохранить exact input/hash и
   request correlation без секретов. Отдельно установить причину OOM.
2. После подтверждённого исправления повторить подготовку Qwen на тех же
   50 originals. Не повторять remember для unconfirmed intent вслепую:
   native reconciliation/resume, либо отдельный явно обозначенный fresh profile
   с сохранением failed данных. Не править pipeline status/индексы вручную.
3. Допускать исходные 144/12 только при подтверждённых 50/50 фрагментах и
   совпадающих text hashes. Учитывать rank внутри dataset: Cognee union не
   является глобальной сортировкой. Финальные ответы проверять через прежний
   frontend с caps 8 cards / 1600 tokens / deadline 20 s; exact reads отдельно.

После двух неудачных технических путей новые обходные слои не добавлялись.
Из альтернатив сейчас выбран возврат к действующему baseline. Owner-local
вариант — исправить подтверждённое подключение/профиль и повторить этот корпус;
отдельный proxy, собственный embedding pipeline и доработка Cognee не предлагаются.
Смена размеров вектора, cache/RAM или новый локальный кандидат потребуют явного
нового профиля сравнения, не ретроспективной подмены условий этих попыток.
