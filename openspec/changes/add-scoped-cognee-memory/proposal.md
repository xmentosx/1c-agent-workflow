## Why

Агентам нужен повторно используемый опыт, относящийся к правильному проекту, продукту и циклу ветки/базы. Существующие локальные заметки и общий templates-сервис не дают этой модели; усложнять первый выпуск одинаковой интеграцией двух движков пользователь отказался.

## What Changes

- До первого выпуска каталога и первого выпуска памяти использовать обязательное подтверждённое наполнение реестра по registry AC-36–38: продукты/проекты, resolved настройки и карта основной функциональности. Memory AC-44 проверяет ту же зависимость, без второго наполнения, каталога или копирования документов в Cognee; minimal seed G2 не заменяет выпускные данные. Это не условие начала кода G4 и не разрешение G3/G4 сейчас.
- Использовать неизменённый Cognee и одно общее техническое подключение. Шесть логических областей отображаются на штатные datasets: задача/ветка/база, локальный проект, рабочее место, продукт, проект, организация. Локальные datasets lazy; общие один раз подготавливаются тем же account с exact IDs. Персональные accounts/grants/роли, outsider и секретность между разработчиками не входят в первый выпуск.
- Каждая запись получает явную наиболее узкую достаточную область через стандартный `dataset_name`; постоянное условие проекта не теряется после reset вместе с task memory. Неопределённое назначение остаётся локальным кандидатом, без автоматического расширения доступа.
- Получать `projectId`, `productId`, источники и правила применимости из отдельного change `add-product-project-registry`. Для общего продуктового знания определить одно каноническое место и разрешённый read set: факт из ERP+PM может храниться в PM КОРП и использоваться в ПРОФ только по подтверждённой области. Требуемое необязательное расширение интерфейса реестра описать явно, без изменения его спеки и без второго каталога/resolver/updater.
- Различать текущий проект и выбранный MCP-source: опубликованные название/версия/индексация из registry, business origin/назначение источника и подтверждённые доработки/ограничения из каталога. Поддержать custom PM5 КОРП → типовой MCP и PM5 ПРОФ → MCP КОРП через ту же карту применимости. Отсутствие source generation/hash не требует доработок Code/Graph и само не делает все факты непроверенными; native Cognee currentness остаются обязательными по прежним правилам.
- Разделить searchable knowledge и точное состояние: полезный опыт хранить в Cognee, настройки и lifecycle читать у существующих владельцев; компактное продолжение задачи сохранять локально вне сбрасываемого дерева.
- Добавить узкую ITL-привязку штатных вызовов Cognee к effective context, текущему циклу, применимым homes и exact native datasets общего подключения. Scope действует до retrieval/graph для релевантности и правильного destination, не является ACL. Current originals/status проверяются независимо от semantic top_k; недостающие native возможности не заменяются своим сервисом версий.
- Привязать память задачи к циклу существующего lifecycle. Reset создаёт новый цикл даже при неизменном HEAD; resume продолжает тот же переход, старые записи остаются историей.
- Применимые native Q1–Q7 используют один technical account: exact IDs, context scope, durable/status, current original, precise retirement и current-state admission после restore, bounded retrieval/whole-run cost. Исторический multi-user ACL proof сохранён, но не обязателен для G5. Native/client/paired proof разделены; update/association/opt-in и initial cycle без reset прежние.
- Сохранить у controlled `ai_rules_1c` правила сохранения исправлений/опыта, recall-first, `memory.md`, `rule-friction:`, TOOL-политику и отчётность. Согласовать managed binding у владельца fork; установленную копию не патчить. Проектные факты не направлять в общий templates-сервис.
- OpenViking оставить необязательным: нет установки, зеркалирования, нового классификатора или обязательного обхода второго backend. Явно подключённый провайдер участвует только в квалифицированной области и по upstream-политике; его отсутствие не является дефектом Cognee-only режима.
- Разделить ограниченный набор backend-кандидатов и меньшую выдачу агенту; сохранить query budget `ai_rules_1c`. Первый профиль использует CHUNKS без синтеза и `self_improvement=false` при поддержке версии. Считать запись, embeddings/graph extraction, проверки источников, повторное присутствие recall в контексте и прочие расходы всей задачи. Сравнить один Cognee с файловым baseline; экономия не объявляется заранее.

Это постановка будущего поведения. Исходные запросы разрешали только документы. Отдельный запрос 2026-10-19 разрешает предварительные native Q1–Q7 на тестовом экземпляре с harmless данными и фиксацию результатов; target/profile и фактический статус отражаются в test-plan. Реализация managed памяти, production изменения, каталог/базы 1С/controlled fork и публикация остаются вне этого разрешения.

## Capabilities

### New Capabilities

- `cognee-scope-storage`: шесть областей, штатные datasets, контекстная привязка общего подключения, подтверждение записи и исправление заметок.
- `memory-task-cycle`: память объединённой задачи/ветки/базы, точное продолжение и reset/resume у существующего lifecycle.
- `registry-memory-context`: использование согласованного каталожного снимка, применимость знаний и обновление контекста без второго updater.
- `memory-policy-and-budget`: совместимость с `ai_rules_1c`, optional OpenViking, ограниченные поиск/контекст, fallback и сравнительная приёмка.

### Modified Capabilities

Нет: основной `openspec/specs/` пока пуст; требования зависимого change реестра здесь не переопределяются.

## Impact

Будущие владельцы: ITL MCP helper/client writer и узкая Cognee-привязка, существующий lifecycle веток, resolver каталога из зависимого change; общая agent policy — controlled `ai_rules_1c`. Cognee остаётся внешним неизменённым продуктом. Ссылки на исходники, точные версии и снимок зависимой спеки приведены в [context-sources.md](context-sources.md).

Зависимость: сначала доступен и квалифицирован контекст `add-product-project-registry`, включая optional canonical home. Поле `knowledgeAreas.<area>.memoryHomeProductId`, его валидация и consumer contract согласованы в обеих постановках 2026-10-18; schema/resolver, подтверждённая seed-карта и installed qualification ещё не реализованы. Общий Cognee descriptor использует общие MCP settings, provider-local dataset IDs не помещаются в business catalog. Контрактные fixtures можно делать независимо, установленная приёмка требует реальной зависимости. Реестр остаётся отдельной неопубликованной постановкой в исходном checkout и не копируется в этот worktree; реализация памяти не становится условием выпуска реестра.

Не входят: реализация реестра, миграция всей истории чатов, исправление code/graph/productDocs MCP, разработка собственной памяти/графа, изменение исходников провайдеров, обязательный OpenViking, фоновая синхронизация, новая IAM-система, общая очередь или диспетчер lifecycle. Размещение экземпляра Cognee и допустимые модели — параметры отдельного canary; автоматическая установка и отправка рабочих данных этим change не разрешаются.

Архитектурная граница, альтернативы, совместимость и откат — [design.md](design.md); наблюдаемые критерии — [test-plan.md](test-plan.md). Подготовка документов не означает реализации или согласования будущего architecture checkpoint.
