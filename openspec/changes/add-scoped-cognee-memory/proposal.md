# Proposal

## Актуальная граница G3 — согласована 2026-10-25

**G3 закрыт в принятом PM5 / Windows 11 / Kilo и Cursor контуре; Codex — только core/API.** [Единая итоговая матрица и остаток до выпуска](../add-product-project-registry/g3-acceptance.md) определяет текущий статус, приоритетный перед историческими записями ниже. Непроверенные клетки не стали PASS; заявленная поддержка сохранена. Полная выпускная квалификация отделена от закрытого G3. G4, Gate 6, рабочая миграция и публикация не разрешены.

## Why

Агентам нужен повторно используемый опыт, относящийся к правильному проекту, продукту и циклу ветки/базы. Существующие локальные заметки и общий templates-сервис не дают этой модели; усложнять первый выпуск одинаковой интеграцией двух движков пользователь отказался.

## What Changes

- До первого выпуска каталога и первого выпуска памяти использовать обязательное подтверждённое наполнение реестра по registry AC-36–38: продукты/проекты, resolved настройки и карта основной функциональности. Memory AC-44 проверяет ту же зависимость, без второго наполнения, каталога или копирования документов в Cognee; minimal seed G2 не заменяет выпускные данные. Это не условие начала кода G4 и не разрешение G3/G4 сейчас.
- Использовать неизменённый Cognee как первый и достаточный поисковый backend. Шесть логических областей отображаются на штатные datasets: текущая задача/ветка/база, локальный проект, рабочее место пользователя, продукт, проект, организация. Личные datasets создаются по необходимости; общие один раз подготавливает администратор штатными средствами Cognee с точными IDs и grants.
- Каждая запись получает явную наиболее узкую достаточную область через стандартный `dataset_name`; постоянное условие проекта не теряется после reset вместе с task memory. Неопределённое назначение остаётся локальным кандидатом, без автоматического расширения доступа.
- Получать `projectId`, `productId`, источники и правила применимости из отдельного change `add-product-project-registry`. Для общего продуктового знания определить одно каноническое место и разрешённый read set: факт из ERP+PM может храниться в PM КОРП и использоваться в ПРОФ только по подтверждённой области. Требуемое необязательное расширение интерфейса реестра описать явно, без изменения его спеки и без второго каталога/resolver/updater.
- Различать текущий проект и выбранный MCP-source: опубликованные название/версия/индексация из registry, business origin/назначение источника и подтверждённые доработки/ограничения из каталога. Поддержать custom PM5 КОРП → типовой MCP и PM5 ПРОФ → MCP КОРП через ту же карту применимости. Отсутствие source generation/hash не требует доработок Code/Graph и само не делает все факты непроверенными; native Cognee currentness/grants остаются обязательными по прежним правилам.
- Разделить searchable knowledge и точное состояние: полезный опыт хранить в Cognee, настройки и lifecycle читать у существующих владельцев; компактное продолжение задачи сохранять локально вне сбрасываемого дерева.
- Добавить узкую ITL-привязку штатных вызовов Cognee к проверенному пользовательскому контексту и разрешённым datasets. Общий экземпляр памяти не становится четвёртой проектной MCP-ролью. Ограничение dataset и права действуют до извлечения; актуальность и происхождение найденного фрагмента подтверждаются штатным точным чтением/статусом независимо от попадания исправления в semantic top_k. Недостающие native возможности требуют пересмотра допуска, а не своего сервиса версий.
- Привязать память задачи к циклу существующего lifecycle. Reset создаёт новый цикл даже при неизменном HEAD; resume продолжает тот же переход, старые записи остаются историей.
- Перед зависимой разработкой пройти native Q1–Q7: exact shared IDs/права, изоляция, durable/status, current original в допущенном store, precise retirement/revoke, административный допуск после restore и bounded retrieval/измеримый ограниченный профиль. Q5 допускает состояние backup на дату T с явным интервалом потери и проверкой до возврата доступа; Q7 измеряет весь прогон с estimates/unknown без обязательного счётчика каждой внутренней операции. Полное paired сравнение — G5. После обновления/ассоциации память включается отдельно, initial cycle без reset, старые заметки не импортируются автоматически.
- Сохранить у controlled `ai_rules_1c` правила сохранения исправлений/опыта, recall-first, `memory.md`, `rule-friction:`, TOOL-политику и отчётность. Согласовать managed binding у владельца fork; установленную копию не патчить. Проектные факты не направлять в общий templates-сервис.
- OpenViking оставить необязательным: нет установки, зеркалирования, нового классификатора или обязательного обхода второго backend. Явно подключённый провайдер участвует только в квалифицированной области и по upstream-политике; его отсутствие не является дефектом Cognee-only режима.
- Разделить ограниченный набор backend-кандидатов и меньшую выдачу агенту; сохранить query budget `ai_rules_1c`. Первый профиль использует CHUNKS без синтеза и `self_improvement=false` при поддержке версии. Считать запись, embeddings/graph extraction, проверки источников, повторное присутствие recall в контексте и прочие расходы всей задачи. Сравнить один Cognee с файловым baseline; экономия не объявляется заранее.

Это постановка будущего поведения. Исходные запросы разрешали только документы. Отдельный запрос 2026-10-19 разрешает предварительные native Q1–Q7 на тестовом экземпляре с harmless данными и фиксацию результатов; target/profile и фактический статус отражаются в test-plan. Реализация managed памяти, production изменения, каталог/базы 1С/controlled fork и публикация остаются вне этого разрешения.

## Capabilities

### New Capabilities

- `cognee-scope-storage`: шесть областей, штатные datasets, пользовательская привязка, подтверждение записи и исправление заметок.
- `memory-task-cycle`: память объединённой задачи/ветки/базы, точное продолжение и reset/resume у существующего lifecycle.
- `registry-memory-context`: использование согласованного каталожного снимка, применимость знаний и обновление контекста без второго updater.
- `memory-policy-and-budget`: совместимость с `ai_rules_1c`, optional OpenViking, ограниченные поиск/контекст, fallback и сравнительная приёмка.

### Modified Capabilities

Нет: основной `openspec/specs/` пока пуст; требования зависимого change реестра здесь не переопределяются.

## Impact

Будущие владельцы: ITL MCP helper/client writer и узкая Cognee-привязка, существующий lifecycle веток, resolver каталога из зависимого change; общая agent policy — controlled `ai_rules_1c`. Cognee остаётся внешним неизменённым продуктом. Ссылки на исходники, точные версии и снимок зависимой спеки приведены в [context-sources.md](context-sources.md).

Зависимость: сначала доступен и квалифицирован контекст `add-product-project-registry`, включая optional canonical home. Поле `knowledgeAreas.<area>.memoryHomeProductId`, его валидация и consumer contract согласованы в обеих постановках 2026-10-18; schema/resolver, подтверждённая seed-карта и installed qualification ещё не реализованы. Общий Cognee descriptor использует общие MCP settings, provider-local dataset IDs не помещаются в business catalog. Контрактные fixtures можно делать независимо, установленная приёмка требует реальной зависимости. Реестр остаётся отдельной неопубликованной постановкой в исходном checkout и не копируется в этот worktree; реализация памяти не становится условием выпуска реестра.

Не входят: реализация реестра, миграция всей истории чатов, исправление code/graph/productDocs MCP, разработка собственной памяти/графа, изменение исходников провайдеров, обязательный OpenViking, фоновая синхронизация, новая IAM-система, общая очередь или диспетчер lifecycle. Размещение экземпляра Cognee и допустимые модели — параметры отдельного canary; автоматическая установка и отправка рабочих данных этим change не разрешаются.

Архитектурная граница, альтернативы, совместимость и откат — [design.md](design.md); наблюдаемые критерии — [test-plan.md](test-plan.md). Подготовка документов не означает реализации или согласования будущего architecture checkpoint.

Общий порядок G0–G6 согласован с registry change 2026-10-19: каталог независим, native G1 предшествует memory G4, installed G5 требует применённый registry context. По поручению «иди по плану» выполнен этап C: пересмотренные Q5/Q7 passed, прежние Q1–Q4/Q6 reuse подтверждены identities профиля. Исходный Q5 failed/старый Q7 unverified сохранены. Files-only baseline подготовлен до managed retrieval tuning, сравнение/экономия не объявлены. G1 закрыт для local profile; до G4 нужны qualified G2/D9. Реализация не начата; фактический proof и оставшиеся installed границы — test-plan, этап C.

Предыдущая фаза планирования 2026-10-19 подготовила конкретный checkpoint D9: owner/state boundaries, bounded cancel/recovery, compatibility/context/canary и rollback. На том этапе отдельного одобрения D9 ещё не было; последующее решение пользователя приведено ниже. G2.1–5 и code/consumer handoff критерий закреплены у registry owner; pure G2 не блокируется D9 памяти. До G4 нужны вместе G1, квалифицированный G2 interface и одобренный D9/разрешение кода. Planning фаза не меняла provider/fork/installed state.

Последующее прямое решение пользователя: D9 согласован, разрешён только G2 реестра; G4/installed migration запрещены. G2 pure interface реализован и qualified owner/consumer tests; фактические ссылки/границы — test-plan реестра и context-sources. Согласование D9 не объявляет реализацию/приёмку памяти.

Затем пользователь отдельно разрешил G3 и его квалификацию. После failed server capabilities 2026-10-19 отдельно разрешено обновление BookStack/Mantis/СППР на dev-ermakov: на 2026-10-20 три attested G3 builds активны, 29 live controls и десять исходных Python suites passed. Full installed/client/platform приёмка G3 открыта. Статус зависимости и единый источник evidence — этот test-plan и registry owner. Это не отменяет passed G1, qualified G2 или approved D9 и не разрешает G4/рабочую миграцию/публикацию workflow. Память не получает собственного updater или обхода server scope.

После Code/Graph/client-file/startup прогона registry owner исправил hidden-console blocker и повторил исходный native PM5 unattended update из прежней capsule: whole command passed без association/consent/defer. [Актуальная зависимость](test-plan.md#повтор-pm5-после-исправления-input-owner-2026-10-20) сохраняет полный registry AC-39 / memory AC-43/G5 открытым: foreground/installed/client/platform критерии ещё не приняты. Шесть областей, ai_rules_1c, обязательное наполнение и запрет G4 прежние.

## Уточнение зависимости источников, 2026-10-21

Memory потребляет [действующий registry context](../add-product-project-registry/design.md#различия-проекта-и-подключённого-mcp-источника), без собственного verifier/updater и требований backend patches Code/Graph. Исторические exact-index/image gaps больше не блокируют G3/G5; six scopes/canonical home/ai_rules_1c/OpenViking и отдельный G4 approval прежние. Документы не реализуют новый consumer и не закрывают AC-43/G5/44; Gate 6, G4, рабочая миграция и публикация не начинаются.
