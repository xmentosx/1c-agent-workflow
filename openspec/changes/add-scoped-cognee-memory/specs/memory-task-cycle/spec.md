# Spec Delta

## Purpose

Надёжно продолжать текущую работу и отделять знания прежнего состояния базы после reset, используя существующий lifecycle без дополнительного контроллера.

## ADDED Requirements

### Requirement: Продолжение задачи читается напрямую

Система SHALL хранить компактную запись продолжения вне сбрасываемого дерева с привязкой к workspace/cycle. Она SHALL включать цель, ограничения, принятые решения, выполненное, следующий шаг и ссылки на доказательства, а не копию всех журналов. Она SHALL NOT владеть статусом проверок, lifecycle, правами на действия или заменять preflight. Актуальность базы SHALL проверяться у существующего владельца.

#### Scenario: Новый чат продолжает текущую задачу
- **WHEN** агент начинает новый сеанс того же цикла
- **THEN** цель и следующий шаг восстанавливаются прямым чтением, независимо от полноты семантического поиска; устаревшая ссылка на проверку не становится новым proof

### Requirement: Reset создаёт новый цикл у владельца lifecycle

Новая задача после reset SHALL получать новый cycle ID независимо от изменения HEAD/имён. Выделение ID, pending transition и activation SHALL принадлежать существующей операции lifecycle. Повтор прерванного reset SHALL использовать тот же выделенный цикл; активировать его можно только после успешного восстановления. Недоступный Cognee SHALL NOT блокировать независимую операцию reset и SHALL NOT требовать ручной правки состояния/lock.

#### Scenario: Reset без нового commit
- **WHEN** дерево уже совпадает с master и база восстанавливается при прежнем HEAD
- **THEN** прежняя task memory не участвует в обычной выдаче нового цикла, а workspace/product/project знания сохраняются

#### Scenario: Прерывание между фазами
- **WHEN** reset прерван после выделения ID или восстановления базы и продолжен штатным helper
- **THEN** продолжается тот же переход, не создаётся третья задача; до завершения память не утверждает готовность новой базы

### Requirement: Старый контекст не становится новым

Запрос SHALL оставаться связанным с тем cycle, для которого создан. После reset старый инструмент/чат SHALL NOT писать заметки о состоянии в новый цикл. Архивная task memory SHALL быть доступна только при явном историческом запросе с указанием происхождения; обычный запрос нового цикла её исключает до retrieval.

#### Scenario: Поздний remember из старого чата
- **WHEN** remember прежнего сеанса приходит после успешного reset
- **THEN** он остаётся записью старого цикла либо отклоняется как устаревший контекст с продолжением; новый цикл не получает старое утверждение об установленном исправлении

### Requirement: Исторический опыт переживает сброс через свою область

Reset SHALL NOT автоматически удалять историю, переносить все заметки в продукт или массово переклассифицировать их. Обобщённый опыт SHALL сохраняться в более общей области только по подтверждённой применимости и правам. Утверждение о фактической установке/проверке в базе SHALL оставаться привязанным к исходному циклу.

#### Scenario: Решение и состояние базы
- **WHEN** в старой задаче установлено исправление и подтверждена общая причина ошибки
- **THEN** общее решение может сохраниться в product/project memory с evidence, но новое состояние базы требует нового подтверждения

#### Scenario: Постоянное исправление после reset
- **WHEN** пользователь уточнил постоянное условие проекта или локальной установки, агент явно сохранил его в project/workspace и затем выполнен reset
- **THEN** новый чат получает это условие из прежней устойчивой области и меняет действие с его учётом; старое состояние базы при этом не считается текущим

### Requirement: Локальный резерв не теряется при reset

Датированные pending/unconfirmed записи и receipts SHALL храниться вне сбрасываемого дерева с исходным scope/cycle. Новый memory-only сеанс SHALL напрямую обнаруживать и ограниченно читать относящиеся к текущему scope pending записи даже при недоступном/отсутствующем Cognee. Постоянное project/workspace условие SHALL оставаться доступным после reset; старый task state SHALL оставаться историей. Перенос в provider SHALL происходить только после сверки исхода и в ту же допустимую область. Memory fallback SHALL NOT ослаблять clean-tree guards или автоматически коммитить файлы ради reset.

#### Scenario: Недоступный backend и повторная задача
- **WHEN** локальная заметка осталась pending, затем ветка сброшена и backend восстановился
- **THEN** заметка не мигрирует в новый task dataset; её исходная область сохраняется и состояние не объявляется текущим

### Requirement: Первое включение существующей ветки не сбрасывает базу

При первом применении default-on qualified памяти либо явном повторном включении existing lifecycle/state owner SHALL сохранять workspace/developer/workplace references и выделять initial current cycle для существующей ветки без reset/init/восстановления базы. Повтор, interrupt/resume и конкурентные сеансы SHALL использовать уже выделенные IDs через прежний writer/hash ownership; отключение/повторное включение SHALL NOT создавать новый cycle вместо reset. Новый cycle SHALL обозначать scope, SHALL NOT подтверждать установку исправлений/прохождение проверок. Неперечитанный старый контекст SHALL NOT писать в новую task область до verified binding. Другие existing worktrees SHALL NOT мигрировать автоматически.

#### Scenario: Включение памяти в рабочей ветке
- **WHEN** существующий registry-bound проект в отдельно разрешённом setup впервые применяет qualified память по default-on policy и затем повторяет/продолжает включение
- **THEN** назначены устойчивые local IDs и один initial cycle, база/HEAD не сбрасываются, другие worktrees не меняются; runtime актуальность проверяется у прежнего владельца

#### Scenario: Две сессии и старый чат
- **WHEN** два сеанса одновременно завершают первое включение, а прежний чат не перечитал binding
- **THEN** существующий owner сохраняет одни IDs/current cycle, старый чат получает продолжение для reload и не загрязняет новую task область
