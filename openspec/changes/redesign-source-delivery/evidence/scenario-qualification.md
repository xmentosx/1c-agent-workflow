# Develop scenario qualification boundary

Architecture checkpoint approved by the user on 2026-10-24: replace whole-journey
coverage with scenario coverage inside the existing source qualification owner,
canonicalize actual client selection, retain strict checks, register the change
and show Plan. Publication remains unauthorized.

The invariant is complete, applicable coverage for the integrated candidate:
each required scenario has actual passed execution or authenticated equivalent
prior evidence. There is one quality catalog and one qualification cache. No
new coordinator, queue, installed lifecycle API, migration, elevation or client
configuration authority is introduced.

The original upgrade/positive/negative and fresh golden/stale/refresh/close
reproducers remain executable. Native summary schema 3 and route schema 2 make
partial execution explicit. Execution-only route schema 3 stores passed subsets
without claiming full qualification. Scope composition is accepted only after current
complete static proof; immutable native evidence and prior report/manifest SHA
checks prevent mutable logs and self-referential certificates authorizing reuse.
Unknown inputs and legacy failures remain conservative. Current-native helper
inputs are bound alongside the runner; controller-only function projections do
not exclude unknown top-level code or newly introduced functions.

Compatibility is read-only for old receipts: schema 1 represents the original
complete journey, with its original hashes and environment. Changed workload,
missing inputs or changed scenario policy can require a first baseline. Reverting
the change returns to the complete route; old supervisors fail closed on new
route schemas instead of treating a partial execution as full qualification.

Foreground hard/no-progress deadlines, stage status, leases, snapshots, disposal
and existing recovery owners remain in force. Failure/interruption retains the
original diagnostics and queue; partial progress cannot become passed coverage.
Unselected journeys may continue valid evidence but cannot launch new native work
implicitly. Actual canary and warm/retry qualification are required to claim an
operational improvement; unit or native-child fixtures alone do not establish it.

Maintained acceptance matrix: update-only/fresh-only/controller/test selection;
MCP writer consumer and prerequisite closure; unchanged-input reuse without a
native launch; sole/default and ambiguous client selection; runtime, fork, UI,
artifact, unknown-input, report, native-evidence and newer-failure rejection.
For the stateless client JSON writer, upgrade update and fresh install/branch
are the native representative producers. The current complete static proof
also covers its preservation, planning and atomic-write contract. Unchanged
verification, stale-export, refresh and close consumers retain their prior
scenario proof only after those current producers pass. This projection is
limited to a known stand with product context disabled in every target root;
enabled/unknown product context, pending operations, new ambient dependencies,
unmapped functions or top-level changes keep conservative native coverage.
Scenario changes must update this matrix and explain measured cost without
increasing targets.
