# Design

## Context

`get-review-scope` (`agent-1c.review-scope.ps1`) уже:
- определяет базу ветки через `Get-DevBranchTransferScopeBaseline`;
- классифицирует пути по видам;
- собирает объекты 1С (`Get-ReviewScopeSubjectObjects`);
- для самопроверки откатывается на `local-delta`, то есть сравнение с `HEAD`.

По контракту он только читает данные: не берёт блокировок, не пишет состояние, индекс, дерево, объекты и ссылки Git. Свежесть проверки ветки рассчитывает `Get-VerificationState` (`agent-1c.vanessa.ps1`). Он сравнивает отпечаток проверенного кода с текущим. При незакоммиченных изменениях отпечаток строится через временный индекс (`New-VerificationEffectiveTree`), и в базу объектов Git попадают неиспользуемые объекты. `/itl-check` выполняет Designer `/CheckModules` при каждой загрузке редактируемых исходников (`verification-result.md`).

Правила ревью (`review-criteria.md`) и описание агента-ревьюера принадлежат controlled fork `ai_rules_1c`, корневые ITL-правила — `templates/ai-rules-overlay/AGENTS.md`. Мотивация и данные — в `proposal.md`.

## Goals / Non-Goals

**Goals:**
- Посильный объём отдельного ревью с выбором, который делает пользователь, а не агент.
- Одно доказательство синтаксиса ветки при любом объёме: свежий `/itl-check`.
- Тот же отчёт и то же поведение для нормальных объёмов.

**Non-Goals:**
- Монтирование worktree или базы в удалённые MCP-серверы, локальный BSL LS.
- Ревью «с прошлого ревью»: записанной точки прошлого ревью нет; при необходимости — отдельное изменение.
- Изменение самопроверки и гейта 1 при разработке.
- Запуск `/itl-check` или иных команд жизненного цикла из ревью.

## Decisions

### Мера размера — текст изменений BSL в байтах, порог 300 КБ

Ревью читает изменения, а не модули целиком. Текст изменений в байтах ближе всего к расходу контекста. Число строк неточно: строки разной длины.

Отвергнуты:
- размер изменённых модулей: в PM5 он превышает 300 КБ почти в любой ветке с BSL, и большим был бы почти любой объём;
- число объектов: XML читается по объектам и почти не влияет на контекст.

Порог 300 КБ (~4–5 тыс. строк, ~80–100 тыс. токенов кириллицы) лежит в пустом промежутке данных PM5 между 90 и 526 КБ. Порог — одна константа помощника, изменить её дёшево.

### Выбор через состояние и повтор вызова

Помощник не может спросить пользователя: его запускает агент, без интерактивного ввода. При большом объёме без диапазона он завершается этапом `review-scope.range-required`. Отчёт содержит готовый вопрос, варианты с размерами и точные команды повтора:
- `-ReviewRange uncommitted`;
- `-ReviewRange since -ReviewSince <commit>`;
- `-ReviewRange branch`.

Текст вопроса принадлежит помощнику, агент его только передаёт. Это соответствует правилу «prompts принадлежат скрипту». Остановка касается только `review` и сразу даёт продолжение: повтор с выбранным диапазоном. По этому пути пользователь доходит до того же ревью.

Явный `-ReviewRange branch` на большом объёме проходит без вопроса, а отчёт помечает режим большого объёма.

Отвергнут вариант «всегда выдавать весь объём и предупреждать»: агент начинает ревью сам, и выбор теряется.

### Незакоммиченные — существующая база `HEAD`

`uncommitted` использует ту же базу `HEAD`, что и откат самопроверки `local-delta`, но с происхождением `uncommitted`. Новой логики сравнения нет.

### Допустимые коммиты — вся собственная линия ветки

Помощник проходит первую родительскую линию от `HEAD` и останавливается на первом из событий:
- коммит сброса ветки (отметка «сброс»);
- граница базы ветки;
- 15 показанных пунктов (просмотр — до 200 коммитов).

Слияние из master не останавливает список, а входит в него отметкой «обновление из master».

Для коммита X без слияния до `HEAD` база — родитель X (для отметки — она сама), сравнение с рабочим деревом. Изменений master в объёме нет.

Для коммита X до слияния база — база ветки, а пути ограничены файлами, которые меняли собственные коммиты первой линии начиная с X (`git log --first-parent --no-merges`) и незакоммиченная работа. База ветки после refresh — сам master, поэтому изменений master в объёме нет. В тех же файлах видны более ранние правки ветки; вариант и отчёт об этом сообщают.

Первая версия ограничивала список коммитами после последнего слияния. На PM5 `1-branch4` вся основная работа лежала до обновления, и выбрать её можно было только целиком. Сравнение `X..рабочее дерево` через слияние действительно принесло бы изменения master. Сравнение от базы ветки с фильтром путей их не приносит.

### Вопрос — плоский нумерованный список

Каждый коммит — отдельный пронумерованный вариант. Агент показывает все варианты списком или таблицей и просит номер. Вложенный список коммитов внутри одного варианта агенты сводили к кнопкам диалога (не больше 4), и остальные коммиты пользователь не видел.

### Описание коммитов

- **Служебный коммит** — коммит без путей предмета ревью. Такие коммиты сворачиваются в счётчик.
- **Автоматический коммит ITL с работой** распознаётся по заголовкам, которые создаёт сам помощник: `chore: checkpoint before …`, `chore: persist …`, `sync: copy combined 1C sources …`. Вместо заголовка показывается пояснение, например «автосохранение работы перед обновлением из master». Регрессионный тест сверяет таблицу заголовков с местами в коде, где помощник их создаёт. Это защищает от расхождения без переноса заголовков в общую константу.
- **Объекты** собирает существующий `Get-ReviewScopeSubjectObjects`.
- **Итоговый объём пункта** считается тем же расчётом, что и размер объёма.
- **Отметка `/itl-check`** — по коммиту проверки из `Get-VerificationState`.

### Свежесть — существующий владелец; контракт «только чтение» сохраняется

Помощник вызывает `Get-VerificationState`, своего расчёта свежести у ревью нет. Состояния отображаются так:
- `status=passed` при совпадении текущего и проверенного отпечатков → «пройдена на текущем коде»; незавершённая приёмка задачи показывается отдельной пометкой и не отменяет доказательство синтаксиса;
- `passed` с другим отпечатком или `stale` → «устарела»;
- `partial` → «неполная»;
- `failed` → «не пройдена»;
- нет записи → «не выполнялась»;
- нет текущего отпечатка или ошибка → «не определено».

Временный индекс отпечатка создаёт объекты Git. Чтобы контракт «не пишет объекты» сохранился, вызов идёт с `GIT_OBJECT_DIRECTORY`, указывающим на временный каталог. Существующие объекты читаются через `GIT_ALTERNATE_OBJECT_DIRECTORIES`. После вызова каталог удаляется, а `GIT_OPTIONAL_LOCKS=0` исключает фоновую запись индекса. Существующий тест «только чтение» и новый тест на грязном дереве это проверяют.

Отвергнуты:
- ослабить контракт до «неиспользуемые объекты допустимы»: обходной путь с временным каталогом объектов дешевле и сохраняет обещание;
- не показывать свежесть при незакоммиченных изменениях: это типичное состояние, и свежий результат бы скрывался;
- отдельный расчёт без записи: второй владелец одного инварианта.

### Размещение правил

- **Fork `review-criteria.md`, общее правило.** Проверка, которую записал проект и которая привязана к текущему содержимому, — доказательство, а не отчёт автора. При большом объёме гейты 2–3 запускаются по процедурам, выбранным по риску, с указанием непроверенного остатка. Если проект предоставляет выбор диапазона, он соблюдается.
- **ITL overlay `AGENTS.md`.** Одна строка: на хостах ITL проверка по пути недоступна, нужно передавать текст. Это постоянный контекст, около 40 токенов; при реализации прирост измеряется.
- **`verification-result.md#review-scope`.** Подробности варианта выбора и свежести; читаются по требованию.

Порядок поставки. Выпуск форка r53 (`claude/review-minor-fixes-r53`) уже стоит в очереди `develop` и меняет те же записи журнала форка и пин. Поэтому правило форка и строка overlay выпускаются как r54 поверх r53 после его публикации. ITL-часть поставляется раньше и работает сама: `AGENTS.md` проекта уже направляет ревью в `verification-result.md#review-scope`, где описаны выбор диапазона и доказательство гейтов.

Архитектурный checkpoint не нужен. Нет нового координатора, состояния, блокировок или миграции, команды жизненного цикла не перехватываются. Прирост постоянного контекста — одна строка.

## Risks / Trade-offs

- **Порог подобран по одному проекту.** → Одна константа; в отчёте видны цифры, и пользователь может явно выбрать `branch`.
- **Расчёт отпечатка и размеров на больших ветках может занять секунды.** → При реализации замерить на PM5 `1-branch4`. Расчёт размеров по коммитам ограничен 15 пунктами.
- **Неизвестный будущий заголовок автоматического коммита покажется как обычный.** → Регрессионный тест таблицы заголовков; при сбое показывается только заголовок, ошибки нет.
- **Выпуск форка r53 добавляет цикл поставки.** → Правило форка короткое; ITL-часть работает и без него, а форк лишь закрепляет правило доказательства.

## Migration Plan

Миграции состояния нет. Существующие вызовы без `-ReviewRange` на нормальных объёмах работают как раньше. Откат — возврат коммитов ITL и пина форка.
