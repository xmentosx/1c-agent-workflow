# Quick-fix в ветке разработки

Используйте этот reference после того, как upstream `AGENTS.md` и `verification-policy.md` независимо определили `executionPath=quick-fix` и `planningMode=direct`. Если eligibility limits нарушены или найден promotion trigger, переключите только execution path на `full-cycle`; planning mode остаётся `direct`, пока пользовательский запрос или ценность формального согласования отдельно не выберут OpenSpec.

Этот leaf описывает direct quick-fix без OpenSpec.

## Общее правило готовности

Здесь `itldev/*` означает текущее имя Git-ветки (`git branch --show-current`), а не каталог или файловый glob. В такой ветке доработка под `exportPath`/`extensionsPath` проходит оценку применимых обязательств и fresh passed `/itl-check`; `testsPath` хранит сохраняемые тесты, а достаточное one-off proof не требует фиктивного файла теста. Запущенный runner с zero tests, invalid JUnit или failure остаётся ошибкой. На `master` правка исходников остаётся branch-safety blocker.

Перед тестами локального алгоритма агент читает `references/yaxunit-tests.md`; перед Vanessa-тестами — `references/vanessa-tests.md`. Режим `off` запрещает автоматический запуск, но не создание теста и не повторное использование уже свежего достаточного proof. При отсутствии такого proof пропуск остаётся partial: `verificationPolicy=block` блокирует result/close, `warn` допускает экспорт с предупреждением; закрытие ветки требует отдельного подтверждения.

### 1. Поставить задачу

```text
Сделай quick-fix без OpenSpec.

Проблема:
<описание ошибки>

Ожидаемый результат:
<что должно работать>

Ограничения:
- меняй минимально необходимый код;
- не меняй архитектуру;
- не добавляй новые метаданные;
- если выяснится, что задача больше quick-fix, переключи execution path на full-cycle; planning mode оставь direct, пока отдельно не нужен OpenSpec.
```

### 2. Реализовать исправление

Агент должен:

- найти место ошибки;
- внести минимальное исправление;
- создать или обновить целевой regression test: YAxUnit для локального алгоритма, Vanessa в `tests/features` для интеграции или UI;
- проверить синтаксис;
- кратко написать, какие файлы изменены;
- описать, чем проверено.

Если во время quick-fix обнаружен upstream promotion trigger или нарушены eligibility limits, execution path переключается на full-cycle. Planning mode остаётся direct, если отдельно не выбран OpenSpec для формального исследования и согласования.

### 3. Обновить базу ветки разработки

После изменения файлов обязательно обновите базу ветки разработки.

В Kilo Code:

```text
/itl-check
```

В Codex:

```text
$itl-check
```

Агент должен обновить копию базы текущей ветки разработки измененными файлами конфигурации.

### 4. Протестировать исправление

Обычная оценка исполняемых доказательств выполняется через:

```text
/itl-check
```

Для quick-fix переиспользуйте достаточное существующее proof; при пробеле получите целевой текущий результат. Сохраняемый regression test добавьте, если он нужен для будущих изменений, и ограничьте каждый дополнительный сценарий отдельным значимым риском. Если нарушены upstream eligibility limits, execution path переключается на full-cycle; planning mode от этого автоматически не меняется.

Тип проверки выбирается по сути изменения: YAxUnit — для локальной логики и её границ, Vanessa integration — для взаимодействия объектов, регистров, документов или обменов, Vanessa UI — для форм, команд и видимого поведения. При пересечении рисков нужны оба слоя.

Если проверка упала, агент анализирует отчёт runner, лог 1С и изменённый код, исправляет причину и повторяет нужную проверку в пределах одной persisted repair session. Её лимит и восстановление принадлежат helper; исчерпание бюджета даёт честную диагностику без нового скрытого цикла.

Перед выгрузкой `CF` и закрытием ветки helper оценивает актуальные доказательства: `block` требует достаточный fresh pass, `warn` сохраняет явно предупреждённый экспорт при неполной проверке. Review не подменяет runtime proof.
