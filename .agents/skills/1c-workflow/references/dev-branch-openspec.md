# OpenSpec в ветке разработки

Используйте этот reference при `planningMode=OpenSpec`: пользователь явно запросил OpenSpec либо формальное исследование и согласование требований, архитектуры, критериев приёмки или этапов реализации действительно добавляет ценность. `executionPath=quick-fix|full-cycle` выбирается независимо по upstream eligibility/promotion policy. Promotion trigger меняет только execution path и сам по себе не требует OpenSpec.

## Общее правило готовности

Здесь `itldev/*` означает текущее имя Git-ветки (`git branch --show-current`), а не каталог или файловый glob. В такой ветке любая доработка агентом под настроенными `exportPath`/`extensionsPath` считается готовой только после релевантных сценариев под `testsPath` и fresh passed `/itl-check`; OpenSpec исключений не даёт. Явно выбранный ITL lite допускает только partial evidence с формулировкой `implemented; executable verification skipped`. На `master` правка исходников остаётся branch-safety blocker.

Перед тестами алгоритма агент читает `references/yaxunit-tests.md`; перед Vanessa-тестами — `references/vanessa-tests.md`. Слой с режимом `off` автоматически не создаётся и в новый план не добавляется. Пропуск никогда не называется `готово/verified/done`; при `verificationPolicy=block` он блокирует result/close, при `warn` требует явного подтверждения partial result.

Для больших OpenSpec changes действует hybrid cadence: каждый срез с наблюдаемым поведением получает минимум один focused Vanessa scenario и дешёвые targeted/static checks изменённого BSL, XML, формы и feature-файла. Промежуточный `/itl-check` нужен только на milestone, где runtime-результат решает, можно ли продолжать выбранную реализацию. Подготовительные tasks фиксируются как pending verification. После последней verification-relevant правки обязателен fresh unfiltered `/itl-check` по всему разрешённому набору сценариев.

## Процесс

OpenSpec используем для задач, где нужно описать, согласовать и потом реализовать изменение.

Обычно начинайте с propose entrypoint, который показывает `/itl`. `/opsx-explore` — optional шаг, нужный только когда перед proposal не хватает понимания текущего кода, границ задачи или возможного подхода. `/opsx-*` ниже — пример native-синтаксиса, а не универсальный контракт. В Codex используйте явные `$opsx-explore`, `$opsx-propose`, `$opsx-apply` и `$opsx-archive`; канонические `openspec-*` остаются доступными модели для неявного выбора.

`/opsx-propose` создаёт proposal и остальные согласуемые OpenSpec-артефакты без изменения кода.

В `natural`-режиме те же этапы вызываются обычными запросами:

```text
Исследуй задачу в режиме OpenSpec, не создавая proposal и не меняя код
Подготовь OpenSpec proposal для <изменение>; создай proposal, design, tasks, test-plan и spec deltas; код не меняй
Реализуй согласованный OpenSpec change <change-id> по tasks.md и test-plan.md
Заархивируй принятый OpenSpec change <change-id> и синхронизируй specs
```

Оба режима используют один `openspec/` workspace, общий preflight и fresh `/itl-check`. Отсутствие внешнего `openspec` executable не блокирует natural flow. Не устанавливайте пакет автоматически и не запускайте `openspec update`.

### 0. Исследовать контекст, если нужно

```text
/opsx-explore
```

Этот шаг опционален. Агент исследует код, текущую реализацию и границы задачи, но не создает proposal и не меняет код.

### 1. Создать proposal

```text
/opsx-propose

Подготовь OpenSpec proposal для <изменение>; создай proposal, design, tasks, test-plan и spec deltas; код не меняй.

Нужно:
<описание задачи>

Контекст:
<что известно про текущую реализацию>

Ожидаемый результат:
<как должно работать после изменения>
```

На этом шаге агент должен подготовить OpenSpec-артефакты:

- `proposal.md` - что и зачем меняем;
- `design.md` - как технически реализуем, если изменение не тривиальное;
- `tasks.md` - какие конкретные задачи будут выполнены;
- `test-plan.md` - какие YAxUnit unit-проверки покрывают алгоритмические классы эквивалентности и границы, какие 1-2 Vanessa integration/UI сценария проверяют сквозное поведение, и какие опасные негативные случаи остаются;
- spec deltas - какие требования меняются или добавляются.

Код на этом шаге не меняется.

### 2. Проверить документы OpenSpec

Разработчик проверяет:

- понятно ли, какую проблему решаем;
- соответствует ли proposal исходной задаче;
- достаточно ли конкретный design;
- можно ли по `tasks.md` выполнить реализацию без догадок;
- указаны ли Vanessa-проверки результата и понятно ли, после каких шагов их запускать.

Если план непонятный, попросите уточнить:

```text
Уточни OpenSpec proposal.
Разбей tasks.md на конкретные маленькие шаги с указанием объектов, модулей, процедур и проверок.
Код пока не меняй.
```

### 3. Согласовать реализацию

Код пишется только после того, как разработчик согласовал:

- `proposal.md`;
- `design.md`, если он нужен;
- `tasks.md`;
- изменения требований в spec deltas.

Если решение затрагивает архитектуру, метаданные, интеграции или права, согласование обязательно.

### 4. Реализовать изменение

```text
/opsx-apply

Реализуй согласованный OpenSpec change <change-id> по tasks.md и test-plan.md.
Действуй строго по tasks.md.
После каждого значимого шага отмечай выполненные задачи.
```

Агент реализует задачи из `tasks.md` и отмечает выполненные пункты.

Если изменение большое или состоит из нескольких самостоятельных шагов, агент обязан разбить работу на проверяемые срезы. Для каждого среза с наблюдаемым поведением он добавляет или обновляет минимум один focused Vanessa scenario и выполняет самые дешёвые достаточные targeted/static проверки. Не запускайте `/itl-check` автоматически после каждого среза. Подготовительные tasks без самостоятельного наблюдаемого поведения фиксируются как pending verification и покрываются ближайшим последующим проверяемым срезом.

### 5. Выполнить executable milestone или финальную проверку

Промежуточный `/itl-check` выполняется только на milestone, где фактическая загрузка или поведение 1С решает, можно ли продолжать выбранную реализацию либо её нужно переделать. После последней verification-relevant правки обязательно выполните финальный `/itl-check`.

В Kilo Code:

```text
/itl-check
```

В Codex:

```text
$itl-check
```

Helper обновит копию базы текущей ветки разработки изменёнными файлами конфигурации и запустит Vanessa Automation. Финальный запуск должен быть обычным unfiltered `/itl-check` без `VanessaFeaturePath` и `VanessaFilterTags`, чтобы проверить весь разрешённый набор сценариев на точном финальном fingerprint. Если проверка потребовала verification-relevant правок, предыдущий pass становится stale и после последней правки нужен новый финальный запуск. Не запускайте после этого `/deploy-and-test`, потому что он повторит тот же полный цикл.

### 6. Протестировать сценарий через Vanessa Automation

Vanessa Automation - стандартный тестовый фреймворк ветки разработки. Тесты хранятся в `tests/features`, отчеты - в `build/test-results/vanessa`.

Перед созданием или правкой тестов агент читает только соответствующий слой: `references/yaxunit-tests.md` для алгоритмов либо `references/vanessa-tests.md` для интеграции/UI; для обычных lifecycle-команд эти файлы не нужны.

Минимальный набор проверок:

- синтаксис BSL;
- корректность измененных metadata XML;
- выполнение всех пунктов `tasks.md`;
- отсутствие лишних изменений;
- 2-3 Vanessa-проверки измененного бизнес-поведения по умолчанию: основной успешный сценарий и минимум один значимый граничный или негативный сценарий; четвертая проверка требует краткого обоснования.

Тип Vanessa-сценария выбирается по сути изменения:

- YAxUnit unit - для прикладной логики, расчетов, условий, заполнения данных и пограничной матрицы;
- integration - для взаимодействия объектов, регистров, документов, обменов;
- UI - только для пользовательских форм, команд и видимого поведения.

Если изменение затрагивает взаимодействие объектов, регистров, документов или обменов, включите интеграционную проверку в этот набор.

Если UI-сценарий нужен и база опубликована для web-клиента, тестируйте через опубликованный URL. Если публикации нет, используйте доступный user-mode сценарий для копии базы ветки или явно зафиксируйте ограничение в отчете.

Если executable milestone или финальная проверка упали, агент не должен останавливаться на констатации ошибки. Он анализирует отчёт Vanessa, лог 1С, скриншоты и изменённый код, исправляет причину, повторяет затронутые targeted/static проверки и снова выполняет полный helper в рамках bounded recovery. Лимит — 3 попытки на одну группу ошибок. После 3 неуспешных попыток агент останавливается, фиксирует диагностику и просит решение разработчика.

В `test-report.md` OpenSpec change нужно записать, какие сценарии запускались, какой тип проверки использован, где лежит отчет Vanessa и какие ошибки были исправлены.

Только после успешного тестирования можно переходить к review или выгрузке `CF`.

### 7. Code review, если нужно

Code review не запускается автоматически.

Если нужен отдельный review, попросите явно:

```text
Сделай code review изменения <change-id>.
Проверь риски, ошибки, регрессии, недостающие проверки и соответствие OpenSpec.
```

Review должен искать:

- возможные ошибки выполнения;
- регрессии;
- нарушение требований OpenSpec;
- рискованные изменения метаданных;
- недостаточные проверки;
- лишние изменения вне задачи.

### 8. Выгрузить результат

Если нужно передать текущую версию изменений в базу, подключенную к хранилищу:

```text
/itl-result
```

В Codex:

```text
$itl-result
```

Если нет свежей успешной проверки Vanessa, helper применяет `VERIFICATION_POLICY`. По умолчанию `warn`: агент должен предупредить об этом, а получить результат без такой проверки можно только после явного подтверждения разработчика. В режиме `block` helper запрещает result до fresh passed `/itl-check` или `verify helper action`.

### 9. Закрыть OpenSpec change

После приемки изменения нужно заархивировать OpenSpec change:

```text
/opsx-archive

Заархивируй принятый OpenSpec change <change-id> и синхронизируй specs.
```

Архивация переносит согласованные изменения требований из `openspec/changes/<change-id>/` в актуальные спецификации проекта.
